# Релиз

Правила кода — `AGENTS.md`, тесты — `CLAUDE.md`. Здесь только выпуск версии: что менять,
в каком порядке и что проверить. Всё ниже снято с прошлых релизов (`git show 2edffab` для
0.11.0, `4fd9150` для 0.12.0) и с `.github/workflows/build-release.yml`.

```
0. Где мы → 1. Версия и дата → 2. main → 3. Пять файлов → 4. Коммит + тег → 5. Пуш → 6. Проверка
```

## 0. Где мы

- Релиз делается **на `main`**, не на ветке фичи: тег собирает только то, что в нём. Если
  просят выпустить, а main отстаёт от смерженной работы — сначала PR, потом релиз.
- `git checkout main && git fetch origin && git merge --ff-only origin/main`.
- Последний релиз — `git tag --sort=-v:refname -l 'v*' | head -3`. **Не** `git describe
  --tags`: в клоне есть локальный тег `nightly`, и `describe` вернёт его, а не версию.
- Что войдёт: `git log --oneline <тег>..main | wc -l` и раздел `## Unreleased` в
  `CHANGELOG.md`. Пустой `Unreleased` — выпускать нечего, спросить пользователя.
- Рабочее дерево чистое: в релизный коммит идут ровно эти пять файлов.

## 1. Версия и дата

- **Минор** (`0.11.0 → 0.12.0`) — все релизы с v0.6.0 такие: в `Unreleased` есть то, что
  пользователь видит. **Патч** (`0.11.1`) — только исправления.
- Суффикс (`-alfa`, `-rc.1`) — только если правда нужен предрелиз: дефис в теге делает
  релиз `prerelease` (в воркфлоу `contains(github.ref_name, '-')`), и он не станет Latest.
- Дата — сегодняшняя, ISO: `2026-11-07`.
- Версию и сводку пользователь видит в релизе — назвать их в ответе до пуша.

## 2. Пять файлов

От релиза к релизу правка одна и та же — 5 файлов, `+6 −4`:

1. **`CHANGELOG.md`** — под `## Unreleased` вставить строку `## v<версия> — <дата>` и пустую
   после неё; выше остаётся пустой `## Unreleased`. Записи идут новыми сверху, раздел
   закрывается **целиком** — даже если в нём остались строки старше прошлого релиза.
2. **`package.json`** — `"version"` (строка 5).
3. **`src-tauri/Cargo.toml`** — `[package] version` (строка 3).
4. **`src-tauri/Cargo.lock`** — запись `name = "kibo-agent"` и её `version`. В lock десятки
   чужих `0.11.0`: правка адресная, не `sed` по файлу.
5. **`src-tauri/tauri.conf.json`** — `"version"` (строка 4); отсюда Tauri берёт версию сборки,
   поэтому он и `Cargo.toml` должны совпадать.

**Проверка версий — до коммита.** В репозитории уже есть тест на это, писать заново
нечего: `the_version_in_the_window_is_the_one_the_build_sends` в `src-tauri/src/architecture.rs`.
Он сверяет версию bundle (`tauri.conf.json` — её показывает About через `getVersion()`) с
`env!("CARGO_PKG_VERSION")` из `Cargo.toml` и падает с «… are bumped together», если поднята
только одна из двух.

```bash
cd src-tauri && cargo test the_version_in_the_window_is_the_one_the_build_sends
```

Он не покрывает `package.json` и `Cargo.lock` — их сверяет эта команда, без сборки:

```bash
bun -e "console.log('tauri', require('./src-tauri/tauri.conf.json').version, 'pkg', require('./package.json').version)"
cd src-tauri && cargo metadata --no-deps --format-version 1 >/dev/null && echo lock-ok
```

Больше `cargo test` для релиза из одной версии не нужен — кода правка не трогает. Но если
релиз выпускается вместе с непроверенным кодом, проверки из `CLAUDE.md` — до коммита.

## 3. Коммит

Сообщение — как у прошлых: `release: <версия>`, затем пустая строка и трейлер.

```bash
git add CHANGELOG.md package.json src-tauri/Cargo.lock src-tauri/Cargo.toml src-tauri/tauri.conf.json
git commit -m "release: 0.12.0" -m "Co-authored-by: Kibo <334272053+kibo-coder@users.noreply.github.com>"
git show --stat HEAD   # 5 файлов, +6 −4
```

## 4. Тег и сообщение релиза

Тег **аннотированный** и указывает на релизный коммит: из его сообщения берётся первая часть
описания релиза, остальное добавляется само. Три части страницы релиза (так собрано у v0.11.0):

```
## What's new      ← сообщение тега с 3-й строки: анонс, его пишем мы
## Changelog       ← дописано воркфлоу: раздел `## v<версия>` из CHANGELOG.md
## What's Changed  ← сгенерировано GitHub: смерженные PR с прошлого релиза
**Full Changelog**: …/compare/v0.11.0...v0.12.0
```

**Анонс — короткий и по делу:** 3–6 буллетов, строка на фичу, словами пользователя — что он
теперь может. Это заголовки фич, а не перечень изменений: «Редизайн окна и голосовой ввод»,
«Два режима — Analyst и Agent». Без дат (они в Changelog), без имён файлов и внутренностей.
Всё остальное читатель найдёт ниже, в списке из changelog, поэтому в анонс не тянуть.

- Строка 1 — `Kibo Agent <версия>`: название релиза.
- Строка 2 — пустая: воркфлоу берёт тело с третьей (`tail -n +3`).
- Строка 3 — `## What's new`, дальше буллеты вида `- **Заголовок фичи** — что пользователь
  теперь может`, как в релизе v0.12.0.
- `--cleanup=verbatim` обязателен: без него git считает строки на `#` комментариями и
  выбрасывает `## What's new` из тега (так вышел 0.13.0, заголовок вернули правкой релиза).
- Строки CHANGELOG и список PR **не повторять** — их добавляют воркфлоу и GitHub.
- `## Changelog` в теле не писать: для воркфлоу это значит «changelog уже есть», и раздел из
  `CHANGELOG.md` не добавится (`grep -q '^## Changelog'` в `build-release.yml`).
- Список PR — это смерженные PR с прошлого релиза; работа, попавшая в main без PR, в нём не
  появится, так что анонс не должен на него полагаться.

```bash
git tag -a --cleanup=verbatim v0.12.0 -m "Kibo Agent 0.12.0" -m "## What's new

- **Voice input** — dictate into the message box from the microphone button or a held Option or Alt key, in Russian, recognized on this computer
- **Two modes instead of three** — Analyst answers with the file and line as evidence, and Agent asked for a plan writes it and offers an Implement button
- **A redesigned window** — a compact message box with its settings in a panel under it, and a Kubernetes chat's cluster in a chip of its own"

git cat-file -t v0.12.0          # tag, не commit
git rev-parse v0.12.0^{commit}    # = HEAD
git cat-file -p v0.12.0 | sed -n '6,9p'   # пустая строка, ## What's new — как прочитает воркфлоу
```

Опечатка после пуша: сам тег не переписать (он уже ушёл), а тело релиза правится
`gh release edit v0.12.0 --notes-file <файл>` — буллеты анонса при этом надо повторить
в файле целиком.

## 5. Пуш

Пуш необратим: после него уходит публичный релиз, и отменить тег — только удалением
релиза и тега с последующим выпуском нового. Делать после подтверждения пользователя.

```bash
git push origin main
git push origin v0.12.0
```

- `main` — прогон `Tests` и `Build and Release` на main: он заменяет предрелиз `nightly`.
- Тег — `Build and Release` на теге: Windows (MSI/NSIS) и macOS (DMG), затем job `release`
  публикует GitHub-релиз с установщиками. Полчаса с небольшим (0.12.0 — 27 минут).
- Пушить оба: nightly и релиз собираются из одного коммита.

## 6. Проверка

```bash
git ls-remote origin main 'refs/tags/v0.12.0*'   # оба коммита — тот, что в теге
gh run list --limit 5                            # Tests (main), Build/Release (main и тег)
gh release view v0.12.0                          # когда сборка кончилась
```

Что должно сойтись: тег на GitHub — объект `tag`, его `^{}` — релизный коммит; в описании
релиза — три части: `## What's new` с анонсом из тега, `## Changelog` с разделом из
`CHANGELOG.md`, `## What's Changed` со списком PR и ссылкой `Full Changelog`; к релизу
приложены `.msi`, `.exe`, `.dmg`; `prerelease` — только при дефисе в теге.

## Что обычно идёт не так

- **`nightly` вместо версии** — `git describe` в этом клоне бесполезен (локальный тег
  `nightly` остаётся на старом коммите и после релиза; на сервере его пересоздаёт воркфлоу,
  локальная копия просто устаревает).
- **Тело релиза не то** — почти всегда легковесный тег или тег не на нужном коммите:
  `actions/checkout` заводит у себя легковесный тег, и `git tag --format=%(contents:body)`
  на нём отдаёт тело коммита (так в 0.6.1 в релиз уехал один `Co-Authored-By`). Поэтому
  `git tag -a`, а воркфлоу читает сообщение через API.
- **Описание релиза — один плотный абзац** — так вышел 0.12.0: чтобы понять, что принёс
  релиз, его надо дочитать до конца. Анонс — буллеты, по строке на фичу.
- **Раздел CHANGELOG не попал в релиз** — в нём нет строки, начинающейся ровно с
  `## v<версия> ` (пробел после версии), либо тег указывает на коммит без неё.
- **Версия в установщике старая** — правлена не `tauri.conf.json`, или добавляли её после
  коммита: сборка тега берёт файл из тега, а не из рабочего дерева.
- **Пять файлов, а не два** — `Cargo.lock` и `package.json` держат версию отдельно.
  Забытые `tauri.conf.json` или `Cargo.toml` ловит тест
  `the_version_in_the_window_is_the_one_the_build_sends`; `package.json` и `Cargo.lock` —
  уже нет, только команда сверки выше.
- Тег и main пушатся вместе; пуш только тега оставит main без релизного коммита, и
  следующий nightly соберётся из версии, которой нет в истории.

## Итог пользователю

Коротко: версия и дата, что в разделе CHANGELOG (сколько строк, главное), хеш коммита и
тега, что запушено, номера запущенных прогонов и через сколько ждать релиз, срок прошлой
сборки для ориентира. Опубликованный релиз — ссылкой.
