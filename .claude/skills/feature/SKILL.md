# Фича: от исследования до PR

Цикл, по которому в этом репозитории делается любая фича. Правила кода — в `AGENTS.md`,
команды тестов — в `CLAUDE.md`; здесь только порядок работы и что сдаётся на каждом шаге.

```
0. Где мы  →  1. Ветка  →  2. Исследование  →  3. План в docs/
                                                    ↓
        ┌──→ 4. Этап: код + тесты → 5. Мутации → 6. Ревью сабагентом → 7. Коммит ──┐
        └────────────────────────── следующий этап ←───────────────────────────────┘
                                                    ↓
                                     8. Финал: CHANGELOG, main, PR
```

Документы и план — по-русски, как весь `docs/`. Код, комментарии, коммиты и PR — по-английски.

## 0. Где мы

Сначала понять, новая это фича или продолжение — по аргументу скилла и состоянию репозитория:

- `git status`, `git branch --show-current`, `git log --oneline origin/main..HEAD`.
- Есть план фичи в `docs/` (строка в `docs/README.md`, статус в его второй строке)?
  Тогда продолжение: первый этап «Нарезки» без отметки «сделано» — текущий.
- PR этой ветки уже смержен — это новая работа: новая ветка от main (шаг 1), старая не
  переиспользуется.

## 1. Ветка — всегда от свежего main

Никогда не работать в `main` и не начинать фичу от старой ветки:

```bash
git fetch origin main
git checkout -b feature/<slug> origin/main   # fix/<slug> — для исправления, docs/<slug> — для одного документа
```

`<slug>` — короткое имя фичи латиницей через дефис (`feature/knowledge-base`,
`feature/session-usage`). Если работа продолжается на существующей ветке, а main ушёл
вперёд — `git merge origin/main` (merge, не rebase: так в этой истории принято), конфликты
решить, проверки прогнать заново.

## 2. Исследование — до любого кода

Цель — знать, что уже есть и что переиспользуется, прежде чем что-то решать.

- `docs/README.md` — нет ли уже документа на эту тему или соседней (исследование,
  предложенный план, «Вне плана» другой фичи). Найденное читать целиком.
- `AGENTS.md` — какие правила затронет фича: слой, sink и канал событий, инструмент агента
  (таблица мест), команда (обёртка в `src/lib/`, `generate_handler!`, capability, `async`
  через `commands::blocking`), фича в Catalog (`domain/features.rs`), UI-компоненты.
- Код: найти ближайший аналог того, что предстоит написать, и читать его, а не
  придумывать форму заново. Для широкого обхода многих файлов можно отдать поиск агенту
  `Explore`; выводы сверять с кодом самому.
- `src/architecture.rs` — какие правила слоёв проверяются тестом и какие исключения уже есть.
- Если нужен внешний факт (API, поведение платформы, версия крейта) — проверить, а не
  вспоминать; дешёвую пробу без кода приложения можно сделать сразу и записать результат.

Итог исследования — не сообщение в чат, а разделы «Что уже есть» и «Решения» в плане.
Решения, которые принадлежат пользователю (продуктовые развилки, цена против пользы),
собрать в «Открытые вопросы» и задать после плана — не угадывать.

## 3. План — документ в `docs/`

Файл `docs/<NN>-<slug>.md`, `NN` — следующий свободный номер после самого большого.
Структура и тон — по [plan-template.md](plan-template.md) и последним планам
(`docs/40-knowledge-base.md`, `docs/42-agent-browser.md`). Главное:

- **Кода в документе нет — только решения**, каждое с причиной и отвергнутой альтернативой.
- **Нарезка** — этапы с префиксом фичи (`KN-1`, `BR-0`…). Каждый этап — законченный кусок,
  который проходит все проверки и коммитится сам по себе; в нём названо, что входит и какими
  тестами это проверяется. Этап 0 — проба, если решение держится на непроверенном факте.
- Строка в таблице `docs/README.md`: «План, предложен <дата>: <суть>».

Коммит плана — отдельный: `docs: plan for <what>`. Затем — короткое резюме пользователю
(решения, этапы, открытые вопросы) и **остановка до его ответа**, если он заранее не сказал
идти по этапам без остановок. Ответы на вопросы вносятся в документ («~~вопрос~~ — решено: …»).

## 4. Этап — реализация

Ровно один этап из «Нарезки». Если по ходу этап оказался не таким, как в плане, — сначала
поправить план (что поменялось и почему), потом код.

Держать в голове из `AGENTS.md`: слои и направление зависимостей; ошибки — `thiserror` в
`domain/`, строки только в `commands/`; никаких `unwrap()` вне тестов; события — сигнал
перечитать, канал — `pub const` с тестом; пути — `Path`/`PathBuf`, канонизация против корня;
настройки — `settings_store::update`; UI — `Dropdown`, `Modal`, `shortcuts.ts`, токены из
`tokens.css`, свой CSS у переиспользуемого компонента. Новый инструмент агента — все места
из таблицы в `AGENTS.md`, включая те, что не держит ни компилятор, ни тест
(`describeTool.ts`, иконка в `ChatPanel.tsx`).

Тесты пишутся вместе с кодом: Rust — `#[cfg(test)] mod tests` рядом с кодом, фронт —
`src/__tests__/` на `bun test`. Этап готов к мутациям, когда зелёные все проверки:

```bash
bun run tsc --noEmit && bun test
cd src-tauri && cargo check && cargo test
```

Если этап тронул то, у чего есть живой тест или бенч из `CLAUDE.md` (модель эмбеддингов,
`code_search.rs`, цикл/промпт/инструмент агента, роль Kubernetes, `image_sanitize.rs`,
`kube_client.rs`, запись звонка, денойзер) — прогнать его, а если нельзя здесь (нет ключа,
кластера, macOS) — записать в отчёт этапа как «не проверено» и сказать пользователю.

## 5. Мутационная проверка

Метод — [`docs/11-mutation-testing.md`](../../../docs/11-mutation-testing.md), прочитать перед
первым прогоном. Коротко:

- По одной мутации на каждое правило, которое тест обязан охранять (снятая проверка,
  ослабленное условие, возврат умолчания, выброшенная ветка, порядок, уборка ресурса,
  обнулённый предел, утечка). Мутация — правдоподобная ошибка, а не абсурд.
- Бэкенд — всегда; фронт — если в этапе есть нетривиальная логика (хук, хелпер в `src/lib/`).
- План — JSON во временной папке (scratchpad), не в репозитории. Фильтр тестов узкий, но
  покрывает все тесты, которые могли бы поймать правку:

  ```bash
  python3 scripts/mutate.py <scratchpad>/plan.json -k
  ```

- **Выжил** — это недостающий тест: написать его сейчас, повторить мутацию, она должна
  упасть. **Эквивалентная** — записать как эквивалентную, не чинить. **Не собрался** —
  переформулировать. **Завис** — пойман.
- Если мутация падает не на том тесте, для которого писалась, — разобраться, что тот тест
  охраняет на самом деле.

Отчёт — в строку этапа в плане: «**XX-N. … — сделано.** Мутационная проверка: N мутантов,
все пойманы (M выжили в первом прогоне — <что ломали>; тесты добавлены)».

## 6. Ревью сабагентом с чистым контекстом

Ревьюер не должен знать, как автор рассуждал, — только код и план. Поэтому агент
`general-purpose`, **не** `fork` (fork наследует весь контекст этой сессии). Запускать в
foreground (`run_in_background: false`): следующий шаг зависит от его ответа. Промпт —
по [review-prompt.md](review-prompt.md), с подставленными веткой, диапазоном коммитов или
`git diff` этапа, путём к плану и id этапа.

Каждую находку проверить самому — это утверждение, а не приказ:

- Настоящий дефект — исправить, с тестом; новая логика в исправлении — тоже под мутацию.
- Неверная или не стоящая своего кода находка — не трогать, а сказать пользователю в
  итоге этапа, почему.
- Вопрос дизайна, выходящий за этап, — пользователю, не решать молча.

После исправлений — снова все проверки из шага 4.

## 7. Коммит этапа

- Коммит по одному слою или одной заботе, где это естественно: этап — это обычно несколько
  коммитов, исправления по ревью — отдельный (`knowledge: review fixes — …`).
- Сообщение — как в истории: `<area>: <что теперь так, строчными>`, без точки, затем
  абзац о том, что и почему изменилось для пользователя или кода. В конце — строки
  атрибуции из системного напоминания сессии.
- В том же или последнем коммите этапа — план обновлён: этап отмечен «— сделано» с
  отчётом мутаций и тем, что не проверено; статус во второй строке плана и в
  `docs/README.md` («План, KN-1…KN-3 сделаны: …»).
- `git push -u origin <branch>` после каждого этапа — контейнер одноразовый.

Итог пользователю — коротко: что сделано в этапе, какие проверки прогнаны (с числом
тестов), мутации, что нашло ревью и что с этим сделано, что не проверено. Дальше — следующий
этап (шаг 4) или остановка, если пользователь так просил.

## 8. Финал: PR

Когда все этапы, которые пользователь хотел в этом PR, сделаны:

1. `CHANGELOG.md`, под `## Unreleased`, сверху — одна строка на фичу: `- <дата> <что
   пользователь теперь может>`. Рефакторинг, тесты и невидимые исправления строки не получают.
2. План и `docs/README.md` — итоговый статус («Сделано XX-1…XX-N», и что не проверено руками).
3. `git fetch origin main && git merge origin/main`, конфликты решить, проверки — заново,
   push.
4. PR в `main` через `mcp__github__create_pull_request` (шаблона в `.github/` нет), по образцу
   смерженных (#56):

   ```markdown
   <Абзац: что пользователь теперь может. Дизайн и этапы — в `docs/NN-<slug>.md`.>

   ## What changed, by phase

   - **XX-1. <Имя>.** <Что сделано.>
   - …

   ## For the reviewer

   - <main смержен (`<sha>`), конфликты и как решены.>
   - **Not checked by hand:** <что не проверено в запущенной программе / живыми тестами и почему.>

   ## Checks

   - `bun run tsc --noEmit`, `bun test` (N pass), `cargo check`, `cargo test` (N pass), после мержа main.
   - Mutation runs (`scripts/mutate.py`) for each phase: <итог, выжившие и чем закрыты>.

   <строки атрибуции из системного напоминания сессии>
   ```

5. Ссылку на PR — пользователю, и предложить следить за ним (`subscribe_pr_activity`):
   CI на Windows и macOS, ревью.
