# Язык постановки: термины и типовые формулировки

> **Цель файла**: Словарь принятых терминов и шаблонов формулировок. Используй как справочник перед написанием любого раздела постановки, чтобы текст звучал «по-своему» для внутреннего читателя.

## Когда применять

- Пишешь любой раздел документа — сверяйся с таблицей терминов.
- Формулируешь шаг алгоритма или поведение при ошибке — бери готовые шаблоны из раздела «Типовые формулировки».
- Редактируешь чужую постановку — не «улучшай» язык, сохраняй принятый стиль.

---

## 🛑 Критические правила

1. **Аббревиатуры никогда не расшифровываются** — ни в скобках, ни сноской, ни в первом упоминании. Расшифровка — маркер «чужого» документа. Пиши: `УЛ`, `СОПД`, `МКС`, `ЭА`, `НТ`, `ОБИП`.
2. **Никаких имён реализации.** Java-классы, бины, интерфейсы, пакеты, Spring/WebFlux/Kafka/Mongo — всё это не попадает в постановку. Исключение: **внешние контракты** (`customers-api#getByIdsV2`, метод `save` в `SignModule`, коллекция `TaxSecretsDocPack`).
3. **Сленг не заменяется синонимами.** «Пакет документов» — всегда так, никогда «комплект» или «набор». «Ручка» — всегда так, никогда «эндпоинт» или «хэндлер».

## Что НЕ должно попадать в текст

### Категорически запрещено

- Имена классов, бинов, интерфейсов, пакетов Java
- Названия библиотек и фреймворков (Spring, WebFlux, React, Kafka)
- Слова-маркеры реализации: «реактивный», «нон-блокинг», «консьюмер», «продюсер», «ретрай»
- Технические подробности внутренней архитектуры (слои, паттерны, очереди)

**Почему**: Постановка живёт дольше реализации и не должна ломаться при переписывании кода.

### Исключение — внешние контракты

Их имена **обязательны**:

- `customers-api#getByIdsV2`
- `/document/tax-secrets-consent`
- метод `save` в `SignModule`
- коллекция `TaxSecretsDocPack` и её поля (`inn`, `fnsId`, `status`)

## Примеры стиля

**Хорошо ✓**

> Для получения данных организации использовать сервис МКС `customers-api#getByIdsV2`.
> Вернуть исключение с кодом `CUSTOMER_NOT_FOUND` при отсутствии клиента.
> Заполняется значением `inn` из ответа, полученного на шаге 2.

**Плохо ✗**

> Мы получаем данные организации через сервис МКС.
> Сервис должен будет проверить наличие клиента и бросить исключение, если его нет.
> Используем значение inn, которое получили на предыдущем шаге.

Разница ровно в трёх вещах: безличный инфинитив вместо «мы», настоящее время вместо «должен будет», ссылка на шаг по номеру вместо «предыдущего».

## Типовые формулировки

### Про заполнение параметра

- «Заполняется входным параметром A-userId»
- «Заполняется значением CORP-<ПРОЕКТ>»
- «Не заполняется»
- «Использовать значение inn из ответа, полученного на шаге 2»
- «Использовать значение fnsInfo.fnsId коллекции TaxSecretsDocPack»
- «Берётся из входного параметра A-userId»
- «передаем текущую дату» / «не передаем»

### Про вызов соседа

- «Вызывается метод МКС для проверки прав пользователя.»
- «Для получения данных организации необходимо использовать сервис МКС `customers-api#getByIdsV2`.»
- «Необходимо получить документ СОПД из ОБИП. Для этого вызывается метод `/document/tax-secrets-consent` …»
- «В качестве ответа метод возвращает сформированный pdf документ.»

### Про ветвление и ошибки

- «Если проверка выполнена успешно (`resultCode = OK`), выполняется следующий шаг.»
- «Если метод вернул ошибку, остановить работу метода и вернуть ошибку (500 ошибка c `type = SERVER_ERROR`, `code = SIGN_ERROR`, описание: `"Не удалось отправить файлы в модуль подписания"`).»
- «Если получена ошибка 4ХХ, 5ХХ — вернуть стандартный responseError.»
- «Вернуть исключение с http code 400 (Bad Request), указанием на некорректный параметр — `"A-userId не указан"`, `type = VALIDATION_ERROR` и `code = INCORRECT_CONTRACT`»

### Про выходные данные соседа

- «В ответе возвращается массив со списком компаний. Приведены только параметры, которые используются в методе для формирования СОПД по шаблону.»

### Про ответ ручки

- «Сформировать ответ следующим образом:»
- «Проставляется по каждому отправленному документу»

## Мелочи оформления, по которым узнают свой документ

- **Диапазоны кодов** — кириллическими Х: «4ХХ, 5ХХ» (не `4xx`, `4XX`).
- **Перенос строки** — `+` в конце строки (ставится часто в AsciiDoc).
- **Значения enum и константы** — как есть, латиницей, без кавычек: `KALUGA`, `ALFA_BANK`, `BACKEND`, `NIB`, `CORP-<ПРОЕКТ>`.
- **Тексты ошибок** — в двойных кавычках внутри предложения.
- **Прочерк в пустой ячейке** «Варианты значений» — дефис (`-`).
- **Комментарии-подсказки** для следующего автора (`// инклюдим пример ответа…`) — **не вычищать** при правке чужой постановки.

## Проблемные ситуации

### Термина нет в таблице

Если встретилось слово, которого нет в словаре:

1. Проверь, не является ли оно синонимом существующего термина (например, «комплект» вместо «пакет документов» → используй «пакет документов»).
2. Если это действительно новый термин — спроси пользователя, как его принято называть в контуре.
3. Не придумывай русские аналоги английским аббревиатурам.

### Пользователь использует «неправильный» термин в запросе

Если пользователь написал «оформи эндпоинт» или «опиши контроллер» — не поправляй его явно, но в самом документе используй правильный термин («ручка», «метод»).

### Сомневаешься, можно ли упоминать технологию

Правило простое: если технология влияет на **бизнес-поведение** (например, «асинхронная обработка» vs «синхронная»), то можно. Если это деталь реализации («реактивный WebClient»), то нельзя.
