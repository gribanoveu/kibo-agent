# Ошибки: коды, типы, формулировки

> **Цель файла**: Стандарты описания ошибок в постановках. Читай этот файл всегда, когда в документе появляется хотя бы одна ошибка (практически всегда).

## Когда применять

- Заполняешь раздел «Обработка ошибок»
- Описываешь поведение при ошибке в шаге алгоритма
- Определяешь `type`/`code` для новой ошибки
- Описываешь ответ соседней системы с возможными сбоями

---

## 🛑 Критические правила

1. **Не меняй существующие коды самовольно.** Если у ошибки уже есть закреплённый `type`/`code` (из существующей версии документа, контракта или реализации) — оставь его как есть, даже если он расходится со стандартной таблицей. Код — часть контракта, который разбирают потребители. Явно укажи пользователю на расхождение, но решение за ним.
2. **Каждая строка таблицы ошибок обязана иметь пару в теле документа** (в таблице валидации или в завершающем абзаце шага), и наоборот. Расхождение — самая частая претензия на ревью.
3. **Текст ошибки пишется от лица системы**, без «пожалуйста» и без технических подробностей наружу.

## Раздел «Обработка ошибок»

Всегда **последний раздел** документа, и заголовок у него именно такой: проверка K.7.1 ищет раздел «Обработка ошибок», а `== Коды ошибок` вместо него её не проходит. «Коды ошибок» — это подпись перед таблицей внутри раздела, а не заголовок.

> Готовая разметка этого раздела — include, подпись и таблица — в образце (`docStandards`, `op: "guide"`, `topic: "template"`), раздел «Обработка ошибок». Бери её оттуда и заполняй строки; словарь `type`/`code` ниже в этом файле.

Структура фиксирована:

```asciidoc
== Обработка ошибок
Описание приведено по ссылке ниже.

include::../CompositeException.adoc[]

*Коды ошибок*

|===
|*Условие* |*Описание* |*Type* |*Code*

|Шаг 1. Валидация. Не указан параметр
|A-userId не указан
|VALIDATION_ERROR
|INCORRECT_CONTRACT

|Шаг 5. Запрос файла СОПД. Не удалось получить СОПД
|Не удалось получить данные организации в customers-api
|SERVER_ERROR
|DOCUMENTS_ERROR
|===
```



### Правила заполнения таблицы

- Таблица — сводка **всех** ошибок документа, по строке на каждую.
- Условия идут в том же порядке, в каком встречаются в документе: сначала валидация (в порядке параметров), затем шаги по номерам.
- Условие для шага начинается с номера и названия шага: «Шаг 5. Запрос файла СОПД. Не удалось получить СОПД».
- Описание в этой таблице — тот же текст, что уходит пользователю в ошибке, с заглавной буквы, без кавычек.
- Каждая строка таблицы обязана иметь пару в теле документа (в таблице валидации или в завершающем абзаце шага), и наоборот. Расхождение между ними — самая частая претензия к постановке на ревью.
- Пустых ячеек в таблице нет: она четырёхколоночная, а пустая ячейка проваливает проверку K.4.2/K.5.2.

### Если состав ошибок пришёл из артефакта

Артефакт возвращает поле `errors` — черновую таблицу из двух колонок (`Код`, `Описание`). Это заготовка, а не готовый раздел: перенеси строки в форму выше, добавив «Условие» (шаг и что пошло не так) и разложив код на пару `Type`/`Code` по таблице ниже. Вставлять `errors` в документ как есть нельзя.

## Стандартные пары type/code

Эта таблица — **дефолт для нового случая**, когда точного `type`/`code` ещё нет.


| Ситуация                                    | http          | type               | code                     | Когда использовать                                                 |
| ------------------------------------------- | ------------- | ------------------ | ------------------------ | ------------------------------------------------------------------ |
| Не передан или невалиден входной параметр   | 400           | `VALIDATION_ERROR` | `INCORRECT_CONTRACT`     | Любая ошибка валидации входных данных                              |
| Сущность не найдена / не связана с клиентом | 400 (или 404) | `VALIDATION_ERROR` | `INCORRECT_CONTRACT`     | Запрашиваемый объект не найден или не принадлежит пользователю     |
| Нет прав на работу с организацией           | 403           | `ACCESS_DENIED`    | `PERMISSION_FAILED`      | Проверка прав вернула отказ                                        |
| Техническая ошибка при проверке прав        | 403           | `ACCESS_DENIED`    | `PERMISSION_ERROR`       | Сбой при вызове сервиса проверки прав                              |
| Не получены данные организации              | 500           | `SERVER_ERROR`     | `CUSTOMER_SERVICE_ERROR` | Сбой в `customers-api`                                             |
| Не получены данные пользователя             | 500           | `SERVER_ERROR`     | `USER_SERVICE_ERROR`     | Сбой в сервисе пользователей                                       |
| Не удалось сформировать/получить документ   | 500           | `SERVER_ERROR`     | `DOCUMENTS_ERROR`        | Любой сбой при работе с документами (формирование, получение СОПД) |
| Не удалось отправить документы на подпись   | 500           | `SERVER_ERROR`     | `SIGN_ERROR`             | Сбой в модуле подписи (`SignModule`)                               |




### Правила именования кодов

- `<ЧТО>_ERROR` — для технических ошибок (`DOCUMENTS_ERROR`, `SIGN_ERROR`).
- `<СЕРВИС>_SERVICE_ERROR` — когда сбой в конкретном сервисе-соседе (`CUSTOMER_SERVICE_ERROR`).
- Новый код заводи **только** если ни один существующий не подходит по смыслу. Потребители разбирают ошибки именно по `code`.
- Один `code` может стоять у нескольких условий (например, `DOCUMENTS_ERROR` покрывает и формирование XML, и получение СОПД) — это нормально, дублировать домен ради уникальности не нужно.

## Формулировки текста ошибки

Текст пишется от лица системы, коротко, без «пожалуйста» и без технических подробностей наружу.

### Хорошо ✓

- `A-userId не указан`
- `A-userId должен содержать 6 алфавитно-цифровых символов`
- `Не найден пакет документов` *(одинаковый текст для всех причин ненахождения, чтобы не подсвечивать внутреннюю логику)*
- `Отсутствуют права на работу с организацией`
- `Не удалось получить данные организации`
- `Не удалось получить НТ из внешней системы`
- `Не удалось отправить файлы в модуль подписания`



### Плохо ✗

- `Пожалуйста, укажите A-userId` *(есть «пожалуйста»)*
- `Ошибка базы данных при поиске пакета документов` *(техническая подробность наружу)*
- `Пакет документов не найден, потому что клиент не связан с организацией` *(подсвечивается внутренняя логика)*
- `Ошибка вызова SignModule` *(непонятно, что именно не удалось, указано название внешней системы, а не ее бизнес суть)*



### Правила оформления в тексте

- В таблице шага текст даётся в кавычках внутри скобок вместе с кодом: `(403 ошибка c type = ACCESS_DENIED, code = PERMISSION_FAILED, "Отсутствуют права...")`.
- В сводной таблице «Обработка ошибок» — отдельным столбцом без кавычек.

## Обработка ответов соседа

Если сосед возвращает свой `enum` результата — разобрать в таблице выходных параметров **каждое значение** и сразу написать реакцию по шаблону:

```asciidoc
OK - успешная проверка. При данном результате переход на следующий шаг.

FAILED - Пользователь не имеет прав на работу с организацией. При данном результате сформировать ошибку вида "…" (стандартный responseError, 403 ошибка c type = ACCESS_DENIED, code = PERMISSION_FAILED), завершить работу.

ERROR - Получена техническая ошибка. При данном результате сформировать стандартный responseError (403 ошибка c type = ACCESS_DENIED, code = PERMISSION_ERROR), завершить работу.
```



### Транспортные ошибки соседа

Описываются отдельной строкой после перечисления `enum`:

> Если получена ошибка 4ХХ, 5ХХ — вернуть стандартный responseError.



### Компенсации и откаты

- Если есть — описываются **в самом шаге**, не в разделе ошибок.
- Если по бизнесу отката нет — это тоже стоит написать явно одной строкой: `Компенсационные действия не предусмотрены.`

## Проблемные ситуации



### Ситуация подходит под две строки стандартной таблицы

Выбирай более специфичную. Например, если не удалось получить данные организации при проверке прав — это `ACCESS_DENIED / PERMISSION_ERROR`, а не `SERVER_ERROR / CUSTOMER_SERVICE_ERROR`.

### Сосед возвращает нестандартный код ошибки

Если сосед вернул код, которого нет в стандартной таблице — не выдумывай новый `type`/`code` самовольно. Опиши ошибку как `SERVER_ERROR` с соответствующим `_SERVICE_ERROR` кодом, если это технический сбой, или спроси пользователя, если это бизнес-ошибка.

### Ошибка должна быть кастомной (новый домен)

Если ни один существующий код не подходит:

1. Придумай код по правилам именования (`<ДОМЕН>_ERROR` или `<СЕРВИС>_SERVICE_ERROR`).
2. Явно укажи в ответе пользователю: «Предложен новый код ошибки `X`, так как существующие не покрывают данный сценарий».
3. Дождись подтверждения пользователя перед финализацией документа.

## Чек-лист по ошибкам

Перед выдачей документа проверь:

- [ ] Раздел «Обработка ошибок» — последний в документе
- [ ] В разделе есть `include::../CompositeException.adoc[]` и таблица кодов
- [ ] Каждая строка таблицы ошибок имеет пару в теле документа (валидация или шаг)
- [ ] Условия в таблице идут в том же порядке, что и в документе (валидация по параметрам → шаги по номерам)
- [ ] Условие для шага начинается с номера и названия: «Шаг 5. Запрос файла СОПД. Не удалось получить СОПД»
- [ ] Текст ошибки в таблице — с заглавной буквы, без кавычек
- [ ] Для каждого `enum` ответа соседа описана реакция
- [ ] Транспортные ошибки соседа (4ХХ, 5ХХ) описаны отдельной строкой
- [ ] Существующие коды не изменены самовольно (если были в контракте/старой версии)
