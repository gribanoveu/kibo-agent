# Разделы постановки: что и как писать

> **Цель файла**: Подробный разбор каждого раздела документа. Читай этот файл **перед написанием нового документа целиком**. При точечной правке достаточно найти нужный раздел.

## Когда применять

- Создаёшь новую постановку с нуля — читай всё сверху вниз.
- Правишь существующую постановку — открой нужный раздел и сохрани его стиль.
- Сомневаешься в формате таблицы (REST vs Thrift) или синтаксисе `include::` — сверься со шпаргалками ниже.

---

## 🛑 Критические правила

1. **Порядок разделов фиксирован.** Отступать от структуры нельзя. Файлы папки метода: `{methodName}.adoc`, `request.adoc`, `response.adoc`, `{methodName}.puml` — заполняй основной сверху вниз.
2. **REST и Thrift таблицы не смешиваются.** Форма таблицы входных параметров зависит от транспорта **самого метода**. Не делай REST-таблицу для Thrift-метода и наоборот.
3. **Состав параметров берётся только из контракта.** Никогда не выдумывай поля, форматы и обязательность. Если данных нет — запроси артефакт или спроси пользователя.
4. **При правке существующего документа** — сохраняй нумерацию шагов, стиль таблиц и набор `include::`. Не переформатируй чужие разделы «по дороге».
5. **В таблицах от четырёх колонок не бывает пустых ячеек.** Нечего написать — ставь дефис. Пустая ячейка проваливает проверку K.4.2/K.5.2 (`docStandards`).

## 1. Шапка документа

Фиксированная структура, атрибуты не менять:

```asciidoc
= Rest-метод createSignOperationV2
:sectnums:
:sectnumlevels: 3
:toc: left
:toclevels: 3
:toc-title: Оглавление

== Назначение
```

🛑 **Пустой строки между заголовком и атрибутами быть не должно.** Она закрывает шапку документа, и `:toc:` перестаёт действовать — оглавление не отрисовывается вовсе. Проверка K.2.1 этого не поймает: она ищет в тексте строку `:toc:`, а не рабочее оглавление. Пустая строка нужна только *после* последнего атрибута, перед первым разделом.

Комментарии `//` перед заголовком шапку не ломают, а вот `// комментарий` в конце самой строки заголовка — не комментарий: он попадёт в заголовок документа как текст.

**Заголовок**: тип транспорта (`Rest-метод` / `Thrift-метод`) + имя ручки в camelCase, как она называется в контракте.
- ✓ `Rest-метод createSignOperationV2`
- ✗ `Метод API createSignOperationV2`, `createSignOperationV2 (создание операции подписи)`, `"createSignOperationV2"`

## 2. Назначение

Два-четыре предложения: что делает ручка, в каком модуле живёт, для какой ветки бизнес-процесса используется.

**Типовая формулировка**:
> Новая версия метода X создания … На текущий момент метод используется для ветки обмена с оператором для обмена с ФНС Калуга Астрал.

### Отличия от старой версии

Если метод — новая версия существующего, сразу после «Назначения» идёт блок `*Отличия от метода <старое имя>*` списком. Каждое отличие — одной строкой, по существу.

**Сравнение идёт по фактам**: транспорт, расположение параметров, соседние ручки, состав и количество файлов, новые обязательные значения.

```asciidoc
*Отличия от метода createSignOperation*

- Реализация метода createSignOperationV2 на REST-API (createSignOperation — Thrift API)
- В методе createSignOperation данные передаются в теле запроса, в createSignOperationV2 — в заголовках и path
- При отправке документов в SignModule в методе createSignOperationV2 передаются 3 файла ...
```

## 3. Описание входных/выходных параметров

Форма таблицы зависит от транспорта, поэтому перед её заполнением определи транспорт: если в теле запроса есть объект `userData`, а URL заканчивается на `/tapi` — это Thrift, иначе REST.

### Входные параметры (REST)

Таблица со столбцами: **Тип параметра | Параметр | Формат | Обязательность | Описание | Варианты значений**.

**Порядок строк:**

1. `Метод` (POST/GET/…) и `Endpoint` с полным шаблоном `https://{host}/<сервис>/<путь>/{pathParam}/...`. Эти две строки занимают всю ширину таблицы через `5+|`, а не четыре пустые ячейки:

   ```asciidoc
   |Метод 5+| POST
   |Endpoint 5+| https://{host}/<сервис>/<путь>/{pathParam}
   ```

2. Стандартный блок заголовков (переносится без изменений, включая дефисы в пустых «Вариантах значений»):

| Параметр | Формат | Обязательность | Описание | Варианты значений |
|---|---|---|---|---|
| A-userId | string (length 6 or 9) | required | Идентификатор УЛ интернет-банка. Заполняется входным параметром A-userId | XAAAAA |
| A-customerId | string (length 6 or 9) | required | Идентификатор клиента. Заполняется входным параметром A-customerId | UAAAAA |
| A-userIp | string | optional | IP УЛ. | 64.233.165.113 |
| A-projectId | string | optional | Идентификатор приложения (модуля приложения) потребителя. | CORP-<ПРОЕКТ> |
| A-clientType | string | required | Тип сервиса инициатора запроса. | FRONT |
| A-channelId | string | required | Идентификатор вызывающей системы (канала). | NIB |

> Этот же блок — в образце (`docStandards`, `op: "guide"`, `topic: "template"`); бери его оттуда и не перепечатывай по памяти.

3. Path-параметры.
4. Body-параметры.

**Важно про описание заголовков:**

- Во **входных параметрах самой ручки** описание заголовка заканчивается на общей фразе.
- В **вызовах соседних сервисов** к той же фразе дописывается, чем поле заполняется на этом шаге: «Заполняется значением CORP-<ПРОЕКТ>», «Заполняется значением BACKEND», «Не заполняется».

**Обязательность:** всегда `required` / `optional` — во всех таблицах, включая body-структуры, Thrift-конверт и таблицы вызовов соседей. Русские `да`/`нет` встречаются в старых постановках; в новых не используются, а при правке существующего документа приводятся к `required`/`optional` вместе с той таблицей, которую и так трогаешь (переписывать документ целиком ради этого не надо).

**Вложенные поля body** — через точку: `Agreement.managerName.firstName`. Порядок — как в контракте.

### Входные параметры (Thrift)

Таблица со столбцами: **Параметр | Формат | Обязательность | Описание** (без «Тип параметра» и без колонки «Варианты значений»; обязательность — `required`/`optional`, как и везде).

**Порядок строк:**

1. `Endpoint` с общим транспортным путём вида `{host}/<сервис>/tapi` (в отличие от REST, он не зависит от конкретного метода).
2. Минимальный конверт `userData` (все подполя обязательные, переносится без изменений):

| Параметр | Формат | Обязательность | Описание |
|---|---|---|---|
| userData | struct | required | Данные пользователя |
| userData.id | string | required | Идентификатор пользователя (xpin/acus) |
| userData.authorizedApplicationId | string | required | Идентификатор приложения |
| userData.ip | string | required | IP-адрес пользователя |
| userData.customerId | string | required | Идентификатор клиента |

> **Важно**: Это минимальный набор. У конкретного метода `userData` может нести дополнительное необязательное поле (например `userData.location`). Это не часть стандарта, а особенность метода — сверяйся с реальным контрактом, не достраивай по аналогии.

3. Собственные поля метода (например `organizationId`, `docPackId`) — каждое отдельной строкой. Их состав **нельзя изобретать** — брать только из контракта/вводных.

### Выходные параметры

Таблица со столбцами: **Параметр | Формат | Обязательность | Описание | Варианты значений** — одна форма для всех таблиц выходных параметров.

- Для структур формат — `struct`, для коллекций — `array`.
- Обязательность — `required`/`optional`: возвращается поле всегда или только в части ответов.
- В описании поля **сразу указывается источник значения**: «использовать значение соответствующего `documents.documentId` коллекции `TaxSecretsDocPack`», «для документов из шага 4 — `kndFile.content`».
- Пустых ячеек нет: в «Вариантах значений», если вариантов нет, ставится дефис.

После каждой таблицы — подраздел `==== Пример запроса` / `==== Пример ответа` с `include::`.

## 4. Схема работы

Фиксированный блок:

```asciidoc
[plantuml, "<имяРучки>", png]
----

include::<имяРучки>.puml[]

----

image:<имяРучки>.png[]
```

**Правила для `.puml`:**
- Sequence-диаграмма.
- Участники называются как системы: «Клиент», «corp-<текущий-сервис>-api», «МКС», «SignModule», «ОБИП».
- Стрелки подписаны шагами из раздела «Алгоритм работы».
- Если исходника диаграммы нет — оставить блок с плейсхолдером и сказать об этом автору, **не выдумывать содержимое**. Проверка K.3.1 в этом случае будет непройденной (она требует непустой `.puml`) — это ожидаемо, так и объясни, а не заполняй файл ради зелёной проверки.

## 5. Алгоритм работы: валидация

Раздел открывается **нумерованным списком шагов** — ровно тем, который дальше разворачивается в подразделы:

```asciidoc
. Валидация входных параметров
. Шаг 1. Проверка права подписания
. Шаг 2. Получение информации по организации +
...
. Формирование ответа
```

Дальше `=== Валидация входных параметров` и таблица **Параметр | Условие | Результат**.

### Правила заполнения таблицы валидации

1. **Вертикальный спан**: У одного параметра может быть несколько условий — они объединяются через `.2+|`, `.3+|`:
   ```
   .2+|A-userId |Параметр имеет значение null или пусто |Вернуть исключение...
                |Длина значения не равна 6 символам... |Вернуть исключение...
   ```

2. **Условие пишется как факт, а не как проверка**:
   - ✓ «Параметр имеет значение null или пусто»
   - ✓ «Длина значения не равна 6 символам либо символы не являются алфавитно-числовыми»
   - ✓ «В БД TaxSecretsDocPack у пакета документов operator имеет значение, отличное от KALUGA»
   - ✗ «Проверить, что параметр не пустой»

3. **Результат — целиком**: http-код, текст для пользователя, `type` и `code`.
   > Вернуть исключение с http code 400 (Bad Request), указанием на некорректный параметр — "A-userId не указан", type = VALIDATION_ERROR и code = INCORRECT_CONTRACT

4. **Проверки принадлежности сущности клиенту** описываются вместе с валидацией, а не внутри шагов.

5. **Нейтральный текст ошибки на ненайденную сущность**: «Не найден пакет документов» — не раскрывать, что именно не сошлось (чтобы не подсвечивать внутреннюю логику).

## 6. Алгоритм работы: шаги

### Заголовок шага

`=== Шаг N. <Что делаем>` — **отглагольное существительное**:
- ✓ «Проверка права подписания», «Получение информации по организации», «Создание XML форм», «Запрос файла СОПД», «Отправка документов в SignModule»
- ✗ «Проверяем права», «Получаем организацию», «Делаем XML»

### Содержимое шага

Шаг — это один поход в соседнюю систему или одно осмысленное действие. Порядок частей фиксирован:

1. **Заголовок** со ссылкой на документацию сервиса в git: `=== Шаг 1. Вызов link:ссылка[названиеМетода]`.
2. **Проза** — одна-две строки о том, зачем этот шаг («Для получения данных организации необходимо использовать сервис МКС…»).
3. **`==== Входные параметры`** — таблица. В колонке «Описание» для каждого поля сказано, чем оно заполняется («Заполняется значением CORP-<ПРОЕКТ>», «Использовать значение `fnsInfo.fnsId`…»).
4. **`include::`** — пример запроса из папки `_external`.
5. **`==== Выходные параметры`** — таблица только с теми полями, которые реально используются дальше; это оговаривается фразой «Приведены только параметры, которые используются в методе…».
6. **`include::`** — пример ответа.
7. **Завершающий абзац** — условие перехода на следующий шаг и поведение при ошибке (http-код, `type`, `code`, текст).

Дополнительно:

- **Мапинги**: Если данные шага нужно сопоставить с сущностями из БД или с полями чужого контракта — отдельный подраздел `==== Маппинг документов` / `==== Маппинг полей метода` с таблицей *слева источник — справа приёмник*. Константы пишутся прямо в ячейке значения (`MMB_Common`, `Отчетность`, `текущая дата и время`, `sign`, `sendToTheBank`).

- **Ссылки на шаги**: Только по номеру шага — «данные, полученные на шаге 2». Никогда по имени ручки.

- **Параллельные вызовы систем**: Каждый вызов описывается отдельным шагом. В таблице ошибок отдельно оговаривается, что происходит, если упал один из вызовов (откат транзакции, возврат специфичной ошибки).

- **Внешняя документация**: Если пример запроса лежит в артефактории или другой вики — вместо `include::` даётся голая ссылка отдельной строкой под `==== Пример запроса`.

- **Пустой ответ**: Так и пишется одной строкой: «Пустой ответ».

- **Условие перехода**: Каждый шаг заканчивается предложением вида:
  > Если метод не вернул ошибку, перейти к следующему шагу, иначе остановить работу метода и вернуть ошибку (500 ошибка c type = SERVER_ERROR, code = DOCUMENTS_ERROR, описание: "...").

### Перенос строки

Перенос строки внутри абзаца — плюс в конце строки (` +`). Это стандартный способ, применяется щедро.

- **Правило** — откуда берётся значение, с указанием шага и имени поля источника.

## 8. Работа с include

### Правила именования и расположения

| Что инклюдим | Путь | Пример |
|---|---|---|
| Примеры запросов/ответов **самой ручки** | Рядом с документом | `include::request.adoc[]`, `include::response.adoc[]` |
| Примеры вызовов **соседей** | Общая папка `_external` | `include::../_external/<домен>/<сервис>/<имяМетода>-request.adoc[]` |
| Общее описание формата ошибки | Родительская папка | `include::../CompositeException.adoc[]` |

**Домен** — `mks` для платформенных сервисов, иначе имя сервиса верхнего уровня.

### Важные правила

- В примере ответа соседа **желательно два кейса**: успешный и ошибочный.
- Имена файлов `include::` выводятся из имени вызываемого метода, **не придумываются**.
- Если файла ещё нет — всё равно поставить `include::` по правилу именования и **предупредить автора**, что его нужно создать.

## 9. Синтаксис таблиц AsciiDoc (шпаргалка)

### Базовая структура

Таблица открывается и закрывается `|===`. Первая строка — заголовки со звёздочками:

```asciidoc
|===
|*Параметр* |*Формат* |*Описание*

|A-userId
|string
|Идентификатор УЛ
|===
```

Каждая ячейка с новой строки, пустая ячейка — просто `|`.

### Компактная запись

Допустима для длинных body-структур — всё в одну строку:

```asciidoc
|Body| Agreement.fnsId | string | required | Код налогового органа - использовать значение fnsInfo.fnsId коллекции TaxSecretsDocPack |
```

### Вертикальный спан (объединение ячеек)

Для нескольких условий одного параметра в таблице валидации:

```asciidoc
.2+|A-userId |Параметр пустой |Вернуть ошибку...
            |Длина не равна 6 |Вернуть ошибку...
```

### Перенос строки внутри ячейки

Делается **пустой строкой**. Так оформляются перечисления вариантов значений (`OK - …` / `FAILED - …` / `ERROR - …`), где к каждому варианту сразу приписано, что делать методу.

## Проблемные ситуации

### Нет исходника PlantUML-диаграммы

Оставь блок `[plantuml, ...]` с пустым телом (как в разделе 4) и явно напиши в ответе пользователю: «Диаграмма не сгенерирована, требуется исходный `.puml` файл». **Не выдумывай участников и стрелки.**

### Нет файла для `include::` (примера соседа)

Поставь `include::` по правилу именования (раздел 8) и добавь в конце документа или в комментарии:
```asciidoc
// TODO: создать файл ../_external/mks/customers-api/getByIdsV2-request.adoc
```

### Неизвестен состав полей метода (body-структура)

Если ни в репозитории, ни во вводных нет контракта — **не выдумывай таблицу**. Запроси состав запроса/ответа у пользователя. Если пользователь ответит «Заполню позже» — оставь таблицу с комментарием `// TODO: заполнить после получения контракта` и явно укажи это в конце ответа.

### Нужно добавить новый раздел, которого нет в структуре

**Не добавляй.** Порядок и состав разделов фиксированы внутренним стандартом. Если есть специфичная информация, которая не ложится в существующие разделы — добавь её в «Назначение» или как комментарий `// TODO:` в конце документа для обсуждения с автором.

## Чек-лист по структуре документа

Перед выдачей проверь:

- [ ] Шапка документа в формате `= Rest-метод <имя>` или `= Thrift-метод <имя>`, атрибуты `:toc:` на месте и идут сразу за заголовком, без пустой строки между ними
- [ ] Раздел «Назначение» содержит 2-4 предложения; если новая версия — есть список отличий
- [ ] Таблица входных параметров соответствует транспорту метода (REST — 6 колонок, Thrift — 4 колонки)
