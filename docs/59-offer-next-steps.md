# Ещё три вида `offer`: syncBase, cleanup и свободные предложения моделью

План, предложен 2026-11-22. Кнопки следующего шага под ответом (`offer`, docs/43-single-loop.md Ш6)
получают три новых вида: **syncBase** — worktree отстал от записанной базы, кнопка просит агента
обновить ветку; **cleanup** — работа worktree опубликована и терять нечего, кнопка ведёт к
существующему диалогу удаления; **message** — модель сама пишет до двух предложений-сообщений
там, где ни один фиксированный вид не подходит. Вид **implement становится `plan`**: карточка
в чате открывает вкладку Plan, а старт реализации живёт только там — кнопка «Implement in Agent
mode» в PlanPanel уже существует. Нажатие по-прежнему ничего не выполняет само:
либо обычное сообщение пользователя, либо существующий UI-флоу.

Кода в документе нет — только решения.

## Решения

### 1. syncBase: проверка — «отстал», нажатие — сообщение агенту

`pr_ready` сегодня отказывает «rebase or merge the base first» — тупик: модель предлагает
PR, получает отказ, и пользователю остаётся писать просьбу руками. Новый вид закрывает этот
шаг: предпосылка — worktree, записанная база, репозиторий не в середине операции, чистое
дерево, `behind > 0`. Считается новой публичной функцией `git_branches::base_behind(root,
base) -> Result<usize, GitBranchError>` из тех же приватных кирпичей, что `pr_ready`;
`behind == 0` — отказ «already up to date», который модель прочитает.

Нажатие шлёт обычное сообщение (константа в `lib/offer.ts`): обновить ветку от записанной
базы подтверждёнными командами, разобрать конфликты, прогнать проверки. Автомерджа по
кнопке нет — это нарушило бы правило Ш6 «нажатие — обычное сообщение, подтверждать нечего».

Чтобы агент знал базу, worktree-абзац промпта называет её (`TurnContext` получает
`worktree_base`, уже доступный в `Place::Folder`). Без этого сообщение «обнови от базы»
заставляло бы агента угадывать базу по имени ветки.

Отвергнуто: переиспользовать `pr_ready` и разбирать текст его ошибки — строковый матч по
сообщению хрупок; отдельная функция с тем же контрактом ошибок честнее.

### 2. cleanup: предпосылка — терять нечего; нажатие — существующий диалог удаления

Предпосылка — `worktree_state(root)`: дерево чистое и `own_commits == 0` (каждый коммит
ветки достижим с другой ветки или remote-ветки). Это ровно условие, при котором
`remove_worktree` удаляет ветку без потери работы, — кнопка и удаление смотрят на один факт.
Грязное дерево → «commit the worktree changes first»; `own_commits > 0` → «N commit(s) on no
other branch — publish or merge them first». Когда звать — говорит описание вида (после
смерженного PR или брошенной попытки); бэкенд охраняет только безопасность, как у остальных
видов.

Нажатие не удаляет само: `gitWorktreeCheck(path)` даёт `main` → `workspace.open(main)` →
`worktreeRemoval.ask(path)` — существующий диалог, который перечитывает состояние и
показывает, что уйдёт (worktree, чаты, ветка). Удаление открытой папки бэкенд запрещает
(commands/git.rs:180), поэтому переход в main обязателен; заодно чат не теряет папку под
ногами. Отмена диалога оставляет пользователя в main — приемлемо, диалог и есть подтверждение.

Ограничение (сознательное): после squash-мержа с удалённой remote-веткой коммиты ветки снова
«свои» (`own_commits > 0`) — кнопки не будет. Содержание работы в базе, но граф этого не
видит; консервативный отказ лучше удаления ветки, чьи коммиты формально нигде больше.

Отвергнуто: новая команда «удалить открытый worktree и перейти в main» одним вызовом —
обходит существующую защиту и дублирует диалог; фронт собирает флоу из трёх уже готовых
вызовов.

### 3. message: свободный текст, до двух на ход, предел — в отображении

`OfferKind::Message`, у `OfferArgs` появляется `text` (serde default — старые вызовы целы).
Для `message` текст обязателен: непустой после trim, ≤ 300 символов (предложение — фраза или
две, не письмо); у фиксированных видов `text` запрещён — иначе модель решит, что им можно
подменить сообщение кнопки. `reason` обязателен как у всех.

Карточка: label — сам текст предложения (то, что уйдёт сообщением), под ним reason — зачем.
Макет существующей карточки (label + reason) не меняется. Нажатие шлёт `text` как обычное
сообщение пользователя; `pickOffer` получает `Offer` вместо `OfferKind` (тип `onOffer` в
`ChatPanel` и проводка в `App` меняются соответственно).

Предел «до двух» держит фронт: `offersOf` для message-предложений ключует по тексту (одинаковый
текст — одна карточка) и оставляет **последние два**; фиксированные виды живут по-прежнему
по одному на вид. Описание вида говорит модели: не больше двух, позднейшее вытесняет раннее.
Бэкенд-счётчик отвергнут: ради правила отображения пришлось бы протаскивать новое
состояние хода через `dispatch` (сигнатура, тесты), а правило «одна карточка на вид,
последняя причина» уже живёт в `offersOf` — предел там же.

Промпт Agent (абзац о следующем шаге) дополняется: `message` — когда пользователь стоит
перед реальным выбором, который ни один фиксированный вид не покрывает; текст — точное
сообщение от лица пользователя; не дублировать вопрос, уже заданный прозой. Исходное
опасение Ш6 («свободный текст — кнопка под каждым ответом») снимается формулировкой
«реальный выбор» + пределом в две карточки, а не запретом.

Маршрутизация простая и без пересечений: план готов → карточка `plan` (открыть и прочитать);
конкретный следующий шаг («Начни OF-1», «сделай только первый этап и остановись») — `message`
с точным текстом. Дублировать нечего: `plan` не шлёт сообщений, `message` не открывает план.

### 4. implement становится `plan`: карточка открывает план, старт — во вкладке

Сегодня кнопка implement в чате шлёт IMPLEMENT_PLAN одним кликом — план можно запустить не
читая, а модель выбирает между implement и message для «начать этап». Теперь:

- Вид `OfferKind::Implement` переименовывается в `Plan` (wire `plan`), предпосылка та же —
  непустой план. Описание вида: «plan: after writePlan… pressing it opens the Plan tab, where
  the user reads it and starts implementation; end your turn there». Промпт Agent и тест
  `each_mode_names_only_tools_it_offers` (ждёт «`offer`, kind implement») обновляются.
- Нажатие в чате: `pickOffer(plan)` → `openTab("plan")` (новая зависимость `openPlan` у
  `useChatRouting`, из App). Ghost-кнопка «Review the plan» и `onOpenPlan` в OfferCards
  удаляются — карточка сама открывает план. `implement()` в хуке остаётся: его зовёт кнопка
  PlanPanel, со сменой режима и `keepChecklist: true` — она доступна в любом режиме, включая
  план, написанный пользователем в Analyst; чатовым предложениям смена режима не нужна
  (Offer есть только у Agent).
- Старт этапа предложением `message` ведёт себя как набранное сообщение: открытые пункты
  чеклиста сбрасываются (`dropOpen`), агент перечитывает план (он восстановлен в истории,
  `restore_plan`) и составляет список заново. Специального пути для message нет.
- Старые транскрипты: `offerOf` принимает и `implement` в сохранённых результатах и
  нормализует в `plan` — кнопка в старых чатах открывает план, а не шлёт сообщение.

Цена (сознательная): «план готов → сразу делать» — два клика вместо одного (открыть план,
нажать Implement). Взамен план читают перед стартом, а у модели нет выбора между видами
для старта. Отвергнуто: оставить обе кнопки (implement в чате + во вкладке) — возвращает
и обход чтения, и путаницу видов.

### 5. Порядок: сначала дешёвые git-виды, потом карточка плана, потом message

syncBase и cleanup — по образцу существующих видов, каждый закончен сам по себе. Карточка
плана — маленькая и меняет маршрутизацию, на которую опирается message. message трогает
форму аргументов, `offersOf`, тип `onPick` и промпт — последним, чтобы регрессия
фиксированных видов была видна отдельно.

## Нарезка

Каждый этап — отдельный коммит с тестами и мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)).

**OF-1. syncBase.** `base_behind` + ветка `offer` + схема; промпт называет базу;
фронт: вид, константа `SYNC_BASE`, `LOOK`, отправка. Тесты: не-worktree / нет базы /
грязное дерево / behind == 0 → отказы с текстом; behind > 0 → Offered; база ушла вперёд
после коммита в worktree → всё ещё Offered (ahead не важен); промпт-тест на имя базы;
схема перечисляет вид. Мутации: снятая каждая проверка, `behind > 0` → `>= 0`.

**OF-2. cleanup.** Ветка `offer` на `worktree_state`; фронт: `cleanupWorktree` в
`useChatRouting` + сборка в `App`, `LOOK`. Тесты: не-worktree / грязное дерево /
own_commits > 0 → отказы; чистый worktree без своих коммитов → Offered; pushed-ветка
(коммиты на remote) → Offered; фронт — порядок open(main) → ask(path), отказ open не
зовёт диалог. Мутации: снятая каждая проверка, порядок шагов, вызов ask без open.

**OF-3. Карточка плана (`implement` → `plan`).** Переименование вида, описание и промпт,
`pickOffer(plan)` → `openPlan`, удаление ghost-кнопки и `onOpenPlan` из OfferCards,
нормализация `implement` в `offerOf`. Тесты: предпосылка плана не изменилась; нажатие
открывает вкладку и ничего не шлёт; старый блок `implement` рисуется карточкой плана;
кнопка PlanPanel по-прежнему шлёт IMPLEMENT_PLAN со сменой режима и чеклистом.
Мутации: предпосылка, нормализация, подмена действия отправкой.

**OF-4. message.** `OfferArgs.text` + валидация; `offersOf` (ключ по тексту, последние
два, дедуп), карточка и `pickOffer(offer)`; промпт-абзац с маршрутизацией (план → `plan`,
конкретный шаг → `message`). Тесты: пустой/длинный text → отказ; text у фиксированного
вида → отказ; два предложения → обе карточки, третье вытесняет первое, одинаковый текст —
одна; нажатие шлёт именно text; фиксированные виды не регрессировали (существующие тесты
offer). Мутации: бэкенд — границы валидации; фронт — предел, дедуп, ключ, подмена
text/reason.

**OF-5. Документы.** `docs/README.md`, `CHANGELOG.md` (одна строка на фичу), итоговый
статус плана.

Проверки каждого этапа: `bun run tsc --noEmit && bun test`, `cargo check && cargo test`;
мутации `scripts/mutate.py`. Правки промпта и описания инструмента положен прогон
`agent_bench` той же моделью; без ключа `AGENT_BENCH_*` этап сдаётся с пометкой «бенч не
прогнан».

## Вне плана

- Кнопка `merge` (смержить PR) — приложение нигде не записывает факт PR; вернёмся, если
  появится состояние PR или дешёвый способ проверить через MCP.
- Кнопка `push` для обычного checkout — отдельный вид со своей предпосылкой (upstream,
  ahead); не нужен для worktree-флоу, который закрывает этот план.
- Подсказки композера из `next_prompt` — ждут своей модели (Ш6), kind `message` их не
  заменяет и не блокирует.
- Бэкенд-предел числа message-предложений — если модель начнёт слать их пачками и предел
  в отображении окажется мало, перенесём счётчик в ход.

## Открытые вопросы

1. cleanup удаляет worktree **вместе с его чатами** (существующая семантика удаления;
   чат, из которого нажата кнопка, исчезнет, пользователь останется в main). Подтвердить,
   что это то поведение, которое хочется от кнопки.
2. message: предел 2 на ход, текст ≤ 300 символов, на кнопке — сам текст предложения,
   под ним причина. Устраивают ли числа и вид карточки?
3. Есть ли ключ `AGENT_BENCH_*` для прогона бенча после правок промпта (OF-1, OF-3, OF-4)?
   Без него этапы сдаются с пометкой «бенч не прогнан».
4. Карточка плана делает старт реализации двумя кликами (открыть план → Implement во
   вкладке) вместо одного в чате. Подтвердить, что чтение перед стартом важнее лишнего
   клика; если нет — оставить кнопку implement в чате рядом с карточкой.
