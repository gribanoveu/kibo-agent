# 3. Целевая архитектура

## 3.1 Ключевое решение: ядро не знает про UI

```
                              ┌──────────────────────┐
                              │  Desktop UI          │
                              │  (Tauri + React)     │
                              └──────────┬───────────┘
                                         │  события turn'а
                              ┌──────────┴───────────┐
                              │  commands/           │  ← sink → Emitter
                              └──────────┬───────────┘
                                         ▼
                    ┌──────────────────────────────────────────┐
                    │  domain/ · services/ · infra/            │
                    │  (про окно не знают)                     │
                    │                                          │
                    │  turn loop · tools · scope · context     │
                    │  sessions · providers · index            │
                    └──────────────────────────────────────────┘
```

Это не пожелание, а то, как код в Alfa Atlas уже написан, и главная причина, почему
перенос вообще возможен. Правило из `AGENTS.md`:

> Сервис, которому нужно что-то сообщить наружу, принимает **sink** —
> `Arc<dyn Fn(Event) + Send + Sync>`, тип события живёт в `domain/`, и только слой
> команд превращает это в Tauri-события.

Агентный цикл (`services::llm_chat`) не импортирует `tauri::` ничего, кроме
`async_runtime::spawn_blocking` в качестве пула потоков. Десктоп подставляет sink,
который эмитит IPC-события; тест подставляет sink, который пишет в вектор. Ядро в обоих
случаях одно и то же — и именно поэтому цикл проверяется без окна.

## 3.2 Раскладка модулей

Отдельного крейта под ядро нет: все переносимые сервисы и так не зависят от Tauri
(единственное упоминание `tauri::` в них — `async_runtime::spawn_blocking`, то есть пул
потоков), поэтому граница держится раскладкой из [AGENTS.md](../AGENTS.md), а не
границей компиляции.

```
src/                      # React
src-tauri/src/
├── commands/             # граница: тонкие #[tauri::command] + адаптеры sink→событие
├── services/             # оркестрация: turn loop, execute_tool, индекс, память
├── domain/               # типы, правила, thiserror-энумы. Без I/O и фреймворков
└── infra/                # git2, ФС, HTTP-провайдеры, SQLite, keychain
```

Направление зависимостей — внутрь: `commands → services → domain`, `infra` реализует
трейты, объявленные в `domain`/`services`.

**Когда заводить крейт.** Если у ядра появится второй потребитель, раскладка выше
выделяется в `crates/agent-core` почти механически — ровно потому, что `tauri::` внутрь
не пророс. До тех пор крейт стоил бы переписывания `spawn_blocking` и не давал бы ничего.

## 3.3 Протокол turn'а — центральный контракт

Всё, что фронт знает об идущем turn'е, приходит одним потоком событий. В Atlas это уже
так: `ChatEventPayload` с вариантами `ChatStreamDelta`, `ChatStreamReasoning`,
`ChatRoundCompleted`, `ChatRetrying`, `ContextUsage`, `ChatDone` — плюс отдельный
`ChatStreamOutcome`, который отличает «turn завершился» от «turn встал на подтверждении».

Требования к протоколу в новом проекте:

1. **Монотонный `seq` на каждое событие.** В Atlas порядок и дедуп уже держатся на нём
   (`createChatTurnProtocol` / `acceptChatTurnEvent` в
   [src/lib/chatTurnReducer.ts](../src/lib/chatTurnReducer.ts)). Без этого UI, который
   подключился к turn'у в середине, не соберёт корректное состояние.
2. **Сериализуемость в JSON-строки.** Не ради второго фронта, а потому что события
   turn'а пишутся в сессию, читаются из неё и сравниваются в тестах. Формат один — тот
   же, что уходит в UI; второго, отдельно поддерживаемого, быть не должно.
3. **Пауза как часть протокола, а не как исключение.** Turn заканчивается либо ответом,
   либо `PendingApproval` со списком `PendingToolCall`. Вызывающий присылает
   `ToolCallDecision[]` и `ResumePoint` — и цикл продолжается ровно с того места.

Именно пункт 3 делает возможными сценарии, которых иначе не будет: сохранение
незавершённого turn'а на диск, возврат к нему после перезапуска приложения и ожидание
человека без удерживаемого потока.

## 3.4 Состав `ResumePoint`

Из Atlas ([services/llm_chat.rs](../src-tauri/src/services/llm_chat.rs)) — список
полей, который стоит воспроизвести, потому что каждое из них уже есть ответ на
конкретный баг:

| Поле | Зачем |
|------|-------|
| `history` | собственно диалог, включая уже выполненные в этом раунде вызовы |
| `round` | чтобы потолок раундов не обнулялся при каждом возобновлении |
| `budget_used` | то же для взвешенного бюджета — иначе подтверждениями можно обойти лимит |
| `event_seq` | чтобы события после возобновления продолжали нумерацию, а не начинали с нуля |
| `decisions` | уже принятые решения по инструментам в этом turn'е («всегда разрешать») |
| `todos` | todo-список, который инструмент не хранит у себя |

## 3.5 Граница инструментов

Одна функция, один диспетчер, одна проверка прав:

```rust
pub fn execute_tool(
    scope: &ToolScope,
    call: &ToolCall,
    reads: &mut ReadFiles,
    todos: &mut Vec<Task>,
    deps: &ToolDeps,
) -> Result<ToolResult, ToolError>
```

`ToolCall`/`ToolResult` — enum'ы с adjacently-tagged serde
(`#[serde(tag = "tool", content = "args")]`), а не набор функций. Что это даёт:

- одна точка проверки allowlist — невозможно добавить инструмент и забыть про права;
- одна точка сериализации на границе с моделью;
- одна точка логирования и редактирования чувствительных данных;
- стабильная проводная форма, которую можно зафиксировать тестом.

Добавление инструмента = модуль в `tools/` (схема и реализация рядом) + вариант в двух
enum'ах + ветка в `match`. Задумывалось «больше нигде»; на деле мест около десятка
(разбор по имени, `ToolName` и его свойства, где инструмент предлагается, журнал, окно) —
их список и что каждое держит, компилятор или тест, в AGENTS.md.

`ToolDeps` — то, что инструментам нужно из окружения (индексы, git, исполнитель
команд). В Atlas это `EmbeddingDeps`; в новом проекте туда же уедет процесс-раннер.

## 3.6 Где живёт состояние

| Состояние | Где | Почему не иначе |
|-----------|-----|-----------------|
| История сессии | SQLite, вне репозитория | переживает перезапуск, не мусорит в рабочем дереве |
| Индекс репозитория | SQLite + векторный файл, каталог по идентичности репо | тот же репо в двух клонах переиспользует индекс |
| Права на проект | `~/.kibo/settings.json`, Ask/Auto на чат или на папку (`ApprovalMemory`) | вне репозитория: у каждого свои |
| Ключи провайдеров | системный keychain, fallback — файл под AES-256-GCM | не в репозитории и не в plaintext |
| Todo текущего turn'а | в вызывающем, круглым ходом через `execute_tool` | исполнитель инструментов остаётся без состояния |
| Настройки | `~/.kibo/settings.json` | вне репозитория, переживают переустановку |

Строка про права отличается от задуманного: файла прав в репозитории (`.agent/project.json`),
который коммитится один раз и работает у всех, нет. Выбор Ask/Auto хранится у пользователя.

## 3.7 Асинхронность

В Atlas HTTP к провайдеру — блокирующий (`ureq`), запускается через `spawn_blocking`.
Для нового проекта это разумно сохранить: агентный цикл по своей природе
последовательный, а блокирующий клиент сильно проще в отладке и не тащит async-окраску
во все сервисы. Асинхронность нужна ровно в трёх местах: стриминг ответа провайдера,
стриминг вывода команды, файловый watcher. Остальное — синхронный код.

Исключение — клиенты, которые есть только асинхронными: Kubernetes (`kube`) и MCP-SDK
(`rmcp`). Их вызовы завёрнуты в `tauri::async_runtime::block_on` в одном модуле каждый
(`infra/kube_client.rs`, `infra/mcp_rmcp.rs`), и наружу они синхронны.
