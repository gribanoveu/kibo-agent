# 13. Исследование: cross-encoder реранкер для семантического поиска

Статус: **предложение, не начато.** Документ фиксирует вопрос, что о нём уже известно и
как на него ответить измерением, а не рассуждением. Ничего в приложение не встраивается,
пока эксперимент ниже не покажет прирост.

## Вопрос

Стоит ли переупорядочивать кандидатов `semanticSearch` cross-encoder'ом — моделью,
которая читает запрос и фрагмент вместе и выставляет им оценку релевантности?

Дешёвые улучшения без нового рантайма — в [14-search-quality-plan.md](14-search-quality-plan.md);
их стоит сделать раньше, чтобы реранкер сравнивался с уже улучшенным поиском.

Сейчас ранжирование — слияние рангов по словам (BM25) и по смыслу (статические
эмбеддинги Model2Vec) с поправками на имя в пути, прозу и историю git
(`services/code_search.rs`, [12-tool-feedback.md](12-tool-feedback.md)). Реранкер
добавил бы третий, намного более дорогой, но и более точный шаг поверх топ-N.

## Где болит сейчас

Бенч `search_bench` (93 вопроса, три репозитория) на 2026-09-21, MRR:

| | MRR |
|---|---|
| все вопросы | 0.564 |
| на английском | 0.619 |
| **на русском** | **0.457** |
| ответ — документация | 0.589 |
| ответ — место вызова (`caller`) | 0.444 |

Слабее всего **русский вопрос к коду с английскими идентификаторами**. Реранкер
окупится, только если поднимет именно такие вопросы, не просев на остальных.

## Цена встраивания (от любой модели)

- **Рантайм.** Нейросетевого рантайма в приложении нет: эмбеддинги статические, пулинг
  написан вручную (`infra/local_embeddings.rs`). Для трансформера нужен ONNX Runtime
  (`ort`, нативная библиотека под каждую платформу — macOS, Windows, Linux), candle
  (чистый Rust, BERT/XLM-R есть, ModernBERT — проверить) или llama.cpp для GGUF.
- **Размер.** +120–300 МБ к установщику (сейчас модель 80 МБ) и +200–500 МБ памяти
  в работе; выгружать по простою, как эмбеддинги.
- **Задержка.** Переупорядочивать ~20 кандидатов на запрос (`top_k × 2`). Средний
  фрагмент ~470 байт — 150–300 токенов в паре с запросом. На CPU от ~0.1 с
  (MiniLM) до ~0.5–1 с (модель ~300M) на поиск.
- **Отказоустойчивость.** Не загрузилась модель — поиск работает без неё и говорит об
  этом в подсказке, как сейчас при отказе эмбеддингов.

## Кандидаты

| | Jina reranker v2 multilingual | ru-reranker-edge-150m | mmarco-mMiniLMv2-L12-H384 |
|---|---|---|---|
| Размер | ~278M (XLM-R) | 150M (RuModernBERT) | ~118M (MiniLM, 384 скрытых) |
| Лицензия | **CC-BY-NC-4.0 — некоммерческая** | Apache 2.0 | Apache 2.0 |
| Языки | многоязычная, в т.ч. ru и en | дообучена **только на русском**; база видела ru, en и код | 14 языков mMARCO, ru и en среди них |
| Код | **в обучении и в замерах** (CodeSearchNet MRR@10 71.4) | нет | нет (переведённые веб-вопросы) |
| Контекст | 1024 | 512 (база до 8192) | 512 |
| Формат | ONNX int8 (~280 МБ); Q4 — только GGUF для llama.cpp | ONNX; int8 нужен по каналам — динамический роняет качество | много ONNX-вариантов и квантизаций |
| CPU (оценка) | ~40 мс на пару в fp32 | ~2× MiniLM | самая быстрая |
| Зрелость | крупный вендор | новая модель одного автора | 2021, миллионы скачиваний |

### Jina reranker v2 multilingual (Q4)

Технически лучшее совпадение с задачей: единственная из трёх, обученная и проверенная
на коде, и многоязычная — как раз русский вопрос к коду. **Стоп-фактор — лицензия
CC-BY-NC-4.0**: коммерческое использование запрещено, для него Jina предлагает свой API
и маркетплейсы. Для рабочего инструмента это требует договора. Q4 — формат GGUF, то есть
ещё и llama.cpp; у cross-encoder'а такого размера Q4 заметно роняет качество, разумный
минимум — int8.

**В исследовании:** прогнать как верхнюю планку. Если даже она почти ничего не даёт,
остальных можно не встраивать.

### ru-reranker-edge-150m (INT8)

Лицензия подходит, сильная для русского: на RusBEIR на уровне учителя
bge-reranker-v2-m3 (nDCG@10 0.609 против 0.607). Но дообучена на русском тексте — без
кода и без английского. В нашей выдаче в основном код с английскими именами, и половина
вопросов на английском. Ожидание — польза на русских вопросах по документации, риск на
всём остальном. Архитектура ModernBERT: поддержку в выбранном рантайме проверить. Int8 —
только по каналам.

### mmarco-mMiniLMv2-L12-H384 (INT8)

Лицензия подходит, самая лёгкая и зрелая. Но старая, обучена на машинном переводе
веб-вопросов MS MARCO и кода не видела. На фрагментах кода ожидание — ноль или минус:
текстовый реранкер судит код по случайным совпадениям слов в комментариях.

### Кого добавить в сравнение

В списке нет многоязычной модели под Apache 2.0, видевшей код. Первый кандидат —
`Alibaba-NLP/gte-multilingual-reranker-base` (~306M, многоязычная, длинный контекст).
**Перед включением проверить лицензию и данные обучения** — здесь они не проверены.
Можно также взять `BAAI/bge-reranker-v2-m3` (Apache 2.0, ~568M) как тяжёлую планку
качества, если Jina исключена лицензией.

## Эксперимент

Решение принимается по бенчу, без изменений в приложении.

1. **Выгрузка кандидатов.** Флаг в `search_bench` (например, `SEARCH_BENCH_DUMP=путь`)
   пишет по каждому вопросу JSON: запрос, язык, тип ответа, ожидаемые файлы и
   объявления, топ-20 кандидатов в порядке нынешнего ранжирования — путь, строки, имя,
   текст фрагмента (полный, не обрезанный). `includeDocs` — как в бенче: включён для
   вопросов с `"answer": "docs"`.
2. **Переранжирование в Python.** Скрипт `scripts/rerank-bench.py`:
   `sentence-transformers` `CrossEncoder` на каждую модель, оценка пар (запрос,
   фрагмент), пересортировка, те же метрики, что у бенча: file@1, @5, @10, MRR, decl@5 —
   в целом, по языку и по типу ответа. Плюс время на вопрос на CPU, чтобы видеть цену.
3. **Варианты смешивания.** Не только «заменить порядок реранкером», но и слить его ранг
   с нынешним через RRF с весом — реранкер может быть хорош в верху и плох в хвосте.
4. **Квантизация.** Для прошедших — повторить с int8 (ONNX), в котором модель поедет в
   приложение, и проверить, что прирост не съеден.

**Критерий:** общий MRR +0.05 или больше, на русских вопросах — рост, ни одна группа
(язык, тип ответа) не проседает больше чем на 0.02, задержка ≤ 0.5 с на 20 кандидатов на
CPU в int8. Не прошла ни одна модель — реранкер не встраиваем, документ фиксирует цифры.

**Оценка трудозатрат:** выгрузка и скрипт — около часа; прогон — минуты на модель
(93 вопроса × 20 пар). Встраивание прошедшей модели через `ort` или candle — отдельная
работа: рантайм, упаковка под три платформы, выгрузка по простою, мутации и бенч.
