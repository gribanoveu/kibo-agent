# Режимы Agent и Analyst: аналитик спрашивает по коду, план пишет сам Agent

План, предложен 2026-11-06. По отзывам режимами Ask и Plan не пользуются, зато системные
аналитики часто открывают репозитории и спрашивают по коду. Выбор сводится к двум режимам:
Agent и Analyst. Plan убирается, Ask заменяется на Analyst. План работы остаётся, но его
пишет Agent по просьбе и предлагает кнопкой Implement. Выбранный режим запоминается.

Analyst сделан режимом `ConversationMode`, а не ролью `ChatRole`: роль живёт в Chat mode без
папки, а аналитику нужны открытый репозиторий, индекс, `semanticSearch`, git-инструменты и
база знаний, то есть `Place::Folder`.

Работа опирается на PR #82 (выбор режима в панели `ComposerSettings.tsx`). На 2026-11-06 он
открыт: CI зелёный, конфликтов нет, ревью нет. **Этапы не начинаются, пока он не влит в
main.** План писался по коду его ветки.

Кода в документе нет — только решения.

## Что уже есть

- `domain/conversation_mode.rs` — пять режимов, `tools()` и `offers()`. Гейт двойной: инструмент
  не попадает в запрос (`llm_chat::offered_here`) и отказывается в `parse::preflight_tool_call`.
- `domain/prompt.rs`, `mode_instructions` — абзац на режим. Тест
  `each_mode_names_only_tools_it_offers` смотрит на всё в обратных кавычках;
  `the_read_only_modes_say_they_cannot_act` требует слов «do not offer to».
- `services/ai_tools/tools/offer.rs` — кнопка под ответом с отказом, когда предлагать нечего.
  Виды: review, commit, worktree, pullRequest. На фронте: `lib/offer.ts`, `OfferCards.tsx`,
  `pickOffer` в `App.tsx`. Кнопки рисуются только при `conversation.value === "agent"`.
- `implement` в `App.tsx` — сначала переключает режим на Agent, потом шлёт `IMPLEMENT_PLAN` с
  `keepChecklist = true`. Обычная отправка роняет незакрытые пункты чеклиста
  (`useAgentTurn`, «a new message drops what the last answer left open»).
- План: `state.written_plan` в цикле, `turn.plan` из окна. Окно обновляет `session.plan` по
  ходу (`useAgentTurn.ts:265`), поэтому при возобновлении план приходит через `chat_resume`.
- `toolSearch`: инструмент не из `loads_up_front` ждёт поиска там, где `toolSearch` предложен.
  Его описание перечисляет ждущие с первой фразой каждого (`tool_search::definition_for`).
- MCP закрыт по режиму ещё в двух местах сверх `offers`: `turn_setup::mcp_for_turn` и
  `commands/chat.rs::next_request_frame` сравнивают режим с Agent напрямую.
- `AgentState.mode` — одно значение на окно, общее для всех чатов (`commands/chat.rs`).
- Запоминание: `settings_store::update`, образец `ApprovalMemory` и `useApprovalMemory.ts`.
  `AppSettings` читается с `#[serde(default)]`, поэтому новое поле старым файлам не мешает.
- `useBackendSetting` — чип двигается после согласия бэкенда, начального чтения в нём нет.

Чего нет: узкого типа «режим, который выбирает пользователь», чтения режима при старте,
признака «план есть» в `ToolDeps`.

## Решения

### 1. Выбирается два режима, и тип не пускает остальные

`Plan` удаляется. `Ask` становится `Analyst`, проводное имя `analyst`. `Review` и `Explore`
остаются внутренними.

Появляется `PickedMode { Agent, Analyst }` рядом с `ConversationMode`, с преобразованием в него.
Этот тип принимает `chat_set_mode`, его хранят `AgentState.mode` и настройки. Так внутренний
режим нельзя ни прислать, ни сохранить: это держит компилятор, а не проверка в команде.
Отвергнуто: хранить `ConversationMode` и отсеивать при записи — правило, которое надо помнить в
каждой точке входа. `ConversationMode` перестаёт быть проводным типом, его serde снимается.

### 2. Инструменты Analyst: чтение, helper, память, доска, MCP

`base_tools()` плюс `Explore`, `Remember`, `Board`, `Mcp`, `ToolSearch`. Без `KnowledgeWrite`,
`todo`, `writePlan`, `offer` и `runCommand`.

`Mcp` помечен `is_mutating`, потому что про чужой инструмент ничего не известно. Он остаётся
единственным мутирующим в Analyst и идёт через карточку одобрения. Причина: у аналитика Jira,
Confluence и трекеры живут в MCP. Отсюда:

- тест `nothing_that_changes_the_tree_is_offered_outside_agent_mode` называет MCP исключением
  для Analyst и почему; для `Explore` исключения нет;
- строка таблицы в `AGENTS.md` и комментарий в `is_mutating` («stays out of the modes that
  promise nothing changes») меняются вместе с тестом;
- `mcp_for_turn` и `next_request_frame` спрашивают `offers(mode, ToolName::Mcp)`, а не равенство
  с Agent. Иначе Analyst предлагал бы MCP, а серверы не запускались бы;
- переключатель одобрения в Analyst остаётся. С Auto вызовы MCP идут без карточки, как в Agent.

Следствие решения про `KnowledgeWrite`: `/analyze` пишет в базу знаний и ведёт чеклист, поэтому
в Analyst недоступен, меню говорит переключиться на Agent. Абзац `knowledge_block` сам перестаёт
предлагать запись: он спрашивает `offers`.

### 3. С `toolSearch` Analyst ничего не теряет с первого шага

Сейчас в Ask `toolSearch` нет, и всё объявлено сразу. В Analyst ждать поиска начнут `gitBlame`,
`readTerminal`, `board` и `mongo`. Всё нужное для первого шага загружено сразу: `readFile`,
`grep`, `listFiles`, `semanticSearch`, `gitLog`, `gitDiff`, `gitStatus`, база знаний, `explore`,
`remember`, `skill`, веб. Промпт ни одного из четырёх ждущих не называет, абзац Analyst тоже не
назовёт. Описание `toolSearch` перечисляет их, так что цена — один раунд.

`loads_up_front` не меняется: он один на все режимы, и добавление `gitBlame` или `mongo`
увеличило бы каждый запрос Agent. Если на практике аналитик не найдёт `gitBlame`, это одна строка.

### 4. Абзац Analyst пишется под аналитика

Собеседник — системный аналитик, не разработчик. Ответ — о поведении системы, бизнес-правилах,
интеграциях, контрактах и потоках данных, а не об устройстве кода. Файл и строка — как
доказательство. Подтверждённое кодом отделено от предположений. Правки и запуск команд не
предлагать, со словами «do not offer to». Инструменты в абзаце не называются, кроме предложенных.

### 5. Implement — новый вид `offer`, и он требует плана

`OfferKind::Implement` в существующем инструменте. Отвергнуто: оставить блок `plan-handoff`,
завязанный на финал хода, — без режима Plan нечем отличить ход с планом от любого другого, а
модель знает это точно.

- **Отказ без плана.** `ToolDeps` получает признак «план есть»: `state.written_plan` или непустой
  `turn.plan`. Пустая строка от редактирования вкладки планом не считается.
- **План и кнопка в одном раунде.** `offer` не `runs_alongside`, значит идёт после `writePlan` в
  порядке вызовов, и план уже записан. Держится тестом.
- **`pickOffer` зовёт `implement`, а не `send(IMPLEMENT_PLAN)`.** Иначе чеклист плана потеряется,
  см. «Что уже есть». Это отличается от commit и pullRequest.
- **Путь к чтению плана.** `OfferCards` при виде implement рисует рядом кнопку «Review the plan».
  `plan-handoff`, `planReady`, проп `onImplement` у `ChatPanel` и их CSS уходят.
- **`PlanPanel`.** Кнопка остаётся и видна всегда, когда план есть и ход не идёт. В Analyst она
  переключает на Agent, и это запомнится: пользователь нажал явно. Текст пустой вкладки больше не
  ссылается на Plan mode.

Места: `OfferKind`, схема и описание в `offer.rs`, `lib/offer.ts` (объединение и белый список в
`offerOf`), `LOOK` в `OfferCards.tsx`, `pickOffer`. Новых инструментов нет, таблица из `AGENTS.md`
не задевается.

### 6. Абзац Agent: план по просьбе — без изменений и с остановкой

Когда просят план, а не работу: прочитать нужное, написать через `writePlan`, завести `todo`,
ничего не менять, предложить `offer` implement и остановиться. Длинная задача, которую просили
выполнить, идёт как раньше: план пишется по ходу и кнопки нет.

**Цена, и она записана.** Раньше «план ничего не меняет» держал гейт, теперь только промпт. С
карточками запись всё равно спросит, с Auto нет. Поэтому поведение меряется задачей в bench, см.
AN-1.

### 7. Режим запоминается один на приложение

Поле в `AppSettings`, запись через `settings_store::update`, выбор в панели. Причины: аналитик —
человек, а не репозиторий; при запоминании по репозиторию каждый новый открывался бы в Agent с
записью. Вопрос о хранении по репозиторию пользователю не выносится: `AgentState.mode` уже одно
значение на окно, а чаты в разных папках идут параллельно
([45-parallel-sessions.md](45-parallel-sessions.md)), так что по репозиторию пришлось бы
переносить режим в сессии. Пользы это не даёт.

- **Запись, потом состояние.** Настройка не записалась — команда возвращает ошибку, не меняется
  ни бэкенд, ни чип, окно показывает причину. Отвергнут порядок `set_unattended` (состояние, потом
  запись): при ошибке бэкенд уже в новом режиме, а чип в старом, и это то расхождение, против
  которого написан `useBackendSetting`.
- **Старт.** Бэкенд читает настройку сам, когда создаётся `AgentState` в `lib.rs`: режим применяется
  там, и ход не зависит от того, успело ли окно. Настройка не читается — Agent.
- **Окно.** Новая команда отдаёт текущий режим, `useBackendSetting` получает необязательное
  начальное чтение. Ответ, пришедший после выбора пользователя, отбрасывается, как в
  `useApprovalMemory`. Команды синхронные: память и маленький файл настроек, что `AGENTS.md`
  разрешает.
- **Комментарий в начале `conversation_mode.rs`** («a restriction switched on in March and wondered
  about in June») и комментарий у `AgentState.mode` переписываются. Ответ на прежний довод: режим
  теперь виден в строке под полем ввода.

### 8. Старые данные мигрировать не нужно

Значения `plan` и `ask` нигде не лежат. `ConversationMode` нет в `chat_record`, в `PendingApproval`
(чекпоинт приостановленного хода) и в настройках; ход возобновляется в режиме чипа. На фронте
`atlas-mode` — это другой выбор, Chat или Agent. Журнал следующих подсказок хранит строки, они ни
во что не разбираются обратно. `deny_unknown_fields` в проекте нет. Старый чат с `writePlan` и
`todo` в истории открывается как есть; вызов из памяти в Analyst отказывается гейтом.

### 9. Подсказка следующего сообщения не меняет формат

`next_prompt` пишет `ask` для Analyst: формат общий со скриптом обучения, и модель училась на этом
слове. Значение `plan` просто перестаёт появляться.

### 10. Что проверено и не меняется

`Settings.tsx:484` — образец кнопок в предпросмотре темы, с режимами не связан. `describeTool.ts`:
подпись `writePlan` и общая строка `offer` от режимов не зависят. Значение `"ask"` в `Composer.tsx`
и текст `Ask` под полем — это одобрение, а не режим.

  `domain/settings.rs` — поле настроек. `domain/next_prompt.rs` — соответствие режима и слова.

  `lib.rs` и старт `AgentState` там же.
- Фронт: `lib/chat.ts`, `lib/offer.ts`, `lib/slashCommands.ts` (`askMode` уходит, `/analyze` требует
  Agent), `hooks/useBackendSetting.ts`, `App.tsx`, `OfferCards.tsx`, `ChatPanel.tsx`, `PlanPanel.tsx`,
  комментарий в `ComposerSettings.tsx`.

## Нарезка

Каждый этап — отдельный коммит с тестами и мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)). Перед мутациями проверить порт 1420 и
предупредить пользователя, если идёт `tauri dev`.

**AN-1. Implement из Agent.** Plan пока остаётся, так что этап работает сам по себе. Вид offer с
отказом без плана, признак в `ToolDeps`, абзац Agent, описание инструмента, `OfferCards` с «Review
the plan», `pickOffer` через `implement`, кнопка в `PlanPanel` вне режима Plan. Задача bench
`plan-on-request`: просьба составить план, проверка — дерево не тронуто и план написан. Для этого
`agent_bench` отдаёт `check.sh` файл с планом хода: без него нетронутый репозиторий прошёл бы
проверку, а README bench требует, чтобы он падал.
Тесты: отказ без плана, с пустым `turn.plan`; согласие с планом из окна и с написанным в этом ходе;
`writePlan` и `offer` в одном раунде; `offerOf` принимает implement; кнопка оставляет чеклист;
«Review the plan» открывает вкладку.

**AN-2. Agent и Analyst.** `PickedMode`, удаление Plan, Ask в Analyst, набор инструментов, абзац
Analyst, MCP в `mcp_for_turn` и `next_request_frame`, `plan-handoff` уходит, `next_prompt`, места в
Catalog, `slashCommands`, подписи в `chat.ts`, таблица в `AGENTS.md`, правка тестов, которые стояли
на Plan (`llm_chat`, `context_compaction`, `turn_setup`, `prompt`, `features`, фронт).
Тесты: Analyst не предлагает ничего мутирующего, кроме MCP; нет `runCommand`, `knowledgeWrite`,
`todo`; серверы запускаются в Analyst и не запускаются в Review; вызов MCP в Analyst идёт через
карточку; `gitBlame` находится через `toolSearch`; `chat_set_mode` не принимает `review` и `plan`.

**AN-3. Режим запоминается.** Поле настроек, запись и чтение, старт `AgentState`, начальное чтение в
`useBackendSetting`, комментарии.
Тесты: файл без поля читается как Agent; выбор переживает перезапуск; ошибка записи не двигает
режим; поздний ответ не перебивает выбор пользователя; ошибка чтения оставляет Agent.

**AN-4. Документы.** `CHANGELOG.md`, снимок `agent-prompt-snapshot.md`, [33-features.md](33-features.md),
этот план и `docs/README.md`. Прогон agent bench до и после на той же модели, если будет ключ
провайдера; иначе в отчёте прямо сказано, что не прогонялось.

## Вне плана

- Старые документы, где упомянуты Plan и Ask (19, 20, 27, 43, 49), остаются историей и не
  переписываются.
- Подсказки про Auto говорят «change files». В Analyst точнее было бы про MCP. Вернёмся, если
  аналитики будут включать Auto.
- Кнопка в `PlanPanel` не смотрит, закрыт ли чеклист, и видна под выполненным планом. Вернёмся,
  если это будет мешать.
