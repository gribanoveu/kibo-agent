# Vision: картинки от пользователя

План; V-0 (проба) и V-1 (санация и команда) сделаны 2026-10-06, итоги в «Нарезке». Пользователь вставляет (`Cmd+V`) или перетаскивает в Composer скриншот или
фото, и модель его видит. Перед отправкой картинка проходит **санацию** (CDR, *Content Disarm
and Reconstruction*): из файла берутся только пиксели, а файл собирается заново нашим
энкодером. Метаданные, профили, комментарии и приклеенные хвосты в него не попадают. Документ
фиксирует, что известно о vision у DeepSeek, правила санации, изменения в типах и на проводе,
нарезку V-0…V-4 и открытые вопросы.

Картинки, которые агент получает сам (скриншот из browser-MCP, `readFile` на PNG), сюда не
входят — раздел «Не в этом плане».

## Зачем

Сейчас ошибку в UI, график из Grafana или стектрейс с чужого экрана приходится пересказывать
словами или перепечатывать. Модели, которыми пользуются в приложении, уже умеют смотреть
картинки, в том числе DeepSeek (`deepseek-flash`). Не хватает трёх вещей: места для картинки в
сообщении, пути от Composer до провода и гарантии, что вместе с пикселями провайдеру не уходят
GPS-координаты из EXIF.

## Что известно о DeepSeek

По [документации](https://api-docs.deepseek.com/guides/vision) на 2026-10-05:

| Что | Как |
|---|---|
| Модель | `deepseek-flash`. `deepseek-v4-flash-vision-exp` выведена, её запросы уходят на Flash |
| OpenAI-формат | parts в `content`: `{"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}`, внешний URL или `{"type":"file","file_id":…}` из их Files API |
| Anthropic-формат | `{"type":"image","source":{"type":"base64","media_type":"image/png","data":…}}` |
| Где можно | **Только в `user`-сообщениях.** Картинка в `system` или `assistant` — 400 |
| Форматы | JPEG, PNG, GIF, WebP; формат определяется по содержимому, а не по имени |
| Лимиты | 32 MiB на картинку (base64), 48 MiB на тело запроса, 600 картинок, 8192 px на сторону (4096 при 15+ картинках) |
| Стоимость | сервер масштабирует картинку примерно до 1300×1300, **не больше 1024 токенов** на картинку |
| `detail` | `low` / `high` / `original` / `auto` |

В документации не сказано, работает ли картинка вместе с tools, thinking и стримингом. Это
проверяет V-0.

Для сравнения у Anthropic: не больше 5 МБ на картинку, рекомендуемый размер — до 1568 px по
длинной стороне, стоимость около `w·h/750` токенов.

## Что уже есть и переиспользуется

| Что | Где | Как пригодится |
|---|---|---|
| `LlmMessage` — общий тип сообщения для обоих провайдеров | `domain/llm.rs` | новое поле `images`; `content` остаётся строкой, поэтому компакция, экспорт и rewind не меняются |
| Anthropic-провайдер уже шлёт блоки | `wire_messages` в `infra/llm_providers/anthropic.rs` | image-блок добавляется в ветку `User` рядом с `text_block` |
| Метки кэша на последнем блоке user-сообщения | `mark_cache_points` там же | работают как есть: `cache_control` на image-блоке допустим |
| Оценка токенов по символам | `estimate_message_tokens` в `domain/compaction.rs` | картинка считается по размерам, а не по длине base64 |
| Заглушка «[image omitted: …]» | `domain/mcp.rs` | тот же текст подставляется для модели без vision |
| Чат хранит `messages` целиком | `ChatRecord` в `domain/chat_record.rs` | картинка живёт в истории как base64, без отдельного хранилища |
| Транскрипт целиком на стороне фронтенда | `chat_start(messages)` | новых команд для хода не нужно |

## Решения (предлагаются, не приняты)

### 1. Санация на бэкенде, один раз, при прикреплении

Байты из буфера обмена или из перетащенного файла сразу уходят в команду `image_prepare`.
Она возвращает очищенную картинку, и только её фронтенд кладёт в сообщение. Превью в Composer
рисуется из результата, так что пользователь видит ровно то, что уйдёт модели.

Почему на бэкенде, а не через canvas в webview:
- декодирование в Rust (`image`, крейты `png` и `zune-jpeg`) не использует C-код:
  ни libpng, ни libjpeg, ни платформенных кодеков;
- лимиты на размеры и память задаются явно, а не тем, что разрешит WebKit;
- правило одно и проверяется `cargo test` с мутациями, а не поведением браузера.

В `chat_start` картинки повторно не чистятся. История приходит от нашего же фронтенда, а
перекодировать всю историю на каждом раунде дорого. Узкий вход держат типы: `media_type` —
enum `Png | Jpeg`, и serde отвергает всё остальное. Подсунуть «сырой» WebP или SVG в историю не
выйдет даже руками в JSON чата.

### 2. Байты в команду — сырым телом IPC

`invoke("image_prepare", bytes)` с `Uint8Array`. Команда принимает `tauri::ipc::Request` и
читает `InvokeBody::Raw`, поэтому 10 МБ не превращаются в JSON-массив из десяти миллионов
чисел. Обратно идёт JSON: `{ mediaType, data /* base64 */, width, height }`.

Перетаскивание идёт через HTML5 drop (`File` → `arrayBuffer()`), как и вставка. Для этого у
окна выставляется `dragDropEnabled: false`: сейчас `onDragDropEvent` Tauri нигде не
используется (проверить в V-3). Так остаётся один вход, байты, и нет пути из фронтенда,
который пришлось бы проверять.

### 3. Хранение: base64 внутри чата

После санации скриншот весит 0,3–1 МБ (PNG, 1568 px по длинной стороне). Он хранится прямо в
`ChatRecord.messages` и копируется при ветвлении и rewind вместе с сообщением. Отдельное
хранилище картинок по хешу со сборкой мусора — только если чаты на диске заметно вырастут.

### 4. Флаг `supportsImages` у провайдера

Модель без vision отвечает на картинку 400, и тогда каждый следующий запрос этого чата падает.
Поле `supports_images: bool` в `ProviderConfig` и галочка в форме провайдера, по умолчанию
выключена, чтобы ни один существующий провайдер не поменял поведение.

- Включена: картинки идут на провод.
- Выключена: Composer не принимает вставку и показывает подсказку, где включить. Картинки уже
  в истории (чат начат на другой модели) заменяются текстом `[image omitted: image/png]`, как
  в MCP, и ход продолжается.

Флаг на провайдере, а не на модели: в конфиге модель одна (`model`). Если у одного провайдера
появятся модели с vision и без, флаг переедет к модели.

### 5. Порядок в сообщении: картинки, потом текст

Так советует Anthropic, и DeepSeek это не мешает. Одинаково для обоих провайдеров.

## Санация (CDR)

`services/image_sanitize.rs`, чистая функция `sanitize(&[u8]) -> Result<ImagePart, ImageError>`.
Ошибки — `thiserror`-enum в `domain/image.rs` (`TooLarge`, `UnsupportedFormat`,
`DimensionsTooLarge`, `Decode`, `Encode`); в `String` их переводит только команда.

Шаги, по порядку:

1. **Размер входа** не больше 32 MiB — до любого разбора. Это лимит DeepSeek, и больше этого
   держать в памяти незачем.
2. **Формат — по магическим байтам**, не по имени и не по MIME из буфера обмена. Белый список:
   **только PNG и JPEG**. Всё остальное — `UnsupportedFormat` с названием формата и
   подсказкой сохранить как PNG или JPEG:
   - **SVG** — это код (скрипты, внешние ссылки, XXE). Не растеризуется, отказ;
   - **HEIC/HEIF** (фото с iPhone) `image` не декодирует — открытый вопрос 2;
   - GIF, WebP, TIFF, BMP, ICO, AVIF не нужны: скриншот macOS — это PNG, фото — JPEG.
     У `image` включаются только фичи `png` и `jpeg` (`default-features = false`): два
     декодера на чужие файлы вместо десятка и меньше времени сборки.
3. **Декодирование с лимитами** (`image::Limits`): не больше 8192 px на сторону (строгий
   лимит, проверяется по заголовку до выделения памяти) и `max_alloc` 256 MiB. PNG-бомба
   (заголовок на 100 000×100 000) падает с ошибкой, а не съедает память.
4. **Ориентация из EXIF применяется к пикселям** до того, как EXIF выбрасывается, иначе фото с
   телефона приедет боком.
5. **Только первый кадр** у анимированного PNG (APNG).
6. **Пиксели приводятся к 8 бит** (`Rgb8` или `Rgba8`): 16 бит, CMYK и палитра сводятся к
   ним. Альфа остаётся, только если хоть один пиксель не непрозрачен.
7. **Уменьшение до 1568 px по длинной стороне** (Lanczos3), никогда не увеличение. Меньше этого
   размера ни один провайдер не просит, а больше всё равно ужмёт сам — за наш трафик и место
   в чате.
8. **Перекодирование нашим энкодером из буфера пикселей:** JPEG на входе даёт JPEG q85, всё
   остальное — PNG. Энкодер пишет только то, что ему дали. Поэтому не переносятся:
   - EXIF (GPS, модель и серийный номер камеры, время, превью-миниатюра со старым кадром);
   - XMP, IPTC (автор, подписи, история правок);
   - ICC-профиль (цвета широкого охвата слегка сдвинутся — для модели неважно);
   - текстовые чанки PNG (`tEXt`, `zTXt`, `iTXt`) и комментарии JPEG (`COM`);
   - всё после `IEND`/`EOI`: полиглоты и приклеенные архивы.
9. **Размер выхода** не больше 5 МБ (лимит Anthropic). Если PNG больше, он перекодируется в
   JPEG q85 поверх белого фона.

Результат — `ImagePart { media_type, data, width, height }`. Ширина и высота нужны для оценки
токенов (`w·h/750`, с запасом для DeepSeek с его потолком 1024) и для превью.

**Чего санация не делает**, это нужно записать в `08-data-policy.md`:
- текст на самой картинке остаётся: пароль на скриншоте или инструкция модели, написанная
  на картинке, уходят как есть. Это содержимое, а не метаданные;
- стеганография в младших битах пикселей переживает PNG без потерь. Защищаться от неё
  незачем: картинку даёт сам пользователь;
- картинка уходит провайдеру, как и текст. Выходы и хранение описаны в политике.

## Типы и провод

- `domain/llm.rs`: `ImagePart`, `ImageMediaType { Png, Jpeg }`. В `LlmMessage` поле
  `images: Vec<ImagePart>` с `serde(default, skip_serializing_if = "Vec::is_empty")`, поэтому
  старые чаты читаются без миграции, а сообщение без картинок сериализуется байт в байт как
  раньше. Конструктор — `LlmMessage::user_with_images`; у других ролей картинок нет.
- OpenAI-совместимый: `WireMessage.content` становится `#[serde(untagged)]` enum «строка или
  массив parts». Массив — только если есть картинки: parts `image_url` с data-URL, затем
  `text`.
- Anthropic: в ветке `User` блоки `image` (`source.type = "base64"`), затем текстовый.
- `supports_images = false`: оба провайдера вместо картинки ставят текст-заглушку. Одна
  функция в `llm_providers/mod.rs`, которую зовут оба.
- `estimate_message_tokens`: плюс `w·h/750` на картинку; длина base64 не считается.
- Компакция: в `render_for_summary` картинка — строка `[image WxH]`. Сводку пишет модель,
  которая может быть без vision, и пиксели ей не нужны.
- Экспорт чата (`domain/chat_export.rs`): та же строка, без base64.

## Нарезка

### V-0. Проба на живом DeepSeek (без кода в приложении) — сделано 2026-10-06

Скрипт на Python без зависимостей, оба формата (`/chat/completions` и
`/anthropic/v1/messages`), модель `deepseek-flash`. Картинка — PNG: левая половина красная,
правая синяя. Если ответ называет обе половины на своих местах, модель картинку видела.
`/models` отдаёт `deepseek-flash` и `deepseek-v4-pro`.

| Что | Результат |
|---|---|
| Картинка плюс текст | 200, «левая половина красная, правая синяя». Thinking у `deepseek-flash` включён по умолчанию (`reasoning_content`) |
| Картинка плюс `tools` плюс стриминг | 200, вызов `report_colors({"left":"red","right":"blue"})` |
| Картинка плюс `reasoning_effort: high` или `thinking: enabled` | 200 |
| Картинка в `assistant` | 400 «Image in assistant message is not supported» |
| Картинка в `tool` (OpenAI-формат) | **200, хотя документация говорит «только `user`»**. С включённым thinking запрос падает раньше, на «`reasoning_content` must be passed back», то есть не из-за картинки |
| Результат инструмента текстом, следом `user` с картинкой | 200, модель описывает картинку как результат вызова |
| Anthropic-формат: картинка плюс текст, картинка плюс tool | 200 и `tool_use` с верными цветами |
| Anthropic-формат: картинка внутри `tool_result` | 200 (без thinking; с ним — та же ошибка про `thinking`, что и выше) |
| Цена 64×32 | ~200 токенов (234 против 31 у того же запроса без картинки) |
| Цена 1568×1000 | ~940 токенов (970 против 31), в пределах потолка 1024 |
| Картинка в истории, следующий ход | `prompt_cache_hit_tokens: 768` — картинка читается из кэша |

Что это меняет:
- tools и thinking с картинкой совместимы, решение 4 и V-2 остаются как есть;
- для картинок от агента (раздел «Не в этом плане») синтетическое user-сообщение может не
  понадобиться: DeepSeek принимает картинку прямо в `tool` и в `tool_result`. Но это
  расходится с документацией, и полагаться на это стоит только после повторной проверки;
- оценка `w·h/750` для DeepSeek завышена вдвое на крупной картинке (2090 против 940) и
  занижена на мелкой (3 против 200). Для триггера компакции завышение безопасно; формулу
  уточняет V-2 — вероятно, с нижней границей около 200.

### V-1. Санация и команда — сделано 2026-10-06

- `image` 0.25.10 с фичами `png` и `jpeg`; `base64` — прямой зависимостью; `png` — только
  для тестов (`tEXt`, APNG). Ориентация — `ImageDecoder::orientation` и
  `DynamicImage::apply_orientation`: `ImageReader::decode` в 0.25 её не применяет, поэтому
  разбор идёт через `into_decoder`. Размеры проверяются нашим кодом сразу после чтения
  заголовка, а не лимитом `image`: так ошибка называет размеры.
- `domain/image.rs`, `services/image_sanitize.rs`, `commands/images.rs` (`image_prepare`,
  сырое тело), регистрация в `generate_handler![]`, обёртка `prepareImage` в `src/lib/chat.ts`.
- Пороги — `Bounds`, параметр `sanitize_within`: тесты гоняют картинки в десятки пикселей, а
  настоящие значения закреплены отдельным тестом.
- Тесты; фикстуры строятся в самих тестах энкодерами `image` и `png`, бинарных файлов в
  репозитории нет:
  - JPEG с EXIF GPS и `Orientation = 6` → в выходе нет `Exif`, `GPS`, `http://ns.adobe.com/xap`;
    ширина и высота поменялись местами;
  - PNG с `tEXt` и ZIP после `IEND` → нет `tEXt`, после `IEND` ничего;
  - PNG-бомба → `DimensionsTooLarge` без выделения памяти;
  - GIF, WebP, SVG, HEIC → `UnsupportedFormat`;
  - 4000×3000 → 1568×1176; 800×600 не увеличивается;
  - RGBA с полностью непрозрачной альфой → RGB;
  - APNG → один кадр PNG;
  - вход больше 32 MiB → `TooLarge` без разбора.
- Мутационный прогон по `sanitize` (`docs/11-mutation-testing.md`). Каждый шаг санации должен
  быть пойман тестом: выброшенный шаг 8 обязан ронять тест на EXIF.

**Мутации: семнадцать, все пойманы** — снятый лимит входа и лимит на единицу строже; снятый
белый список форматов; снятая проверка размеров и проверка одной ширины; неприменённая
ориентация; снятое уменьшение и уменьшение по короткой стороне; альфа, выброшенная или
оставленная не по правилу; исходный файл наружу вместо перекодированного; фото в PNG; нет
перехода в JPEG, JPEG без белого фона, неверный вес белого; снятый лимит выхода; JPEG не как
MIME.

Уменьшение по короткой стороне выжило бы: все фикстуры были шире, чем выше, но не настолько,
чтобы короткая сторона оказалась под порогом. Это видно было до прогона, и тест на полосу
400×40 добавлен заранее; мутация падает на нём.

## Не в этом плане

- **Картинки от агента**: скриншот из browser/playwright MCP вместо `[image omitted]`,
  `readFile` на PNG. У DeepSeek картинка разрешена только от `user`, поэтому результат
  инструмента остаётся текстом, а картинка идёт следующим синтетическим user-сообщением. Это
  изменение цикла в `llm_chat`, отдельный план после V-0. Санация из V-1 переиспользуется как
  есть.
- Files API DeepSeek и внешние URL: base64 хватает с запасом, а URL — это запрос провайдера
  на чужой сервер.
- Параметр `detail`: по умолчанию `auto`, и уменьшение до 1568 px уже сделано у нас.
- Хранилище картинок по хешу (решение 3).
