# Один цикл вместо субагентов: план работ по шагам

План, предложен 2026-10-26, по issue
[#57](https://github.com/gribanoveu/kibo-agent/issues/57). Источник — статья Anthropic
«Building agents: when to fold subagents into your main agent loop». Здесь не её пересказ
(он в issue), а порядок работ: что делать, в каких файлах, чем проверить и когда шаг
считается сделанным.

Кода в документе нет — только решения и места в коде.

## Порядок и зависимости

```
Ш0 замер «как есть»
 └─ Ш1 бенч A/B ─┬─ Ш2 новые задачи ─ Ш3 решение по explore ─ Ш8 передача от explore
                 │                                          └─ Ш10 форк/продолжение (по замеру)
                 ├─ Ш4 параллельные чтения (независим от ревью)
                 ├─ Ш5 ревью в чистом контексте ─ Ш6 offer ─ Ш7 предложения на бенче
                 └─ Ш9 аудит промпта и числа инструментов
Ш11 режимы по требованию — отдельно, по [35](35-loadable-modes.md)
Ш12 гигиена навыков — позже
```

Ш4 и Ш5–Ш7 друг от друга не зависят и могут идти в разных ветках. Всё, что меняет
промпт, инструмент или цикл, после себя гоняет бенч той же моделью (`CLAUDE.md`).

Правило замеров для всех шагов: **≥3 прогона на задачу**, сравнение **по задачам**
(какие перевернулись), не только итоговый процент. Где меняется промпт — хотя бы две
модели разного уровня (сильная и DeepSeek/OpenAI-совместимая).

## Ш1. Бенч: «с субагентом» и «без него»

**1.1 Флаг `AGENT_BENCH_NO_EXPLORE=1`.**
- Где: `agent_bench::run_task` — сейчас `agents: Some(…)`. Убрать `explore` из
  предложенных инструментов надо так, чтобы модель его **не видела** в определениях, а
  не получала отказ: иначе это не A/B, а тест на обработку ошибки.
- Как выбрать: посмотреть, как `tool_definitions_for` строит список для
  `ConversationMode::Agent`, и дать `Turn` способ исключить инструмент (например,
  через существующие `features`, если `explore` можно сделать фичей, или параметр
  бенча). Решить при реализации, по самому короткому пути, без нового слоя.
- Описание флага — в шапку `agent_bench.rs` к остальным `AGENT_BENCH_*`.

**1.2 Токены и вызовы хелпера отдельно.**
- `tokens_spent` возвращает итог; добавить в `Run` раздельные поля: основной цикл и
  хелперы (`agents.list()` уже есть), число вызовов `explore`.
- В `Run::json`: `explores`, `helperTokensIn/Cached/Out`, `mainTokensIn/Cached/Out`.
  Старое `tokensIn` оставить суммой — со старыми файлами сравнивать можно.
- Тест рядом с `a_run_costs_its_own_requests_and_its_helpers`: раздельные суммы
  сходятся с общей.

**1.3 Скрипт сравнения двух прогонов.**
- `scripts/agent-bench-diff.ts` (bun): на входе два JSONL, на выходе таблица по
  задачам — pass-rate A/B, **перевернувшиеся задачи** (passed→failed и обратно),
  медианы раундов, ошибок инструментов, токенов (основные/хелпер), секунд.
- Задача с разным числом прогонов в A и B — предупреждение, не падение.
- Проверка: на двух файлах из Ш0 (одинаковый конфиг) — переворотов мало, медианы
  близки; вручную подправленный файл даёт ожидаемый переворот.

**1.4 (опционально) Ожидаемый инструмент в `task.md`.**
- Поле вроде `expects: explore` / `expects: skill:<name>`; в JSONL — был ли он вызван
  (`trace` уже есть). Это «routing accuracy» из статьи. Делать, только если в Ш3
  понадобится объяснить, *почему* перевернулась задача.

**1.5 Навыки и MCP в бенче.**
- Сейчас `skills: &[]`, `mcp: McpTools::default()`. Подключить навыки задачи (папка
  `skills/` рядом с `repo/` или общий набор бенча) и, если нужно, MCP-сервер-заглушку.
- Без этого Ш9 (progressive disclosure, отложенные инструменты) не проверить — но для

- Обновить строку «Not wired in yet» в шапке.

## Ш4. Параллельные немутирующие вызовы

Сейчас параллельно идут только ≥2 подряд `explore`. Расширить этот же путь, а не
писать второй.

**4.1 Какие вызовы можно.** Нужен явный признак на `ToolName` — exhaustive `match` без
wildcard, как у `is_mutating` (иначе новый инструмент молча попадёт в параллель).
Рабочее имя `runs_alongside`. Можно: не мутирующие, не спрашивающие подтверждения и не
трогающие состояние раунда — `readFile`, `grep`, `listFiles`, `semanticSearch`,
`gitDiff`/`gitBlame`/`gitLog`/`gitStatus`, `knowledgeSearch`/`knowledgeRead`,
`webFetch`, `webSearch`, `explore`. Нельзя: всё из `is_mutating`, `runCommand` (даже
`ReadOnly` — у него вывод в карточку и процессы), `todo`/`writePlan` (пишут состояние
хода), `skill` и `toolSearch` (меняют, что модель видит дальше), MCP (риск и
подтверждения у каждого свой). Чтения `kube*` — отдельным решением, у них свой бенч.
- Это новое место в таблице контракта инструментов из `AGENTS.md` — добавить строку
  («compiler — exhaustive `match`»).

**4.2 Цикл.** `explore_side_by_side` → общий: берёт с текущей позиции подряд идущие
вызовы с `runs_alongside`, у которых нет отказа в `decisions` и которым
`requires_approval_for` не требует карточки. Остальное без изменений: хуки
`pre_tool_use` по порядку до запуска, отказанный хуком остаётся отказанным, результаты
через `Early`, цикл обрабатывает их по порядку — история, лог, `loop_guard`,
`dedupe_repeat_result` видят вызовы один за другим, как сейчас. Константу переименовать
(`MAX_PARALLEL_CALLS`), `ponytail:` про пачки перенести вместе с ней.

**4.3 Состояние раунда.**
- `ReadFiles`: каждому параллельному вызову — свой пустой `ReadFiles`, после пачки
  слить в `state.reads` **в порядке вызовов** (нужен `ReadFiles::merge` в `domain`,
  поздняя запись побеждает — как при последовательном выполнении). Отдать из `Early`
  вместе с результатом.
- `history` для `execute_call`: параллельным вызовам она не нужна — проверить по
  `tools/mod.rs`, кто её читает; читающих в параллель не пускать.
- `result_clearing` работает по истории после раунда — не задет, проверить тестом.

**4.4 Тесты** в `llm_chat` рядом с `// parallel explore`:
- два `readFile` + `grep` идут одновременно (счётчик в провайдере-заглушке, как
  `most` у explore);
- результаты в истории в порядке вызовов, даже если второй закончил первым;
- хук отказывает второму — первый и третий выполнились, второй отказан;
- `readFile` в пачке, затем `editFile` того же файла в том же раунде проходит
  (`ReadFiles` слит), а без чтения — отказ, как раньше;
- `readFile`, `writeFile`, `readFile` — пачкой идёт только первый.
- Мутации по [11](11-mutation-testing.md): убрать слияние `ReadFiles`, сломать порядок,
  пустить мутирующий в пачку — каждое ловится.

**4.5 Бенч:** секунды ниже при прежнем проценте прохождения.

**Готово:** тесты и мутации, бенч не хуже по качеству и быстрее по времени.

**Сделано** (2026-10-26): `ToolName::runs_alongside`, `ReadFiles::merge`, `llm_chat::side_by_side`
вместо `explore_side_by_side`, `MAX_PARALLEL_CALLS = 4`; тесты на порядок и границы пачки,

## Ш5. Ревью в чистом контексте

**Проблема:** `review_start` получает `messages` — всю историю чата — и дописывает
дифф. Модель проверяет код, видя свои рассуждения о том, почему он правильный.

**Как сделано** (2026-10-26). Хелпер-ход (`run_review`, `ToolResult::Reviewed`, запись в
Agents) не понадобился: после Ш6 ревью никогда не запускается внутри чужого хода — кнопка
предложения отправляет `/review`, то есть ревью всегда идёт ручным путём, при
пользователе. Поэтому чистый контекст сделан в самом ходе ревью:

- **Граница в истории.** `domain::review::own_context(history)` — срез с последнего
  сообщения ревью (оно начинается строкой `REVIEW_REQUEST`). В режиме Review
  `llm_chat::run` отрезает по ней чат и запускает цикл (`run_loop`) только на своей части:
  запрос к модели, счётчик контекста, очистка старых результатов, сжатие, метка «пора
  сворачиваться» — всё видит только ревью. Чеклист чата на время ревью пуст. На любом
  выходе — конец, остановка, пауза на подтверждение — чат приклеивается обратно перед
  историей ревью, чеклист возвращается как был, и фронтенд получает полную историю:
  разговор после ревью видит находки. Граница выводится из истории, поэтому переживает
  паузу без нового состояния.
- Первый вариант — фильтр только в `request_messages`/`request_usage` — ревью субагента
  разобрало: открытая задача чата всё равно дописывалась в запрос (`restore_checklist`),
  метка бюджета от прошлого ревью в чате глушила новую, сжатие и очистка работали по всей
  истории. Разрез на входе в цикл закрывает всё это сразу.
- **План чата в ревью не попадает:** `llm_chat::chat_plan` в режиме Review — `None`, и
  `restore_plan` не дописывает план автора после сообщения с диффом.
- **Права ревьюера не менялись:** `runCommand` с подтверждением, как и было — пользователь
  рядом. Отдельное решение понадобится, только если ревью начнёт идти без него.
- Фронтенд, `FindingCard` и Fix не менялись.
- `ponytail:` если сжатие свернёт само сообщение с диффом, границы не останется, и
  следующий ход ревью получит всю (сжатую) историю. Метка, переживающая сжатие, — когда
  такие длинные ревью появятся.

Тесты: `a_review_reads_from_its_own_message_on` (граница, последнее ревью, без ревью — всё),
`a_review_reads_only_the_change_and_hands_the_chat_back` (в запросах нет чата, его плана и
открытой задачи, через паузу и после неё; счётчик считает только своё; чат и чеклист
возвращаются), `a_stopped_review_hands_the_chat_back`, `a_second_review_is_asked_to_wrap_up_again`.
Мутации: 11 из 11 пойманы (разрез, чеклист, чат и чеклист на каждом из трёх выходов, план, граница).
В приложении не проверялось.

## Ш6. Предложения в конце ответа: `offer { kind, reason }`

Модель не запускает ревью и не просит на него разрешения — она **предлагает**. Во время
хода модель копит предложения, а после ответа пользователь видит их кнопками. Нажатие —
обычное сообщение пользователя, поэтому у предложения нет своего пути выполнения и
подтверждать нечего: в Auto, в обычном режиме и в бенче вызов ведёт себя одинаково и ход
не блокирует.

**6.1 Инструмент.** `offer { kind, reason }`, доступен в `ConversationMode::Agent`.
- `kind` — закрытый enum в `domain`: `review`, `commit`. Свободного текста кнопок нет,
  иначе кнопка появится под каждым ответом. Новый вид — новый вариант enum.
- `reason` обязателен, пустой — ошибка, которую модель прочитает. Пользователь видит,
  зачем предложено: «изменена логика блокировок в двух модулях», а не голое «ревью?».
- Вызов ничего не запускает. Результат для модели — «предложение покажут пользователю
  после ответа». Повторный вызов того же `kind` в ходе заменяет `reason`: по одной
  карточке каждого вида.

**6.2 Когда предложение отказано.** Проверку делает инструмент, а не промпт: иначе
коммит будут предлагать после ответа на вопрос.
- `review`: изменения есть и `review::select` что-то оставил. Иначе ошибка с тем же
  текстом, что у `/review` («nothing to review…»).
- `commit`: дерево отличается от HEAD (`git2`, как у `gitStatus`). Иначе ошибка
  «коммитить нечего».

**6.3 Карточки в чате.** Предложения — это обычные блоки вызова `offer` в транскрипте:
нового канала событий и своего хранилища нет, после перезагрузки всё на месте.
- `ChatPanel` собирает блоки `offer` **последнего хода** и рисует их после ответа
  кнопками, а не на месте вызова. Повторный `kind` — показывается последний.
- Нажатие отправляет сообщение пользователя: `review` → `/review` (путь из Ш5, ревью в
  чистом контексте), `commit` → «Закоммить изменения». Дальше идёт обычный ход со всеми
  обычными подтверждениями (`requires_approval_for`), так что через кнопку ничего не
  обходится. Если модель под prompt injection предложит странное, пользователь сначала
  видит текст кнопки.
- После следующего сообщения пользователя карточки гаснут.
- Пока в ходе есть карточки, серая подсказка в композере
  ([20](20-next-prompt-suggestions.md)) не показывается: одно и то же двумя способами
  не предлагаем.

**6.4 Что после ревью.** Ход `/review` остаётся таким же, как ручной: находки
карточками и кнопка Fix. Модель находки сама не разбирает — разбор начинается, когда
пользователь нажимает Fix или пишет. Тогда модель по каждой находке решает, исправить или
отклонить, и в ответе говорит, что исправлено, что отклонено и почему. Ложная находка не
должна молча превращаться в правку.

Цикл «ревью → исправление» внутри одного хода без присмотра этим теряется. Сознательно:
отчёт пользователь видит раньше ревью и решает сам. Нужен ли цикл — показывает Ш7.

**6.5 Промпт.** В описании инструмента и `mode_instructions(Agent)` (`domain/prompt.rs`):
- `review` — один раз, в конце задачи, если изменение нетривиально: несколько файлов,
  логика, конкурентность, безопасность, обработка ошибок. Не для опечаток, документации и
  переименований.
- `commit` — когда задача закончена и проверена, а пользователь не просил коммитить сам.
- В тексте ответа не дублировать предложение вопросом («закоммитить?») — кнопка уже есть.

**6.6 Контракт инструмента** (таблица из `AGENTS.md`), каждое место:
`ToolName` + `ALL` (51 → 52), `wire_name`, `loop_weight` (минимальный), `is_mutating`
(нет), `rewind_sees` (нет), `runs_alongside` из Ш4 (нет), `ToolCall`/`ToolResult`, модуль
в `services/ai_tools/tools/`, `dispatch`, `model_text.rs`, `DEFINITIONS`, `parse.rs`,
редакция в `tool_call_log.rs`, набор `ConversationMode::Agent`, `ACCOUNTED` в
`src/lib/rewind.ts`, `describeTool.ts` и иконка в `ChatPanel.tsx`. Сам блок вызова в
ленте не рисуется — только карточка после ответа.

**6.7 Тесты.**
- Rust: пустой `reason` — ошибка; `review` без изменений и `commit` при чистом дереве —
  ошибка; вызов в `skip_all` не останавливает ход (`Done`, не `PendingApproval`).
- Фронтенд (`bun test`): карточки последнего хода рисуются после ответа, повторный
  `kind` — один, последний; нажатие отправляет `/review` / текст коммита; после
  следующего сообщения карточек нет; подсказка композера скрыта, пока карточки есть.
- Мутации: убрать проверку изменений, убрать замену повторного `kind`.

**Готово:** тесты и мутации, проверено в приложении (`bun run tauri dev`): модель
предлагает ревью после нетривиальной правки, кнопка запускает ревью в чистом контексте.
`CHANGELOG.md`: «агент предлагает ревью и коммит кнопками в конце ответа; ревью идёт в
чистом контексте».

## Ш7. Предложения на бенче

Вопрос, на который отвечает Ш7: стоит ли ревью своей цены, и нужен ли цикл «ревью →
исправление» без пользователя.

- Флаг `AGENT_BENCH_OFFER=review`: бенч «нажимает» за пользователя. Если в ходе есть
  `offer { kind: review }`, после хода идёт ход ревью в чистом контексте, как от `/review` (Ш5),
  затем ещё один ход с сообщением «Ревью нашло: … Разбери каждую находку: исправь или
  отклони» — то же, что нажать Fix. `check.sh` запускается после всего.
- В JSONL: было ли предложение, его `reason`, число находок, токены ревьюера и второго
  хода отдельно (по образцу 1.2).
- Задачи уже есть: `flaky-counter` (гонка в `take` не видна тестам),
  `expression-precedence` (видимый тест ловит одну ошибку из трёх).
- Сравнить A (без флага) и B (`review`), ≥3 прогона: процент, перевернувшиеся задачи,
  токены, и ещё — **как часто модель предлагает ревью** там, где оно нужно, и там, где
  нет (маленькие правки).
- Решение:
  - B не лучше A → ревью остаётся ручным (`/review` в чистом контексте), вид `review`
    у `offer` убрать; `commit` остаётся.
  - B лучше → оставить как есть. Если выигрыш большой, а пользователи кнопку не жмут —
    тогда, и только тогда, обсуждать запуск ревью внутри хода.

**Готово:** решение с цифрами в `docs/reports/`.

## Ш8. Если `explore` остаётся: передача без «испорченного телефона»

Только после Ш3 и только если решено оставить.

- **Схема ответа.** Вместо слов в `mode_instructions(Explore)` — структура: факты с
  `path:line`, короткие выдержки, «что выяснить не удалось». Разбор ответа хелпера в
  `domain` (чистая функция), невалидный — возвращается как есть с пометкой.
- **Проверка ссылок** до возврата: `path:line` не существует или за пределами файла —
  пометить в результате, как `domain::review` сверяет цитаты с диффом.
- **Прочитанные файлы** — в результате (`AgentInfo::steps` уже есть): основной агент
  перечитает нужное сам.
- **Описание инструмента:** делить по контексту (независимые направления, чтение, которое
  не влезет), а не по типу задачи.
- Бенч: A/B до и после, ≥3 прогона.

## Ш10. Практики субагентов из Claude Code — по замеру

Только если Ш3 оставил `explore` и бенч показывает повод:

- **Форк вместо брифа** (`explore { fork: true }`): хелпер получает историю разговора,

Не делать: хелпер с записью (если когда-нибудь — только в отдельном git worktree),
фоновые хелперы, общее «делегируй кому угодно».
