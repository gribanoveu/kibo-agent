# Встроенный браузер: агент ходит по сайтам, пользователь видит то же окно

План, предложен 2026-10-25. Агент получает браузер, в котором сам открывает страницы,
читает их и жмёт по ним; страница при этом живёт в окне приложения, так что пользователь
видит ровно то, что видит модель, и может вмешаться — в первую очередь чтобы войти на
корпоративный сайт своими руками, не отдавая модели пароль.

Кода в документе нет — только решения. Самое важное из них — движок: свой Chromium здесь
не появляется (решение 1), а «сайдкар» с ним остаётся запасным путём (вне плана).

## Зачем свой, если Playwright MCP и так подключается

Серверы со скриншотами — Playwright, Chrome DevTools — сегодня добавляются в Settings → MCP
как обычные MCP-серверы ([23-mcp-extension.md](23-mcp-extension.md), строка «Картинки в
результатах», M-3). Браузер получается сразу, без кода. Чего у этого пути нет:

- **Пользователь ничего не видит.** MCP-сервер запускает свой Chromium без окна; что модель
  делает и на какой странице она застряла — видно только по логу вызовов.
- **Войти нельзя.** Логин на корпоративном сайте — это пароль или SSO, которого у модели
  нет и быть не должно. Видимое окно решает это без секретов: человек входит сам.
- **Картинки до модели не доходят.** Скриншот — самая частая польза browser-MCP, а результат
  инструмента у нас текст: картинка идёт следующим синтетическим сообщением пользователя
  ([30-vision.md](30-vision.md), «Не в этом плане»). Ни один MCP-сервер этого не обойдёт.
- **Отдельный профиль.** Cookies и входы MCP-браузера не имеют отношения к тому, что
  пользователь уже открыл; у встроенного они одни.

Поэтому: свой браузер — встроенный; MCP-серверы со скриншотами остаются для того, что
встроенный не умеет (перехват сети, несколько вкладок).

Если выбирать MCP как быстрый baseline сегодня, то два разумных — и они разные по смыслу
(оба говорят с моделью текстом, так что без вижена работают оба):

| | `@playwright/mcp` (Microsoft) | `@mozilla/firefox-devtools-mcp` |
|---|---|---|
| Движки | Chromium, Firefox, WebKit — **свои сборки**, скачиваются отдельно | **только системный Firefox** |
| Протокол | свой слой Playwright (CDP / Juggler) | WebDriver BiDi, с откатом на Marionette |
| Как отдаёт страницу | `browser_snapshot` — дерево доступности с `ref`, клик по `ref` | `take_snapshot` с `uid`, `click_by_uid` / `fill_by_uid` |
| Сессия пользователя | своя, `browser_save_storage_state` для входа | `--connect-existing` — **подключается к уже запущенному Firefox с вашим профилем** |
| Сверх кликов | `--codegen typescript` пишет тест из прогулки, PDF, вкладки, `--caps` | сеть, консоль и загрузки — включены всегда; пресеты `slim`/`basic`/`developer` |
| Где живёт | stdio, ставится `npx @playwright/mcp@latest` | stdio, ставится `npx @mozilla/firefox-devtools-mcp` |

Источники — документация обоих: `microsoft/playwright-mcp` (capabilities, `browser_snapshot`),
`mozilla/firefox-devtools-mcp` (`docs/tools.md`, флаги) и страница Mozilla про DevTools MCP.
Вывод для нас: Playwright MCP — про **тесты и воспроизводимость** (codegen, три движка,
`storageState`), Firefox MCP — про **живой браузер пользователя** (`--connect-existing`), но
только Firefox. Ни один не даёт «видно пользователю внутри приложения» и своего профиля — это
и есть причина решения 1 и 2.

## Решения

### 1. Движок — системный webview, а не свой Chromium

Приложение уже живёт на системном движке: `tauri` без своего браузера, превью прототипа —
`<iframe>` в главном окне по схеме `artifact://` (WKWebView на macOS, WebView2 на Windows,
WebKitGTK на Linux; `infra/prototype_protocol.rs` 373–379 сверяет версии `tauri`/`wry`).
Свой браузер — это второй движок в бандле:

- **Размер.** Chromium — 300+ МБ на платформу, три платформы, обновления отдельно от
  приложения. Прецедент есть (`bundle.resources`: модели ~1 ГБ, `scripts/fetch-meeting-models.ts`),
  но это вес, который платится всегда, а не только теми, кто браузером пользуется.
- **Подпись.** На macOS вложенные helper-процессы Chromium подписываются и нотаризуются
  вместе с приложением; сейчас подпись — `signingIdentity: "-"` с entitlements, и вложенный
  браузер делает нотаризацию отдельной работой.
- **Смысл.** Модель всё равно получает текст (решение 4), а пользователь — картинку, которую
  рисует системный движок. Своего Chromium ради этого не нужно.

Переключаться на свой движок стоит, когда появится сайт, который в WebKit не работает, или
когда понадобится то, чего у системного webview нет вовсе (перехват запросов, несколько
вкладок, загрузки) — тогда тот же интерфейс инструментов получает вторая реализация
(«вне плана»: сайдкар с CDP).

### 2. Видно пользователю — отдельное окно, а не фрейм в доке

Три способа показать страницу, и только третий работает:

- **`<iframe>` в доке, как у прототипа — нельзя.** Чужой сайт в фрейме закрыт
  `X-Frame-Options` и `frame-ancestors`, а из фрейма чужого origin нельзя ни прочитать DOM,
  ни нажать кнопку. К тому же `frame-src` окна сегодня разрешает только `artifact:`
  (`tauri.conf.json`).
- **Дочерняя webview внутри окна (`window.add_child`) — позже и, возможно, никогда.** В Tauri 2
  это за флагом `unstable` (официальная документация: «hidden behind an `unstable` Cargo
  feature flag»), а нативная вьюха рисуется поверх HTML — модалки, дропдауны и композер
  оказались бы под ней, и их пришлось бы прятать при каждом оверлее.
- **Отдельное окно — делаем.** `WebviewWindowBuilder::new(app, "browser-<n>",
  WebviewUrl::External(url))` — тот же приём, что у окна Markdown-просмотрщика
  (`commands/viewer.rs` 112–128), только адрес чужой. Окно без декораций не нужно:
  заголовок — адрес и название страницы, размер и место запоминаются как обычно.

В главном окне — панель в правой колонке (там, где превью прототипа): адрес, заголовок,
журнал действий агента («открыл», «снимок», «нажал [e12] Войти»), кнопки **Show the window**
(фокус), **Take over** (фокус и подсказка «входите, я подожду» — после этого ход ждёт),
**Close**. Пользователь видит страницу целиком, сам кликает и сам вводит пароль; агент
продолжает с того места.

### 3. Обратный канал из страницы — один узкий инструмент, а не IPC

В страницу при загрузке вставляется наш скрипт (`initialization_script` билдера, иначе тот же
скрипт `eval`-ом в `on_page_load`): он снимает видимые элементы с номерами, обводит элемент
перед нажатием и сообщает о переходах и ошибках страницы.

Наружу — **ровно одна команда**, `browser_report`, и только у окна `browser-*`
(`capabilities/browser.json`, `remote.urls` с шаблоном `*`). Ничего из `core:*` этому окну не
даётся: страница не может читать файлы, события, состояние окон или звать другие команды.

Что остаётся: скрипт страницы технически может звать `browser_report` сам (в Tauri IPC из
любой вьюхи достижим, держит его ключ вызова — тот же урок, что в
[31-prototype-role.md](31-prototype-role.md) 150–172). Поэтому:

- команда принимает отчёт только с одноразовым `nonce`, который бэкенд выдал вместе со
  скриптом и погасил, — отчёт «не в свой момент» отбрасывается;
- отчёт — это снимок и событие навигации, то есть текст самой страницы. Подделать их
  враждебная страница может и без IPC: она и так пишет всё, что модель прочитает. Худшее,
  что даёт канал, — тот же уровень доверия, что у любого прочитанного сайта (решение 7);
- `browser_report` не отвечает странице ничем, что та не знала бы.

Ключевое — проверить, **доходит ли `browser_report` до приложения**: инъекция и `eval` от CSP не зависят (см. ниже), а вот `fetch` к своей схеме и `img`-маячок — зависят, поэтому канал остаётся один — IPC. Если Tauri откажется принимать IPC из удалённого origin даже с `remote` в capability, придётся держать окно браузера на своей странице (`artifact://`), а сайт в ней — во фрейме; это ломает решение 2 и решается в BR-0.

### 4. Инструменты — текст, потому что результат инструмента картинку не несёт

| Инструмент | Аргументы | Что возвращает |
|---|---|---|
| `browserOpen` | `url` — только `http`/`https` | Адрес после перехода, заголовок, код состояния и снимок страницы |
| `browserSnapshot` | `full?`, `waitFor?` (test id или регион) | Снимок: адрес, заголовок, `[e12] button "Купить" data-test-id="buy"`, заголовки и до 2 000 символов текста; `ref` живут до следующей навигации, внизу — «ещё 43 элемента не показаны» |
| `browserAct` | `action`: `click` / `type` / `press` / `scroll` / `back` / `forward` / `reload`; `ref?`, `text?`, `key?` | Изменения: новый адрес, появившиеся и исчезнувшие `ref`, сообщения страницы, ошибки консоли |

Адреса `file:`, `data:`, `javascript:` и `chrome:` отклоняются доменом, а не проверкой в
инструменте. Действие по `ref`, а не по CSS-селектору: селектор протухает между вызовами, а
`ref` либо ещё жив, либо инструмент честно отвечает «страница изменилась, сделайте снимок».

`browserScreenshot` и `browserEval` — вне первой нарезки (см. «Вне плана»): картинку модель
получает только синтетическим сообщением пользователя, а свободный JS даёт модели всё, что
видит страница, включая токены в `localStorage`, — это дверь, которую не надо открывать, пока
снимка и действий хватает.

### 5. Где предлагается: фича `browser`, а не роль

Роль — это когда нужен другой промпт и другой набор инструментов на весь чат (Kubernetes,
Kibana). Браузер нужен в обоих местах: в Agent — «проверь, что dev-сервер открывается и форма
отправляется», в Chat — «посмотри, что на этой странице». Поэтому — фича каталога `browser`
(включается пользователем, как Knowledge):

- **чтение** (`browserOpen`, `browserSnapshot`) предлагается везде, где включена фича;
- **действия** (`browserAct`) — только там, где меняют (тест «Plan, Ask и помощник ничего
  мутирующего не получают» из AGENTS.md), и с карточкой подтверждения: `is_mutating = true`;
- вкладка **Read only / Can act** над полем ввода (как «Changes» у Kubernetes) выключает
  действия и в Agent, и в Chat;
- без открытого окна браузера действия отвечают «ask the user to open a page», а не открывают
  окно сами: окно появляется на экране пользователя, и это должно быть его решением.

Итог по местам контракта инструмента (таблица в AGENTS.md): `ToolName`, `ToolCall`,
`ToolResult`, модуль в `services/ai_tools/tools/`, `dispatch`, `model_text.rs`, `DEFINITIONS`,
`parse.rs`, `tool_call_log.rs`, `conversation_mode.rs` (чтение), `features.rs`, `describeTool.ts`,
иконка в `ChatPanel.tsx`; в `rewind.ts` — `ACCOUNTED` без изменений: файлов браузер не пишет,
`rewind_sees = false`.

### 6. Постоянный профиль, вход — руками пользователя

Cookies, `localStorage` и входы — в каталоге приложения (`<app dir>/browser/`), один профиль
на приложение. Это обратная сторона решения 2 и главная его польза: человек один раз входит в
Confluence, Jira или Kibana в этом окне, и дальше агент работает уже в его сессии.

- Пароль модель не видит никогда: поле ввода поднимает окно и ждёт пользователя, дальше
  снимок показывает уже страницу после входа.
- «Забыть всё» — кнопка в панели, сносит каталог профиля (как удаление данных фичи).
- Чтения сохранённых паролей, автозаполнения и менеджера паролей нет вовсе.

### 7. Данные и безопасность

- **Страница уходит провайдеру модели** так же, как текст файлов: снимок — это содержимое
  страницы. Строка в [08-data-policy.md](08-data-policy.md), и пункт «снимок — это то, что
  видно на странице, включая личные данные, которые в неё попали».
- **`data_policy.rs` этого не увидит.** Он ловит сеть в Rust (`ureq` и компании в
  `NETWORK_ALLOWED`), а тут ходит webview. Значит правило ручное и записано в документе
  политики: браузер — единственный путь наружу мимо `http_agent`.
- **Страница — данные, не инструкции.** «Ignore previous instructions» в тексте страницы
  ничего не меняет: правило из `INSTRUCTIONS` действует и на снимок.
- **Что модели недоступно:** диск (кроме профиля), буфер обмена, загрузки, DevTools, история
  других окон; окно браузера не может звать команды приложения (решение 3).
- **Публичный сайт под нашим окном.** Окно `browser-*` — единственное место, где в приложении
  исполняется чужой JS. Оно вне `main`: `capabilities/browser.json` называет один
  `browser_report`, а тест `architecture.rs` держит правило «окно зовёт только своё».

### 8. Корпоративный сайт на core-ds и микрофронтендах: локаторы и автотест

Три вещи делают такой сайт удобнее для агента, чем «любой сайт», и все три живут в снимке и
в мосте, а не в движке.

**`data-test-id` — главный селектор, и он уже в разметке.** core-ds рисует `dataTestId` как
`data-test-id`, а вложенным элементам даёт производные (`submit-button-loader`) — это записано
в скилле `.agents/skills/core-components/SKILL.md` (таблица «`data-test-id` attribute →
`dataTestId` prop») и сверяется по MCP `component_info`, который у приложения уже подключён.
Поэтому снимок показывает `data-test-id` рядом с `ref`, а `browserAct` принимает и то и
другое: `ref` — чтобы нажать сейчас, `data-test-id` — чтобы нажатие стало строкой теста.
Классы не годятся вовсе (хеши, см. [37-prototype-styles.md](37-prototype-styles.md) 18–24),
текст — только когда id нет, и снимок говорит об этом прямо: «6 элементов из 24 без
`data-test-id`». Это же — бесплатный аудит тестируемости для фронтенд-команды.

**Снимок обязан знать, что core-ds рисует не в дереве страницы.** `Modal`, `Select`/`Mq`,
`Toast`, `Tooltip`, `Notification`, календарь `DateRangeInput` — порталом в `body`; `Select`
— не `<select>`; у `Input` обёртка `Field`. Снимок, обходящий только корень remote'а, не
увидит ни выпадающего списка, ни модалки — самая частая причина «модель жмёт в пустоту».
Поэтому: обход всего документа, оверлеи отдельным слоем («overlay above the page»), и для
каждого элемента — вид контрола и работающий способ действия (`click`, `type` + `press`,
клик по оверлею + выбор), а не только тег. `Skeleton` — это состояние, а не контент:
снимок говорит «страница ещё грузится, 3 skeleton'а» и ждёт.

**Микрофронтенды: регион, готовность, переход.** Shell рисуется раньше remote'ов, поэтому
`load` ≠ «готово», и флейк ручного теста переезжает в автоген такой же. Снимок перечисляет
регионы (mount-точки) и состояние каждого: готов / пусто / remote не загрузился.
`browserSnapshot` с `waitFor` ждёт test id или регион, а не `waitForTimeout`. Переходы внутри
remote — `pushState`, и `on_page_load` их не даёт: мост (решение 3) сообщает
`pushState`/`popstate`/`hashchange`, иначе «переход» в снимке не виден. Remote в `<iframe>` —
обход по кадрам, а в записи `frameLocator`; есть ли такие у вас — вопрос 7.

**Запись → автотест.** Транскрипт `browserAct` — это уже шаги теста: адрес, локатор
(`getByTestId('submit-order')`), действие. Нового инструмента для письма нет: агент пишет
спеку в открытую папку обычными `writeFile`/`editFile`, а проверки берёт из того, что реально
видел («видно», «в адресе `/orders/17`», «в таблице 3 строки»). Это не противоречит решению 5
в [28-api-tester-role.md](28-api-tester-role.md) («отчёт, файлов чат не пишет»): там артефакт
чата, здесь — код в репозитории. Прогон — `runCommand` (`bunx playwright test`), падение
читается и правится как сборка; ожидания в тесте — по `data-test-id` региона.

- **Вход в тест:** команда `browser_state` отдаёт cookies профиля как Playwright
  `storageState.json` — файл в `.gitignore`, пароля в коде нет, руками логиниться повторно не
  надо. Вторая польза постоянного профиля (решение 6).
- **Фреймворк — настройка проекта:** транскрипт нейтрален, а шаблон спеки берётся из
  настройки (Playwright по умолчанию; Cypress или Testing Library — другие шаблоны).
- **Чего не делаем:** своего раннера, своих фикстур, своего языка тестов и второй справки по
  core-ds — `component_info` из Settings → MCP уже есть, правило в промпте: перед первым
  использованием компонента спросить `component_info`, модификаторы test id не выдумывать.

## Проба: что уже проверено на WKWebView (2026-10-25)

Стенд — отдельная Swift-проба на `WKWebView` (без сборки приложения и без MCP-браузера):
страница с живым, но строгим CSP (`default-src 'none'; script-src 'none'; connect-src 'none'`),
два пользовательских скрипта (`.atDocumentStart` и `.atDocumentEnd`), свой обработчик схемы и
`WKScriptMessageHandler` — тот же механизм, которым Tauri отдаёт IPC на macOS.

| Вопрос | Ответ |
|---|---|
| Выполняется ли вставленный скрипт при `script-src 'none'` | **Да**, оба (внутренний инлайновый скрипт самой страницы при этом заблокирован — CSP живой) |
| Работает ли `eval`/`new Function` из этого скрипта | **Да**, вернули `2` — CSP страницы их не блокирует |
| Доходят ли сообщения в `messageHandlers` (механизм IPC Tauri) | **Да**, все: нет `nonce`, `localStorage`, `testid`, `title`, `pushState` |
| `fetch` к своей схеме | **Нет**: `TypeError: Load failed`, обработчик не вызван — `connect-src` страницы сильнее |
| `new Image().src` на свою схему | **Зависит от момента**: в `atDocumentStart` (до разбора `<meta>` CSP) доходит, после — `img-error`, обработчик не вызван |
| Видны ли переходы SPA | **Да**: `history.pushState` работает и виден в скрипте — мост может его перехватить и сообщить |
| `document.querySelectorAll('[data-test-id]')` | **Работает**: 0 в начале документа, 1 после загрузки — снимок берётся не раньше `atDocumentEnd` |
| Снимок экрана | `takeSnapshot` у `WKWebView` **работает** и вне видимого окна (1800×1400 при 900×700 @2x), но в `tauri`/`wry` 2.11.5 API для него нет (в wry есть только iOS-биндинг) — нужен свой вызов через `objc2` |

Выводы для решений выше: **3** — канал только IPC, `fetch`/маячок не запасной путь, значит
`remote` в capability обязателен и `nonce` тоже; **2** — отдельное окно живёт; **4** — снимок
экрана возможен, но своим кодом и только на macOS пока.

Стенд был одностраничный и временный (лежит в `/tmp`, в репозиторий не попал). Windows
(WebView2, Chromium) не проверялся вовсе — там другой движок и другой механизм инъекции.

### Живой стенд: wowtax (2026-10-25, Chromium)

Прошёл сценарий глазами будущего агента: `testlink.alfabank.ru/corp-customer-creator-ui/login/
wowtax/?profileId=…` → календарь сроков внизу главной → модалка по строке.

| Что | Как вышло |
|---|---|
| Вход | Сессия в профиле уже была — страница открылась сразу на `/wowtax/`, заголовок «Бухгалтерия – Альфа-Бизнес Онлайн» |
| `data-test-id` на странице | **87 штук на 72 интерактивных элемента** — практика есть, но покрытие неровное |
| Календарь (`[data-test-id="calendar"]`) | core-ds `Table`: вкладки «Актуально» / «Все», группы «Прошедшие» / «Актуальные», статусы «К ОПЛАТЕ» / «ОПЛАЧЕНО» / «ПРЕДСТОИТ ОПЛАТИТЬ» / «ПРЕДСТОИТ ПОДАТЬ» |
| Контролы самого календаря | **10 штук, и ни у одного нет `data-test-id`**: вкладки только текстом, восемь кнопок-иконок сортировки вообще без текста |
| Строки таблицы | `role="presentation"`, `cursor: auto`, ни кнопок, ни ссылок внутри — по ним **всё равно можно нажать**, модалка открывается |
| Идентификаторы строк | `table-33-row`, `table-34-row`… — **позиционные**: после переключения вкладки были `17/18/19`, стали `33/34/35` |
| Модалка | `role="dialog"`, `data-test-id="sidebar-declaration-modal"` (осмысленный id), 1400×829, портал не в `body`, а двумя уровнями ниже |
| Внутри модалки | «14 347,50 ₽ · Фиксированный страховой взнос за I квартал 2027 · К ОПЛАТЕ ДО 31 МАРТА 2027», блоки «Что такое фиксированный взнос», «Как оплачивать»; кнопки — «Оплатить», «Уже оплачено», закрытие — `aria-label="закрыть"`; **внутри ни одного `data-test-id`** |
| Скрытые модалки | в DOM лежат уже отрисованные `base-modal` («Нейропомощник») без видимости — фильтр по видимости обязателен |
| Помеха клику | клик по «Добавить доход» не прошёл: `<canvas>` онбординг-подсветки перекрывает кнопку |

Что это значит для решений:

- **Снимок индексирует не только интерактив.** Строка таблицы — цель клика без роли и без
  курсора; снимок по a11y-дереву её кликабельной не назовёт. Поэтому в снимке отдельным
  списком идут «строки и карточки» (текст строки одной строкой), а `browserAct` умеет по ним
  кликать и говорит, изменилось ли что-то, — модель учится на результате, а не на эвристике.
  Это не требует знания core-ds: правило общее для таблиц.
- **Генератор тестов обязан ругаться на позиционные id.** `table-33-row` живёт до перерисовки;
  якорем теста должен быть осмысленный id (`sidebar-declaration-modal`) или содержимое
  (текст/статус/сумма), а позиционный id — только как последний довод и с пометкой.
- **Вакансия тестируемости реальна:** у модалки есть id, а у её кнопок и у всех вкладок
  календаря — нет. Снимок это показывает числами, и это же — самый полезный отчёт для команды.
- **Оверлей-подсветка** (первый заход, онбординг) ломает и запись шагов: агент должен видеть,
  что верхний элемент в точке клика — не тот, что он выбрал, и говорить об этом, а не молча
  кликать по координатам.

Стенд проверен в Chromium (у агента был он, не WKWebView): DOM и `data-test-id` те же, но
поведение кликов в WKWebView может отличаться — в BR-0 прогнать один и тот же сценарий в
окне приложения.

### 9. Без вижена: на чём агент ориентируется

Проверено на себе в этом же сценарии (wowtax, 2026-10-25): страница разобрана **без единого
пикселя** — только текст. Значит вижен для функциональной работы не нужен; нужен снимок
правильной формы и три привычки в промпте.

Что должно быть в снимке, чтобы это работало:

1. **Роли и `ref`, как в a11y-дереве** — то же, что отдают `browser_snapshot` у Playwright MCP
   и `take_snapshot` у Firefox DevTools MCP; здесь — свой снимок с теми же свойствами.
2. **`data-test-id` рядом с `ref`** и число элементов без него (решение 8).
3. **Только видимое**, плюс отдельный список «оверлеи» и «скрытые диалоги в DOM» — иначе
   модель жмёт по невидимому.
4. **Строки и карточки отдельным списком** (живой стенд): цель клика без роли и без курсора.
5. **Что изменилось после действия** — дельта (новые и исчезшие `ref`, адрес, сообщения
   консоли и ошибки сети), а не вся страница заново: дешевле по токенам и точнее.
6. **Перекрытия — геометрией, а не глазами:** проверка `document.elementFromPoint` в точке
   клика и сравнение с целевым элементом. Так и нашлась онбординг-подсветка на `<canvas>`,
   которая съедала клик; это заменяет «посмотреть глазами» для самого частого визуального сбоя.

Чего текст не даёт и что с этим делать: «правильно ли выглядит» (вёрстка, цвета, контраст),
графики на `<canvas>`, содержимое картинок, PDF. Для функциональных сценариев и тестов этого
не надо; когда надо — это либо человек в том же окне (решение 2), либо `browserScreenshot`
синтетическим сообщением ([30-vision.md](30-vision.md)), когда появится модель с vision.
Поэтому `browserScreenshot` и не в первой нарезке: он не про ориентацию.

Промпт инструментов (три правила, которые заменили мне вижен в этом прогоне): снимок перед
действием и после изменения; адресовать по `data-test-id`/`ref`, а не по координатам; «не
знаю, нажимается ли» — нажать и посмотреть дельту, а не гадать.

### 10. Чем встроенный браузер лучше общего — профиль сайта

Вопрос был поставлен так: «заточить под эти страницы, потому что общие работают плохо». Это
решаемо и решается **данными, а не движком**: у встроенного браузера есть профиль сайта,
который читают и снимок, и действия. Всё в таблице ниже — замеры на wowtax 2026-10-25, где
общий инструмент (a11y-снимок + клик по `ref`) теряет именно то, что здесь важно.

| Что теряет общий инструмент (замер) | Что делает профиль |
|---|---|
| Строка таблицы кликабельна, но `role="presentation"`, `cursor: auto`, внутри ни кнопки | `rows`: какие контейнеры — цели клика и **что клик открывает** (`sidebar-declaration-modal`) — модель знает эффект до нажатия |
| Сумма в a11y-дереве рассыпается: «14 347» / «,» / «50» / «₽» | `normalize`: текст из `[class*=amount__component]` → «14 347,50 ₽» (сам элемент, не общий обход) |
| Ячейки — плоский текст вперемешку с заголовками | `columns`: `data-index` у ячеек уже `date` / `action` / `status` / `sum` — строка рендерится как таблица с именованными колонками |
| Id строк позиционные: `table-17-row` → `table-33-row` | `anchors`: осмысленные (`calendar`, `sidebar-declaration-modal`, `application-menu-item`), позиционные — в список «в тестах не использовать» |
| 10 контролов календаря без `data-test-id`, вкладки только текстом, 8 кнопок-иконок без текста | `controls`: объявленные контролы с локатором (регион + текст/aria), а не догадка по дереву |
| В DOM уже лежат скрытые `base-modal` («Нейропомощник») | `ignore` / `hidden`: что не показывать модели и куда не кликать |
| Онбординг-подсветка на `<canvas>` съедает клики | `blockers`: известные перекрытия и как их снять; плюс `elementFromPoint` в `browserAct` |
| Шум: iframe `ru.id.facct.ru/id.html`, `module-webPush`, коммуникатор, тултипы | `ignore`: 150 узлов мимо контекста уходят из снимка |
| «Оплатить», «Уже оплачено» — реальные последствия | `danger`: метки опасных действий → карточка подтверждения; на проде — запрет по умолчанию |
| Агент прокликивает то, что имеет адрес: `?tab=taxable&taxPeriod=КВ.01.2027`, `/feed/`, `/payment-hub/` | `deeplinks`: переход по адресу вместо трёх кликов — меньше шагов и меньше флейков |
| Не знает слов предметной области | `glossary` в промпт: «К ОПЛАТЕ», «ПРЕДСТОИТ ПОДАТЬ», `КВ.01.2027` — что значит и что делать |
| Регионы микрофронтендов неотличимы от обычной страницы | `regions`: `corpShared`, `module-webPush`, `module-*` (прямые дети `body`) — снимок сгруппирован по модулям, а не плоский |

Почему это нельзя получить от Playwright и Firefox MCP: их снимок — дерево доступности,
одинаковое для любого сайта. Оно не знает, что строка таблицы — кнопка, что `data-index=sum` —
деньги, что «Оплатить» тратит деньги и что у страницы есть прямой адрес на нужный квартал.
Наш выигрыш — ровно в том, что a11y-дерево выбрасывает: семантика самодельных виджетов,
намерение мутации и навигация самого приложения.

**Как это устроено.** Профиль — **данные, а не код**: файл на origin (`browser-sites/wowtax…`),
встроенный и пользовательский (`~/.kibo/browser-sites/`), по образцу ранбуков
(`domain/runbooks.rs`) и стилей прототипа ([37-prototype-styles.md](37-prototype-styles.md));
раздаётся каталогом как новый вид — как `prototype-style` в 37. Читают его: `browserSnapshot`
(регионы, нормализация, колонки, `ignore`, `anchors`), `browserAct` (`danger`, `blockers`,
`rows`), промпт (`glossary`, `deeplinks`). Второй сайт — второй файл, а не второй набор
инструментов.

**Профиль проверяет себя.** `browserProfileCheck` открывает сайт и проверяет, что каждый
объявленный якорь/строка/контрол существует и видим; расхождение — ошибка с именем пункта, а
не тихая деградация до общего режима. Это ответ на «сайт поменялся» и условие, без которого
профиль через месяц хуже, чем ничего.

**Лучше — это измеряется.** `bench/wowtax-tasks/` на стенде: задачи с скрытой проверкой
(«модалка по сроку открыта и в ней нужный квартал», «тест на модалку написан и зелёный»),
два оружия — встроенный браузер с профилем и baseline (Playwright MCP), метрики — шаги до
цели, неудачные клики, токены, доля прошедших сгенерированных тестов. Без этого «лучше» —
заявление, а не факт.

**Границы.** Профиль привязан к вёрстке — отсюда проверка якорей и бенч. Стенд и прод — разные
origin'ы, и на проде `danger` запрещает мутации по умолчанию. И профиль не делает «красиво
ли выглядит» — это по-прежнему не текст (решение 9).

## Слои

- `domain/browser.rs` — чистое: адрес (`http`/`https`, отказ остальному), состояние окна
  (id, адрес, заголовок, ждёт ли пользователя), снимок (элемент → `ref`, обрезка, потолки),
  действие → скрипт, разбор отчёта, ошибки (`thiserror`).
- `infra/browser.rs` — единственное место с `tauri::`: окно `browser-*`, вставка скрипта,
  `eval`, приём отчётов. Порт (`trait BrowserEngine`) — не сейчас: вторая реализация (CDP)
  вне плана, а trait без неё противоречит «не строй границу заранее» из AGENTS.md.
- `services/ai_tools/tools/browser.rs` — три инструмента; `ToolDeps` получает дескриптор
  браузера рядом с `web` и `history`.
- `commands/browser.rs` — открыть, закрыть, фокус, отдать панели состояние, принять отчёт.
  Всё, что ждёт страницу, — `async` через `commands::blocking`.
- Событие — `browser:changed` с `{ id }` (sink по образцу `ProcessEventSink`), в
  `NETWORK_ALLOWED` не попадает; `commands::blocking` — да, `infra/browser.rs` ждёт webview.
- Фронт: `src/lib/browser.ts` (обёртки и `onBrowserChanged`), `src/hooks/useBrowser.ts`,
  `src/components/BrowserPanel.tsx` в правой колонке рядом с превью.

## Нарезка

Каждый шаг — отдельный коммит; бэкенд — с мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)).

**BR-0. Проба — без кода приложения.** Часть уже сделана (таблица выше, WKWebView/macOS).
Осталось проверить в самом приложении: доходит ли `browser_report` из окна с `remote` в
capability; что возвращает зов того же `browser_report` из окна `main` и оттуда, где такой
capability нет; держатся ли cookies профиля между запусками; открывается ли живой `https://`
со SSO/сертификатом; и то же самое на WebView2 (Windows) — там инъекция, `script-src 'none'`
и поведение `eval` могут отличаться. Ответ на первый пункт решает, живёт ли решение 3.

**BR-1. Домен.** `domain/browser.rs`: адрес, снимок и `ref`, потолки, действие → скрипт,
разбор отчёта, ошибки. Тесты: `file:`/`data:`/`javascript:` отклоняются; `ref` не переживает
навигацию; обрезка снимка и «ещё N элементов»; пустая страница; ошибка консоли в отчёт.

**BR-2. Окно и канал.** `infra/browser.rs`, `capabilities/browser.json`, `browser_report` с
`nonce`, заголовок окна по `title`, закрытие по выходу из приложения. Тест
`architecture.rs`: окно `browser-*` может звать только `browser_report`.

**BR-3. Инструменты.** Три инструмента по контракту (все места из таблицы AGENTS.md),
`describeTool.ts`, иконка. `browserOpen` на живом сайте, `browserAct` — по фикстуре.

**BR-4. Фича, панель, вкладка.** `features.rs` (`browser`, выключена по умолчанию), строка в
`conversation_mode.rs`, вкладка «Read only / Can act» в `PlainChat.tsx`, панель в правой
колонке с журналом и кнопками Show / Take over / Close, «Забыть всё».

**BR-5. Бенч.** `bench/browser-tasks/` на локальных страницах, без сети: найти цену в
таблице, пройти форму из трёх полей, найти ошибку в консоли, страница, которая «зависла».
Метрика — действия до цели, ошибки `ref`, токены; провайдер — `AGENT_BENCH_*`, как у
`kube_bench`.

**BR-6. Сайт на core-ds и тест.** Оверлеи и `data-test-id` в снимке, регионы и `waitFor`,
`pushState` в мосте, `browser_state` → `storageState.json`, шаблон спеки (Playwright) в
настройке. Проверка — на живом стенде микрофронтендов: агент проходит сценарий, пишет спеку в
открытую папку, прогоняет её через `runCommand` и доводит до зелёного; отдельно — страница
без `data-test-id`, где он обязан сказать об этом, а не выдумать локатор.

**BR-7. Профиль сайта и бенч.** Формат профиля (`domain/browser_site.rs`), встроенный профиль
wowtax с регионами, колонками, `normalize`, `anchors`, `rows`, `danger`, `ignore`,
`deeplinks`, `glossary`; `browserProfileCheck`; `bench/wowtax-tasks/` с baseline `playwright
mcp` и метриками. Готово, когда профиль даёт меньше шагов и меньше неудачных кликов, чем
baseline, на всех задачах бенча.

**BR-8. Документы.** [08-data-policy.md](08-data-policy.md), `docs/README.md`,
`CHANGELOG.md`.

## Вне плана

- **Свой движок-сайдкар (CDP).** Второй exe вроде `meeting_sidecar` (флаг на `argv[1]`, JSON в
  stdout, убийство дерева процессов — `infra/mcp_stdio.rs`, `infra/background.rs`) или отдельный
  бинарь Chromium с `--remote-debugging-port=0` и WebSocket на `127.0.0.1`. Даёт то, чего у
  системного webview нет: перехват сети, несколько вкладок, загрузки, одинаковый движок на всех
  ОС. Цена: 300+ МБ на платформу, подпись вложенных процессов, клиент WebSocket (в зависимостях
  его нет — `ureq` не про это), а «видно пользователю» превращается в трансляцию кадров
  (`Page.startScreencast` в canvas) вместо настоящего окна. Делать, только если BR-0 покажет,
  что инъекция не работает, или когда появится сайт, не работающий в WebKit.
- **Дочерняя webview в доке** вместо окна (`unstable` в Tauri 2) — если пользователю окно ОС
  окажется неудобно.
- `browserScreenshot` как синтетическое сообщение пользователя ([30-vision.md](30-vision.md)).
- `browserEval`, загрузки файлов, несколько вкладок, печать и PDF, история переходов между
  запусками.

1. ~~Вставленный скрипт при строгом CSP страницы~~ — **закрыт для macOS/WKWebView** 2026-10-25:
