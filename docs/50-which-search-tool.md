# Какой поиск выбрать: `grep` или `semanticSearch`

План, предложен 2026-11-02. Повод — модель почти никогда не ищет по смыслу: в журнале
вызовов за месяц `semanticSearch` — 20 вызовов против 933 у `grep`
([agent-tools-count.md](reports/agent-tools-count.md)). Цена — не в токенах схемы, а в
лишних раундах: имя, которого нет, угадывается 2–3 раза подряд, вместо одного поиска по
описанию поведения. При этом сам поиск с 2026-10-27 не дёшев (ниже): он делает свой
дополнительный запрос к модели.

Здесь: что сейчас сказано модели и где, почему просьба в промпте — слабый рычаг, четыре
правки с точными формулировками, и **отдельная задача бенча под эту потребность** — без
неё сравнить «до и после» нечем.

## Что сейчас в текстах

| Где | Что сказано | Что из этого следует |
|---|---|---|
| `INSTRUCTIONS` ([prompt.rs:47](../src-tauri/src/domain/prompt.rs#L47)) | «`grep` is the repository's own search… **Use it to find where something is in the code**, one `grep` per name in the same response.» | Единственный поиск, названный в постоянно присутствующем тексте, назван с директивой |
| там же | `semanticSearch` **не упоминается вовсе**; про `listFiles` — одна строка | Поиск по смыслу модель видит только в списке инструментов |
| описание `semanticSearch` ([semantic_search.rs:57](../src-tauri/src/services/ai_tools/tools/semantic_search.rs#L57)) | Первая фраза: «Find code by what it does or what it is called, when you do not know the file». **Предпоследняя**: «For every occurrence of an exact string, use grep»; после неё только «At most N matches» | Разрешение в первой фразе, императив — почти в самом конце: последнее, что модель читает, и выигрывает |
| описание `grep` ([grep.rs:209](../src-tauri/src/services/ai_tools/tools/grep.rs#L209)) | «Use it when you know what the code says; use listFiles when you know where it lives» | Альтернатива названа одна — `listFiles`, не поиск по смыслу |
| результат `grep` при нуле ([model_text.rs:370](../src-tauri/src/services/ai_tools/model_text.rs#L370)) | «No matches. Git-ignored paths (build output, dependencies) are not searched — use runCommand to search them.» | В момент, когда гипотеза провалилась, совет ведёт в `runCommand`, а не к поиску по смыслу |
| подсказки самого поиска ([code_search.rs:261](../src-tauri/src/services/code_search.rs#L261)–347) | `meta.hint`: слова нет в индексе, документация не включена, фильтр отсёк, язык не тот | Механизм «подсказать в момент неудачи» здесь уже есть и работает |

Схема `semanticSearch` при этом стоит 701 токен — самая дорогая из встроенных
(там же, [agent-tools-count.md](reports/agent-tools-count.md)), то есть платим за неё в
каждом запросе и почти не зовём.

## Цена поиска — не как у `grep`

С 2026-10-27 `semanticSearch` — это **два** запроса: индекс отдаёт 30 кандидатов, и активная
модель чата одним запросом без инструментов и без истории называет лучшие
(`services/search_rerank.rs`, коммит `08da499b`). Это подняло сразу и качество, и цену
([13-reranker-research.md](13-reranker-research.md), `search_bench`, 93 вопроса):

| | MRR | file@1 |
|---|---|---|
| индекс сам (BM25 + векторы) | 0,546 | 37 |
| + переранжирование моделью чата | **0,786** | **68** |
| русские вопросы (32) | 0,441 → **0,700** | 10 → 21 |
| место вызова (12) | 0,444 → **0,861** | 3 → 10 |

Цена — 4,1 с и ~3,7 тыс. токенов на входе плюс ~600 на выходе **за каждый поиск**. Значит
«дешевле, чем два-три промахнувшихся `grep`» верно по раундам, но не по токенам: `grep`
своего запроса не делает. Правило выбора поэтому — про **когда** (имени не знаю), а не
про «всегда дешевле»; и удалять инструмент только из-за цены — не расчёт: он единственный,
кто даёт 0,786 там, где ранжированный `grep` даёт ничего.

Переранжирование есть только у `semanticSearch`: вопросы, похожие на поиск по коду, решает
он один.

## Почему «дописать в промпт» — слабый рычаг

Это уже проверено на соседнем правиле: «`grep`, а не shell grep» модель не выполняет и с
правилом — 1 вызов `grep` против 26 shell-грепов с ним и 3 против 23 без него
([agent-tools-count.md](reports/agent-tools-count.md), «Правило 2 и имя `grep`»).
Переименование инструмента в `findInFiles` тоже ничего не дало.

Вывод для этого плана: **убеждение живёт в двух местах и оба — не общий промпт.**
В описании того инструмента, чей это выбор, и в тексте результата в момент провала —
там, где модель читает его, принимая следующее решение. Общий промпт — только чтобы
назвать разделение один раз.

## Четыре правки

Порядок — по возрастанию силы; каждая отдельным коммитом, чтобы мерить по одной.

### 1. Описание `grep`: назвать третью дорогу

`tools/grep.rs`, `definition().description`:

| | |
|---|---|
| было | Use it when you know what the code says; use listFiles when you know where it lives. |
| стало | Use it when you know what the code says and need every place it occurs; `listFiles` when you know where it lives; `semanticSearch` when you know what the code does but not what it is called. |

### 2. Описание `semanticSearch`: «когда» — вперёд, «точная строка» — условием

`tools/semantic_search.rs`:

| | |
|---|---|
| было (первая фраза) | Find code by what it does or what it is called, when you do not know the file. |
| стало | Find code by what it does, when you cannot name it: write the behaviour as one sentence, with the identifiers you do know, and get the few best places — path, lines, enclosing declaration — from the folder's index. Reach for it first on «how does this work / where does this start», and after a `grep` for a guessed name came back empty: another spelling rarely helps — describe the behaviour instead. |
| было (последняя фраза) | For every occurrence of an exact string, use grep. |
| стало | When you can spell the string and want every occurrence, or a count, `grep` is cheaper and complete; this searches one meaning at a time. |

Остальное в описании не трогать: язык запроса, `fts`, `queries`, `meta.hint`, `topK` —
на них стоят тесты, и `fts` — ровно то, что лечит промахи ранжирования.

### 3. Подсказка в результате `grep` при нуле совпадений

`model_text::grep`, ветка «No matches». Самая сильная правка: приходит в тот момент, когда
догадка провалилась.

| | |
|---|---|
| было | No matches. Git-ignored paths (build output, dependencies) are not searched — use runCommand to search them.{not_searched} |
| стало | Nothing matched. If you guessed the name, it may be spelled differently — `semanticSearch` finds code by what it does when you cannot name it. Git-ignored paths (build output, dependencies) are not searched — use runCommand for those.{not_searched} |

Только при нуле: в каждом ответе эта строка была бы шумом.

### 4. Одна строка в `INSTRUCTIONS`

В абзац про `grep` ([prompt.rs:57](../src-tauri/src/domain/prompt.rs#L57)):

> `grep` and `semanticSearch` answer different questions: `grep` when you can name the
> string and need every occurrence, `semanticSearch` when you know the behaviour but not
> the name — ask it in a sentence about what the code does. A guessed name that finds
> nothing is the signal to switch, not to guess again.

Тест `every_backticked_word_is_a_real_tool` это пропустит: оба имени — настоящие
инструменты. Правка отдельная, потому что это единственная из четырёх, которая меняет
общий промпт для всех режимов.

## Что не меняется

- **Ранжирование** (`services/code_search.rs`) и **переранжирование моделью**
  (`services/search_rerank.rs`) — ни весов, ни порогов, ни `meta.hint`, ни `POOL`:
  это `search_bench`, отдельная работа; правки ниже меняют только выбор инструмента.
  Замер качества после любой такой работы — с `SEARCH_BENCH_RERANK=1`, иначе меряется
  индекс без модели, а не то, что видит агент.
- **Схема** `semanticSearch`: поля, размеры, `TEXT_CHARS`.
- **`grep`** остаётся полным и точным: правка только в описании.
- **Когда индекса нет** — `semanticSearch` по-прежнему отвечает «this folder has no index»
  и указывает на `grep`; тексты не должны обещать поиск, которого в этой папке нет.

## Задача для бенча: `find-by-behaviour`

Ни одна из четырёх правок не проверяется тестом «модель выбрала нужный инструмент» —
это поведение, и мерить его надо бенчем. Существующие 13 задач этого не ловят:
`find-by-search` — 10 файлов, где причина находится по словам задачи, а `one-handler-in-many`
и `log-forensics` — случаи, где прав именно `grep`. Нужна **новая задача, в которой
дешёвый путь заведомо проваливается.**

### Каким должен быть её репозиторий

1. **25–40 файлов**, связная небольшая программа (например, сервис на 4 модуля плюс
   тесты и заглушки) — чтобы `listFiles` + чтение наугад были дороже одного поиска.
2. **Слова задачи не встречаются в коде.** Пользователь говорит «итог считается неверно,
   когда скидка и налог вместе» — в коде нет ни `discount`, ни `tax`, ни `total` в именах:
   есть `Adjustment`, `Rate`, `Settlement`, `apply_rules`. Ни в именах файлов, ни в
   идентификаторах, ни в комментариях — иначе `grep` по словам задачи находит место и
   задача ничего не меряет.
3. **Причина — одна строка в одном из 2–3 файлов**, но поведение видно только по смыслу:
   порядок применения правил в конвейере. Знание, что искать, есть только у того, кто
   прочитал описание задачи и перевёл его в «как это называется в коде».
4. **Документации, которая выдаёт ответ, нет** — иначе модель найдёт её (или `includeDocs`),
   и снова не будет выбора инструмента.
5. **Тот же класс ошибки, что в `find-by-search`**: неверный результат на одном входе,
   верный на остальных, — проверяется скрытым тестом на нескольких входах, включая
   контрольный, который уже работает.

### Формат — как у остальных задач

`src-tauri/bench/agent-tasks/find-by-behaviour/`:

| Файл | Что в нём |
|---|---|
| `task.md` | сообщение пользователя дословно: симптом в терминах домена, без имён из кода |
| `repo/` | папка задачи (25–40 файлов, `.gitattributes` задачи требует `-text`) |
| `check.sh` | `PYTHONPATH=. python3 "$TASK/hidden_test.py"` в копии (`WORKSPACE`) |
| `hidden_test.py` | 4–6 входов: два на исправленное поведение, один контрольный (работал и раньше), один на порядок применения правил; ничего не видно из `repo/` |

**Самопроверка без модели — обязательна** (как у всех задач, см. README бенча):

1. на нетронутом `repo/` — `check.sh` падает;
2. с эталонной правкой (одна строка, лежит рядом с задачей, не в `repo/`) — проходит;
3. с правдоподобной неверной правкой (симптом ушёл, скрытый вход — нет) — падает.

Без третьего пункта задача проверяет только «модель что-то поменяла».

### Что мерить

`target/agent-bench/<stamp>.jsonl`, одна строка на прогон. По строке видно:

| Поле | Что из него берём |
|---|---|
| `passed` | решена ли задача (это главное: правки не должны ломать качество) |
| `rounds`, `calls` | сколько шагов понадобилось |
| `trace[].tool`, `.status`, `.args` | **сколько было `semanticSearch`**, сколько `grep`, сколько `grep` подряд до первого поиска по смыслу |
| `repeats` | повторные вызовы с теми же аргументами — признак «угадываю имя» |
| `toolErrors` | отказы инструментов (в том числе `semanticSearch` без индекса — быть не должно) |
| `tokensIn`, `tokensCached`, `seconds` | цена |

Важно: **переранжирование в эти токены не входит.** Это запрос мимо хода — `usage` его
ответа отбрасывается (`search_rerank::rerank`), а бенч считает токены хода. Поэтому стоимость
поиска в замере приходится добирать отдельно (по `seconds`, по логу провайдера или
добавив счётчик в `search_rerank`), иначе «после» будет выглядеть дешевле, чем есть.

Бенч зовёт **настоящий** `semanticSearch` — тот, что с переранжированием: обёртка собирается в
`execute_call` ([llm_chat.rs:1028](../src-tauri/src/services/llm_chat.rs#L1028)), а не в бенче. Поэтому
`seconds` прогона включает и этот запрос, а `tokensIn` — нет (см. выше).

Скрипта сравнения в репозитории нет (`scripts/agent-bench-diff.ts` из
[43-single-loop.md](43-single-loop.md) Ш1.3 не делался), поэтому по JSONL — `jq`
одной строкой: сумма `semanticSearch` и `grep` по `trace`, медианы `rounds` и `tokensIn`
по прогонам. Если замер пойдёт в работу дальше, скрипт стоит написать — но не раньше: на
двух прогонах хватит `jq`.

### Протокол «до и после»

1. **`git lfs pull`** — бенч индексирует каждую копию встроенной моделью
   (`agent_bench.rs:38`, `searcher`, стр. 185–196), и без весов `semanticSearch` не
   работает.
2. **База («до»)**: все задачи как есть, `AGENT_BENCH_RUNS=3`, две модели — одна сильная и
   `deepseek-flash` (`AGENT_BENCH_KIND=openai`, `https://api.deepseek.com`). Сохранить
   JSONL под именами «модель-до-дата».
3. **После каждой правки** (SS-2…SS-4) — только 4 задачи, чтобы не платить за весь бенч:
   `AGENT_BENCH_TASKS=find-by-behaviour,find-by-search,one-handler-in-many,log-forensics`.
   Первая — потребность, вторая — соседний случай «поиск по симптому», третья и четвёртая —
   **контроль**: там имя точное или данные большие, и прав именно `grep`/конвейер.
4. **Полный прогон** всех задач — один раз, в конце, после решения по всем правкам: правка
   общего промпта видна и на задачах, которых в списке нет.
5. **Решение** — по задачам, а не по итоговому проценту: на `find-by-behaviour` правка
   считается удавшейся, если `passed` не упал и стало **меньше** `rounds`/`repeats` и
   `semanticSearch` встречается в большинстве прогонов; правка откатывается, если
   `passed` где-то перевернулся или если `grep` просел на контрольных задачах (модель стала
   искать по смыслу там, где нужен был точный поиск).

## Инварианты

1. **Тексты не обещают того, чего нет.** Нет индекса — `semanticSearch` отказывает и
   указывает на `grep`; ни описание, ни подсказка не должны звать в поиск, который сейчас
   недоступен.
2. **Подсказка — только на нуле совпадений.** Она не появляется в успешном ответе `grep`.
3. **`grep` остаётся полным.** Ни одна правка не сужает то, что он находит.
4. **Схема не дорожает.** Ни новых полей, ни выросшего описания сверх пары фраз.
5. **Ранжирование не трогаем.** Улучшение выбора инструмента не выдаётся за улучшение
   ранжирования, и наоборот.
6. **Каждое изменение промпта или описания — с прогоном бенча** той же моделью, что база
   (`CLAUDE.md`), и с решением, записанным цифрами.

## Риски и потолки

- **Перекос в другую сторону.** Модель начнёт звать `semanticSearch` на всё: на это
  контрольные задачи (`one-handler-in-many`, `log-forensics`), где просадка `grep` видна.
- **Задача может оказаться решаемой `listFiles`.** Если после SS-1 модель проходит её без
  единого поиска — задача слабая: файлов слишком мало или имена говорящие. Переделать
  репозиторий, а не списывать на модель.
- **Индексация стоит времени.** Каждый прогон индексирует копию (см. `searcher`), поэтому
  задача — про 25–40 маленьких файлов, не про мегабайты.
- **Одна модель — не ответ.** `deepseek-flash` ошибается иначе, чем сильная модель; решение
  по одной модели — не решение (это записано в аудите промпта).
- **Правка 4 (общий промпт) — самая рискованная** и самая дешёвая по тексту: 2 предложения.
  Если она ничего не даёт без правок 2–3, её стоит убрать, а не оставлять «на всякий
  случай»: правила без эффекта делают промпт дороже и обучают модель пропускать правила.
- **Цена одного поиска.** 4–5 с и ~4,3 тыс. токенов за вызов: цель — 1–2 поиска на прогон,
  а не «искать на каждом шаге». Поэтому в критерии решения и стоит «`semanticSearch` в
  большинстве прогонов», а не «в каждом раунде»; обратное — тоже перекос, только дорогой.

## Открытые вопросы

1. **Подсказка при `weak`, а не только при нуле.** Поиск уже говорит «слова нет в
   индексе»; стоит ли `grep`-ответ с одним-двумя совпадениями в посторонних файлах тоже
   подсказывать? Ответ — из замера: считать такие случаи по `trace` в базе.
