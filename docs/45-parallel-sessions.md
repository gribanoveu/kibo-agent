# Параллельные сессии агента (PS)

Статус: **PS-0 сделан** (2026-10-30) — поведение приложения пока не менялось. Следующий — PS-1.

Рабочий документ фичи. F-8 ([10-multi-workspace.md](10-multi-workspace.md)) сознательно
оставила «один ход за раз» (её инвариант 7: второй `chat_start` при идущем ходе
отказывает) с пометкой «параллельные ходы — отдельная фича потом». Это то самое «потом»:
два и более хода одновременно в разных чатах, в том числе в одной папке.

Документ живёт до конца фичи: опись, решения, нарезка, инварианты, журнал.

## Решения (приняты пользователем 2026-10-30)

| Вопрос | Решение | Что это значит |
|---|---|---|
| Единица параллельности | **Ход в чате; сессия = чат** | Не «вкладки агента», не субагенты: два обычных чата, в каждом свой ход. Субагенты (`explore`, `/review`) уже параллельны внутри хода и здесь не меняются |
| Состояние хода в бэкенде | **Реестр по `chat_id`** вместо синглтонов в `AgentState` | `cancel`, `steering`, `next_prompt`, `finished_turn` — на сессию; `approval` и `mode` — как решено в F-8 (на папку / общий). См. опись ниже |
| Промпт | **Замороженная заметка о параллельной сессии** | При старте хода, если в той же рабочей копии уже идёт другой ход, в системную часть добавляется заметка (текст ниже). Читается **один раз на ход**, как skills/rules, и не меняется между раундами — иначе каждый раунд мимо кэша (аргумент `Frozen` в `llm_chat.rs`) |
| Worktree | **По инициативе модели через `offer`; перенос — между ходами** | Заметка в промпте разрешает модели предложить перенос чата в worktree — новый kind `offer { kind: "worktree" }`; кнопка переносит чат, и **следующие** ходы собираются со scope'ом worktree (detached → ветка `agent/<slug>`, base запоминается). Посреди хода scope не перепривязывается — причины ниже. Когда работа сделана: `offer { kind: "pullRequest" }` → PR из ветки worktree в base. `git_branches::add_worktree` уже есть |
| Лимит | **3–4 идущих хода**, дальше — очередь | У всех троих ниже практический потолок один: дальше узкое место — ревью человеком, а не рантайм. Лимит в настройках, не в коде |
| Карточки и стоп | **Адресные** | Карточка подтверждения, Stop, steering — каждое в свой чат; глобального «стоп» нет |

**Предлагаемое, требует подтверждения:**

- **Один и тот же чат параллельно сам с собой не идёт.** Второй `chat_start` с тем же
  `chat_id` отказывает — внутри одного чата ход по-прежнему один, иначе история,
  которой владеет окно, раздвоится.
- **Семантический конфликт заметка не решает.** Два хода могут править разные функции
  одного файла — файловых коллизий нет, а смысловая поломка есть. Смягчение — PS-4
  (запись только по свежему прочтению); решение — worktree.

Общий паттерн, на котором сошлись все: **сессия = свой контекст + свой checkout, а
координация («кто за какой кусок отвечает») живёт вне агентов**. У нас это ложится на
уже существующее: ядро хода stateless (историю приносит окно), worktree-поддержка есть,
мультиплексированный канал событий есть.

## Индикация в сайдбаре (дизайн)

Когда ходов несколько, список чатов — единственное место, где видны все сразу: чат на
экране один, а работать могут трое. У каждого чата в списке — индикатор состояния его
сессии:

| Состояние сессии | Индикатор у чата |
|---|---|
| Ход идёт (`running`) | Анимированная точка/спиннер; у чата на экране совпадает с индикатором композера |
| Ждёт карточки (`awaitingApproval`) | Свой значок (вопрос/карточка), не спиннер: это состояние требует человека, и молчать о нём нельзя — именно ради него индикация и нужна в фоне |
| Фоновый ход завершился, пока чат был не на экране | Спокойная метка «завершился», снимается при открытии чата — аналог непрочитанного |
| Нет сессии / чат на экране и дошёл | Ничего |

Источник истины — реестр сессий фронтенда (PS-3): он знает `turnId → chatId` и статус
каждой сессии, потому что через него идут и запуски, и события канала. Опроса и
таймеров нет: индикатор — производная от событий `chat:turn-event` и результата
`chat_start`/`chat_resume`, по правилу AGENTS.md «the frontend does not poll».
Перезапуск окна состояния не теряет: идущий ход живёт в окне, а не в бэкенде, так что
после перезагрузки идущих нет и индикаторов нет — честно.

Стилем — токены из `src/styles/tokens.css`, не браузерные контролы (правила UI из
AGENTS.md); анимация спиннера уважает `prefers-reduced-motion`.

## Заметка в системный промпт (дизайн)

**Триггер.** При сборке хода (`turn_setup::run_in_folder`) реестр сессий отвечает: есть
ли ещё идущие ходы в **той же рабочей копии** (тот же канонизированный root; другой
worktree той же репы — другая копия, по файлам не конфликтует, но ветки общие — это
говорит заметка).

**Заморозка.** Заметка — поле в `prompt::TurnContext` (`parallel: Option<…>`),
заполняется один раз при старте хода и дальше идёт в системный блок неизменной, как
`skills`/`rules`. Причины те же, что у `Frozen` в `llm_chat.rs`: системная часть стоит
первой в каждом запросе, и любое её изменение между раундами — промах кэша на всю
историю. Изменившийся состав параллельных сессий доносится как standing-заметка в конец
истории (`restore_standing`), а не правкой промпта.

**Кто видит.** Вторая сессия — сразу при старте; первая — со своего следующего хода
(её текущий ход уже собран; standing-заметка может сказать и ему).

**Черновик текста:**

```
- Another agent turn is running in this folder right now (chat "<title>"). Its edits
  can land while you work: a file you read earlier may have changed since, and a
  write that finds it changed is refused — re-read the file and apply your change to
  what is there now. Never revert, delete or commit changes you did not make;
  branches and the git index are shared — do not run git checkout, switch, reset,
  clean or rebase. If your task is likely to touch the same files, offer the user a
  move of this chat to a separate worktree (offer `worktree`) and carry on there.
```

**Почему перенос — между ходами, а не посреди.** `ToolScope` собирается при сборке
хода (`turn_setup::run_in_folder`) и заимствуется `Turn<'a>` на всё его время;
промпт называет рабочую папку, а `reads` считает прочитанное относительно её корня.
Перепривязка scope посреди хода ломает всё трое сразу. Ход короткий: кнопка
`offer worktree` переносит чат, и следующий ход уже собирается в worktree — цена
решения одна итерация, а не рефакторинг времени жизни. `git worktree add` через
`runCommand` модель сделать может и сейчас, но толку нет: файловые инструменты
откажут в путях вне scope'а — поэтому перенос и должен быть первоклассным, а не
самодельным.

**PR в конец — тоже `offer`.** Новый kind `pullRequest`, по образцу `review`/`commit`:
инструмент сам решает, есть ли что предлагать — чат в worktree, ветка впереди base,
дерево чистое (всё закоммичено на свою ветку; в своей копии git-guard PS-5 не
действует). Кнопка шлёт обычное сообщение («создай PR»), и его выполнение — push и
создание PR — идёт через `runCommand` **с карточкой**: уход в remote — это выход
данных наружу ([08-data-policy.md](08-data-policy.md)), а не локальная операция.
Сама модель в ветку пользователя не мёрджит никогда — граница та же, что у Codex
cloud: агент правит, человек мёрджит.

**Почему без «re-read before editing».** Править непрочитанное модель не может уже
сейчас: гейт read-before-write в `preflight_tool_call` (ветка «a write without a
read» в `llm_chat.rs`) отказывает такой записи. Но он проверяет **факт** прочтения в
этом ходу, а не его **свежесть**: файл, прочитанный десять раундов назад и с тех пор
тронутый соседней сессией, гейт пропускает. Свежесть добавляет PS-4 — и именно текст
его отказа («changed since you read it») учит модель перечитывать, а не заметка.
Формулировка выше потому описывает не приём («перечитывай перед правкой»), а правило
и его следствие («запись по устаревшему прочтению отказывает — перечитай и правь то,
что есть»). До PS-4 такая фраза обещала бы правило, которого ещё нет.

**Честность заметки.** Она — не гарантия, а этикет. Гарантию дают PS-4 и PS-5: запись
только по свежему прочтению и запрет git-мутаций дерева при >1 идущем ходе. Без них
заметка — пожелание; с ними — описание реальных правил. Поэтому **PS-4 и PS-5 идут
раньше PS-6** (см. нарезку): заметка появляется в промпте, когда правила уже
действуют.

## Инварианты — проверяются тестами, не дисциплиной

1. **Стоп адресный.** `chat_cancel` останавливает ровно свой чат; «стоп при показанной
   карточке» выживает до резюме — на сессию, не на приложение.
2. **`turnId` глобально уникален.** Формат `<chatKey>/turn-<N>`; два экземпляра хука не
   могут сгенерировать один id.
3. **Чат не параллелится сам с собой.** Повторный `chat_start` с идущим `chat_id` —
   ошибка, а не вторая история.
4. **Заметка о параллельности стабильна внутри хода.** Меняется только между ходами;
   изменения состава — standing-заметкой в историю, не правкой системной части.
5. **Запись — только по свежему прочтению.** Файл, изменившийся с момента чтения,
   перечитывается перед правкой, кто бы его ни тронул.
6. **Git-дерево неприкосновенно при >1 идущем ходе.** `checkout`/`switch`/`reset`/
   `clean`/`rebase`/`merge` отказывают в preflight, пока в копии идёт другой ход.
7. **Пауза и резюме независимы.** Чекпоинт одной сессии резюмится её решениями, пока
   другая работает; `resume` чужим чекпоинтом — ошибка (уже есть `check_decisions`,
   добавить `chat_id` в чекпоинт).
8. **Сохранение — в чат хода.** Идущий в фоне ход пишет транскрипт в свой чат, куда бы
   пользователь ни смотрел (наследуется из F-8.7).
9. **Модель не мёрджит и не пушит сама.** В ветку пользователя изменения из worktree
   попадают через PR/мёрдж человеком; уход в remote (push, создание PR) — только через
   карточку подтверждения. Тест: `offer pullRequest` ведёт к сообщению, а не к push;
   `git push` в `runCommand` — всегда карточка, и в Auto тоже.

## Проверка

- После каждого шага: `cargo check && cargo test`, `bun run tsc --noEmit && bun test`.
- В конце — сквозной прогон по инвариантам: для каждого назван тест, который его держит.
- Живая проверка (`bun run tauri dev`), чеклист:
  1. Два чата в одной папке, задача в каждом — оба идут, карточки и стоп свои.
  2. Во втором чате в промпте — заметка о первом (debug-лог запроса).
  3. Первый чат пишет файл, второй его читал раньше и пытается править — отказ
     «changed since you read it», после перечтения — правка проходит.
  4. При двух идущих ходах попросить модель `git checkout -b x` — отказ preflight.
  5. Остановить один ход на середине — другой не замечает.
  6. Переключаться между чатами, пока оба идут, — транскрипты полные, оба сохранены;
     в сайдбаре у обоих — спиннер, у ждущего карточки — значок карточки, у
     завершившегося в фоне — метка, снимающаяся при открытии.
  7. Перезапуск приложения при паузе на карточке — резюме работает, соседняя сессия
     не пострадала.
  8. При двух идущих ходах второй чат заканчивает ответ кнопкой `worktree`; нажатие
     переносит чат, следующий ход — уже в worktree, заметки о параллельности нет.
  9. Доработав в worktree, модель предлагает `pullRequest`; нажатие → push/PR через
     карточку; в ветку пользователя без карточки не уходит ничего.

## Потолки

- **Rate limits провайдера общие.** N сессий × раунды × хелперы (`MAX_PARALLEL_CALLS`)
  упираются в лимиты одного ключа; при 429 каждая сессия ретраится сама
  (`llm_retry`), но глобального координатора нет — ponytail: если 429 станет нормой,
  нужен общий счётчик in-flight запросов на провайдера.
- **Порты, dev-серверы, локальные БД не изолируются** ни заметкой, ни worktree — как и
  у Codex. Два хода, поднявшие dev-сервер, дерутся за порт; заметка в промпте это
  честно называет, но не чинит.
- **Семантический конфликт в одном файле** смягчается PS-4, решается только worktree
  (PS-7) и ревью человеком — у всех троих так же.
- **Очередь сообщений в чате** (`queued`) остаётся per-session; глобальной очереди
  ходов на лимите (PS-1) на первой фазе нет — лишний старт отказывает с объяснением.
- **Реестр сессий не чистится** (PS-0): растёт на число чатов, тронутых за один запуск
  окна, — записи маленькие, а жизнь окна ограничена. Ponytail: если длинная сессия
  окна это когда-нибудь покажет, путь — LRU по последнему обращению.
