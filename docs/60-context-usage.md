# Метр контекста: якорь на реальном usage провайдера плюс оценка нового хвоста

План, CU-1…CU-3 сделаны 2026-11-23; предложен 2026-11-23, пересмотрен 2026-11-23 по исходникам pi и opencode. Кольцо
контекста и Overview показывают оценку «4 символа = токен», которая занижает русский чат с
рассуждениями примерно на четверть: в чате `e1d1053f` метр говорил 175k, а провайдер за тот
же запрос взял 222k. Число становится якорем на реальном `prompt_tokens` последнего запроса
плюс оценка только тех сообщений, что добавлены после него; то же число решает, когда
сворачивать разговор. Кольцо и Overview показывают это число (при открытии чата — из
таблицы маркеров), а не отдельную оценку.

Кода в документе нет — только решения.

## Как решают другие (проверено 2026-11-23 по исходникам)

- **pi (badlogic/pi-mono).** Локального токенизатора нет: `estimateTokens` = `ceil(chars/4)`
  (`compaction.ts:266-306`), картинка — фиксированные 4800 символов (`:244`). Но занятость контекста
  — гибрид `estimateContextTokens` (`:202-242`): берётся usage последней валидной assistant-
  строки (`calculateContextTokens` = `totalTokens || input+output+cacheRead+cacheWrite`) как
  реальный якорь, и только сообщения **после** неё оцениваются chars/4 и прибавляются.
  Порог: `contextTokens > window − reserve` (reserve по умолчанию 16384, `:132-136`,
  `shouldCompact :235-238`). После компакции, пока нет нового assistant-ответа, usage
  считается недостоверным и число обнуляется (защита от null после компакции). Разбор категорий (system/tools/
  skills) нормируется к реальному итогу: относительные доли — оценкой, сумма — якорем
  (pi-context-inspector, проверено по dist). Токенизатор явно отвергнут как низкий ROI.
- **opencode.** Процент и порог — от реального usage: `count = tokens.total ||
  input+output+cache.read+cache.write`; `usable = limit.input − min(20000, maxOutputTokens)`
  (`session/overflow.ts`); chars/4 только для бюджета сохраняемого хвоста
  (`preserve_recent_tokens = clamp(usable×0.25, 2000, 15000)`). Багфикс #46136: порог должен
  смотреть на **кумулятивный** контекст, а не на одну assistant-строку. Issue #32119:
  знаменатель — `limit.input`, а не `limit.context` у моделей с раздельными окнами.
- **Общее:** якорь на usage провайдера; оценкой меряется только новый хвост и бюджет хвоста
  свёртки; категории нормируются к реальному итогу; локальный токенизатор не вводится.
  Наш план следует этому — он проще глобального коэффициента и проверен двумя проектами.

## Что уже есть

- **Метр — чистая оценка.** `domain/compaction.rs`: `estimate_message_tokens` считает
  `content`, id вызова, вызовы и картинки по 4 символа на токен; `native_content`
  (рассуждения, которые уходят провайдеру обратно) не считается вовсе; кириллица занижена —
  это названо в док-комментарии `estimate_tokens`. `ContextUsage::new(frame, history, limit)`
  раскладывает оценку на части (instructions/skills/tools/mcp/conversation);
  `estimate_tool_schema_tokens` сериализует схемы инструментов.
- **Два пути числа в UI.** Между ходами — `chat_context_usage` (`commands/chat.rs:309`) →
  `context_compaction::usage` (`services/context_compaction.rs:89`). Во время хода —
  событие `ContextEstimate` в начале раунда (`services/llm_chat/round.rs:107`,
  `request_usage` на 506). Фронт выбирает: `useAgentTurn.ts:819` — `busy ? turn.estimate :
  session.context`; `ContextMeter.tsx` и `OverviewPanel.tsx` рисуют `context.total`.
- **Реальный счёт API уже приходит каждый раунд** — событие `ContextUsage { usage, cause }`
  (`round.rs:120`). `ChatUsage.prompt_tokens` — входная сторона контекста: Anthropic-адаптер
  суммирует input + cache_read + cache_creation (`infra/llm_providers/anthropic.rs:547`),
  OpenAI-совместимый берёт `prompt_tokens` (включает закешированное). Это строже pi-шного
  `totalTokens` (тот включает и output) — для «занятости контекста» правильнее. Но в UI это
  только фраза в попапе и строка «Cache hit»; заголовок метра его не использует.
- **Отпечаток запроса уже несёт длину истории и хэши частей** — `RequestFingerprint`
  (`domain/request_marker.rs`): system, tools и по хэшу на сообщение истории;
  `compare(previous, current)` даёт `System` / `Tools` / `History{from,of}` / `Unchanged`
  (префикс вырос, ничего не менялось). Снимается в `ask_the_model` (`round.rs:352`) до
  запроса; строка с usage пишется в `requests` (`tool_calls.db`) после попытки, включая
  неудачную (TJ-3).
- **Состояние на чат через ходы — `SessionHandle`** (`commands/agent_state.rs:20`):
  `last_request` — отпечаток последнего запроса. Порт `RequestMarkers`
  (`domain/request_marker.rs:115`) проведён через `turn_setup`; адаптер `ChatMarkers`
  (`commands/chat.rs:78`) пишет строку и помнит отпечаток; `RequestRecord` несёт `usage`.
  У помощника, Chat-режима и теста маркеров нет (`None`).
- **Компакция решает той же оценкой.** `should_compact` — 90% окна (`TRIGGER_PERCENT`);
  `compact_if_needed` (`context_compaction.rs:100`) читает `ContextUsage::new(...).total`;
  хвост (`KEEP_TAIL_PERCENT` 25%) и вход суммаризатора (`SUMMARY_INPUT_PERCENT` 50%) меряются
  `estimate_message_tokens`. Реактивная свёртка после отказа `too_long` — запасной путь с
  хвостом 10%.
- **Живой случай.** Чат `e1d1053f`: оценка 175k (conversation 136k), провайдер 222k —
  русская переписка плюс рассуждения в `native_content`. Занижение ~27%.
- **Метр помощника** (docs/53) — та же формула по символам стрима, якоря по раундам нет.
  **Chat-режим** — `plain_chat_context_usage` (`commands/plain_chat.rs:191`) зовёт тот же
  `usage()`, но `SessionHandle` и маркеров у него нет.

## Решения

### 1. Число = реальный якорь последнего запроса + оценка добавленного после него

Последний успешный запрос взял `prompt_tokens` за всю историю на тот момент. Следующий
запрос — та же история плюс то, что добавлено после: новое сообщение пользователя, заметки,
результаты вызовов. Поэтому итог = `prompt_tokens` якоря + `estimate_tokens` сообщений после
якоря. Оценкой меряется только небольшой хвост, а не весь разговор: её ошибка ограничена
размером хвоста, а не длиной чата. Провайдер — источник правды о своём токенизаторе,
накладных расходах провода и токенах картинок; локальный счёт всего этого не видит.

Отвергнуто: глобальный поправочный коэффициент (прежняя редакция плана) — требует
сглаживания, границ и сброса по модели, и всё равно масштабирует всю оценку, так что ошибка
растёт с чатом; pi и opencode якорятся на usage вместо этого. Отвергнуто: полный токенизатор
как единственный источник — крейт `tiktoken` (pure Rust, v5) несёт словари Qwen (`qwen2`,
`qwen3_5`, 564–989 КБ) и `encoding_for_model`, HuggingFace `tokenizers` уже в зависимостях,
но имя модели за шлюзом не гарантирует кодировку (`qwen4-max` покрыт `qwen3_5` с пометкой
«Qwen 4 (assumed; unpublished)»), и текст-онли счёт не видит накладные расходы и картинки.
pi и opencode токенизатор не вводят; не вводим и мы (открытый вопрос 3 закрыт исследованием).

### 2. Якорь живёт рядом с маркером; достоверность проверяется отпечатком

`SessionHandle.last_request` уже хранит отпечаток; рядом кладётся usage последнего запроса
(`ChatMarkers::record` сохраняет оба). Длина истории в отпечатке (число хэшей сообщений)
говорит, где якорь заканчивается: хвост = `history[len..]`. При открытии чата и после
перезапуска якорь читается из последней строки `requests` (prompt_tokens + хэши).

- Якорь достоверен, только если `compare(отпечаток якоря, текущий отпечаток)` = `Unchanged`
  (префикс тот же, вырос). Сменились system/tools или история переписана (компакция, откат,
  очистка результатов) → якорь недействителен → полная оценка до следующего запроса. Это
  обобщает pi-шный null-守卫 после компакции: не показывать устаревший якорь.
- Смена модели или провайдера инвалидирует якорь (другой токенизатор): модель/провайдер
  хранятся рядом с якорем и сравниваются.
- Неудачный запрос (usage `None`) якорь не обновляет.
- Порт `RequestMarkers` отдаёт якорь (`Option<Anchor>`: prompt_tokens + отпечаток +
  модель/провайдер); у помощника, Chat-режима и теста его нет → полная оценка.

Отвергнуто: новый порт и поле на `Turn` — дубль времени жизни маркера; хранение якоря в
`chats.db` — он про запрос этого процесса, а не про запись чата (в таблице маркеров уже есть).

### 3. Якорь+хвост решает и в метре, и в компакции; категории нормируются к итогу

`should_compact` читает итог гибрида — автокомпакция срабатывает на реальных 90% окна, а не
на реальных ~115%, как сейчас. Бюджет хвоста `plan_compaction` и вход суммаризатора остаются
оценочными (как у pi и opencode: считать историю назад нужно по сообщениям, а якорь там не
помогает); порог честен, потому что основную массу несёт якорь. Части раскладки (instructions/
skills/tools/mcp/conversation) масштабируются так, чтобы сходиться в итог: относительные доли
— оценкой, сумма — якорем+хвостом (паттерн pi-context-inspector). Одно число, которое и
показывает, и решает — этого требует комментарий метра.

Отвергнуто: якорь только в заголовке — порог продолжает срабатывать поздно.

### 4. Слепые зоны оценки закрываются отдельно

`native_content` считается размером сериализованного JSON. Единицы счёта — UTF-8 байты
(как и раньше): это ≈4 ASCII-символа на токен, ≈2 кириллических и ≈1.3 CJK — мультиязычное
правило большого пальца, ближе к правде для CJK, чем плоский вес «2 символа на токен»
(ревью CU-1: вес 2 занижал CJK сильнее байтов). Двойной учёт исключается: у Anthropic
`native_content` — массив блоков, отправляемый **вместо** текста и вызовов, поэтому при
массиве считается только он; у OpenAI-совместимого это объект с одним reasoning-полем поверх
текста и вызовов — прибавляется. Зачем отдельно: полная оценка (до первого запроса, после
переписывания истории, у помощника и Chat-режима) и относительные доли категорий перестают
не видеть рассуждения вовсе; якорь несёт основную массу, но хвост и fallback должны быть
честны. (pi принимает chars/4 как есть, потому что якорь несёт массу; у нас есть
fallback-пути без якоря, поэтому учёт рассуждений стоит того.)

### 5. Кольцо показывает то же число, что вернул API, плюс видимый хвост

Заголовок метра и Overview — итог гибрида: сразу после хода он равен реальному
`prompt_tokens` (хвост пуст), а когда пользователь набрал новое сообщение — якорь плюс
оценка этого сообщения. При открытии чата и после перезапуска якорь берётся из `requests`.
Части сходятся в это число: кольцо, полоса и строки — одни данные. Пока запросов не было или
якорь недействителен (после компакции/отката/смены модели) — полная оценка, и панель называет
её оценкой; когда число якорное — называет «по последнему запросу». Отдельная строка «Last
request» не нужна: заголовок и есть она.

Отвергнуто: заголовок-прогноз всей истории рядом с реальным числом в панели — два числа об
одном, пользователь не знает, которому верить; именно это и жаловало «цифры не отображают
реальность».

## Слои

- `domain/compaction.rs` — чистое: вес не-ASCII, `native_content`; функция гибридного итога
  (якорь + хвост по длине отпечатка, fallback-оценка); нормировка частей к итогу.
- `domain/request_marker.rs` — чистое: `Anchor` (prompt_tokens + отпечаток + модель/провайдер),
  правило достоверности через `compare` и смену модели; `last_anchor()` на порту.
- `services/llm_chat/round.rs` — `request_usage` считает гибрид по якорю порта.
- `services/context_compaction.rs` — `usage()` и `compact_if_needed` с гибридным итогом.
- `commands/agent_state.rs` — якорь рядом с `last_request` в `SessionHandle`;
  `commands/chat.rs` — `ChatMarkers` сохраняет usage, `chat_context_usage`/`chat_compact`
  читают якорь (при открытии — из `requests`); `plain_chat` не тронут (вне плана).
- `infra/tool_call_log.rs` — чтение последней строки `requests` чата (prompt_tokens + хэши).
- Фронт: `src/lib/chat.ts` (тип `ContextUsage` + признак якорности), `src/lib/usage.ts` —
  нормировка частей под итог; `ContextMeter.tsx`, `OverviewPanel.tsx` (заголовок и
  формулировки «по последнему запросу» / «оценка»). `useAgentTurn` отдаёт сведённое число.

## Нарезка

Каждый этап — отдельный коммит с тестами и мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)).

**CU-1. Слепые зоны оценки — сделано.** `native_content` в `estimate_message_tokens` (массив
Anthropic — вместо текста и вызовов, объект OpenAI — поверх); единицы — UTF-8 байты (≈2
кириллических символа на токен, ≈1.3 CJK). Тесты: рассуждения посчитаны; verbatim-массив не
двойится; объект reasoning прибавляется; кириллица ≈2 симв/токен; ASCII и CJK по байтам;
картинки не изменились; части `ContextUsage` сходятся в итог. Мутационная проверка: 6
мутантов, все пойманы (снятый учёт native_content; снятое verbatim-правило; перепутанные
массив/объект; счёт по символам вместо байтов; округление вниз; снятые картинки); первый
прогон на редакции с весами тоже 6/6, после правок по ревью прогон повторён. Ревью
сабагентом: три находки, все исправлены с тестами — двойной учёт verbatim-массива Anthropic
(массив отправляется вместо текста и вызовов), вес «2 символа на токен» занижал CJK сильнее
байтов (единицы возвращены к байтам), док-комментарий выдавал якорь CU-2 за текущий. Не
проверено: вручную в запущенном приложении; agent_bench не нужен — запросы не меняются.

**CU-2. Якорь и гибридный итог — сделано.** `Anchor` (prompt_tokens + отпечаток +
модель/провайдер), `holds_for` (compare = Unchanged и та же модель/провайдер), `trailing` с
клампом; `anchored_tokens` = якорь + оценка хвоста, иначе полная оценка; `last_anchor()` на
порту; `ChatMarkers` хранит якорь в `SessionHandle` через ходы; `tool_call_log::last_anchor`
читает последнюю строку с ценой при открытии (NULL и нули отсеяны, нечитаемые хэши → None).
Тесты: якорь+хвост и пустой хвост; переписанная история / смена system/tools / смена модели →
fallback; usage None и нули не якорят; адаптер помнит якорь через ходы; чтение из таблицы.
Мутационная проверка: 8 мутантов + 2 после ревью, все пойманы (снятый сброс по модели; снятая
инвалидация по отпечатку; сдвинутый хвост; недостоверный якорь в силе; fallback без
фиксированной части; строка без usage / с нулём как якорь; нечитаемые хэши как пустой
префикс; адаптер не сохраняет якорь). Ревью сабагентом: одна находка, исправлена с тестами —
usage с нулями (serde default шлюза) становился якорем и обрушил бы итог почти в ноль;
фильтр `> 0` в `Anchor::of` и в SQL. Не проверено: вручную в запущенном приложении;
подключение к метру и компакции — CU-3.

**CU-3. Гибрид в решениях — сделано.** `ContextUsage::with_total` (части сходятся в итог,
разговор вбирает дрейф округления); `request_parts` (frame + системные сообщения и инструменты в
wire-порядке для отпечатка); `anchored_usage` / `anchored_compact_if_needed`; проводка в
`chat_context_usage`, `chat_compact` (`chat_anchor`: сессия → строка маркеров),
`round::request_usage` (отпечаток тот же, что у маркера раунда). Порог компакции решает по
якорному итогу. Тесты: порог на якорных 90% и fallback на устаревшем якоре; части сходятся;
якорь во время хода (оценка 2-го раунда = usage 1-го + хвост); fallback якоря сессия→строка;
измеренный system-промпт совпадает с отправляемым. Мутационная проверка: 6 мутантов + 1
после ревью, все пойманы (дрейф частей; пустая оценка; метр без якоря; порог по оценке;
якорь не читается после перезапуска; метр хода без якоря; голое имя шелла в измерении).
Ревью сабагентом: одна high-находка, исправлена с тестом — между ходами отпечаток строился
из приближённого промпта (шелл голым именем, `parallel: None`), и якорь всегда отвергался;
измерение теперь описывает шелл как ход. Остальные расхождения (замороженные правила/
parallel, инструменты, найденные `toolSearch`) консервативно откатывают к оценке до
следующего запроса — это намеренно. Не проверено: вручную в запущенном приложении.

**CU-4. Кольцо = число API.** Признак якорности в DTO/типе; заголовок кольца/Overview — итог
гибрида; формулировки «по последнему запросу» / «оценка»; нормировка частей на фронте для
события `ContextEstimate`. Тесты: сразу после хода заголовок = usage раунда; после компакции
— оценка с пометкой; без запросов — оценка; части сходятся в заголовок.

**CU-5. Документы.** `docs/README.md`, `CHANGELOG.md` — одна строка под `## Unreleased`.

## Вне плана

- **Chat-режим и помощники.** `SessionHandle` и маркеров у них нет — якорю негде жить; CU-1
  улучшает их формулу. Вернёмся, если Chat-режиму понадобится якорь (там свой стор на чат).
- **Ремонт старых записей чатов** (например `e1d1053f` с потерянным ходом) — пользователь
  отложил; к подсчёту не относится.
