# PR текущей ветки из Bitbucket Data Center — под веткой в Overview

План, 2026-11-14. BB-0…BB-8 сделаны — проба на живом сервере, домен, клиент с хранилищем,
сервис с командами и наблюдателем, строка PR в Overview с черновиками и серверы в шторке функции в Catalog, документы, инструменты агента `pullRequestStatus` и `pullRequestCreate`, замечания ревьюеров и кнопки-задачи. BB-9 (Auto-fix) отложен — решено 2026-11-23: сначала пожить с кнопками. Функция `pull-requests` в Catalog: под веткой в панели Overview
— строка pull request'а текущей ветки с self-hosted Bitbucket Data Center: заголовок,
состояние, ревьюеры и их решения, сборки по HEAD-коммиту, можно ли мержить и почему нет;
кнопки Create PR, Approve / Unapprove, Merge, Open in browser. У каждого сервера — свой
доверенный сертификат (корпоративный CA). Отдельным пунктом агент получает читающий
инструмент `pullRequestStatus`: тот же PR и те же сборки. Снаружи имена нейтральные, Bitbucket —
только в адаптере, чтобы GitLab, Gitea или GitHub потом стали ещё одним адаптером (решение 9). Образец — то, как Claude
Code (desktop) работает с PR на GitHub, и с 2026-11-15 это не только вид, но и связка с агентом
(решение 10): агент создаёт PR, читает его состояние, а конфликт и замечания ревьюеров
становятся для него задачей одной кнопкой. Работа кончается тем, что пользователь
видит и ведёт свой PR, не открывая браузер.

Кода в документе нет — только решения.

## Решения

### 1. Bitbucket определяется не по адресу, а сервером, которого пользователь добавил

Self-hosted адрес может ничего не говорить: `git.corp.local`, `code.example.ru`. Поэтому
источник истины — список серверов, которые пользователь добавил сам (базовый адрес + токен).
Токен никогда не уходит на хост только потому, что его назвал remote.

Распознавание — только чтобы заполнить форму и подтвердить догадку:

- **Подсказки из remote.** HTTP-клон Data Center выглядит как `https://host[/контекст]/scm/PROJ/repo.git`
  — всё до `/scm/` и есть базовый адрес, вместе с контекстным путём (`/bitbucket`). SSH —
  `ssh://git@host:7999/proj/repo.git`, порт 7999 — порт Bitbucket по умолчанию; базовый адрес
  предлагается как `https://host`.
- **Проба без токена.** `GET {base}/rest/api/latest/application-properties` по документации
  отвечает без аутентификации: JSON с `displayName: "Bitbucket"` и версией. Это и есть
  ответ на «Bitbucket ли это»: ни GitLab, ни Gitea так не отвечают. Проба идёт только по
  кнопке в форме подключения — на адрес, который пользователь видит и может поправить.
- **Принадлежность репозитория — по ссылкам клона.** С токеном
  `GET /rest/api/latest/projects/{p}/repos/{r}` (project и slug — из пути remote) отдаёт
  `links.clone`; один из них, приведённый к той же форме, что и remote
  (`domain::code_host::canonical_remote`: снимаются схема, credentials, `.git`, `/scm/`,
  слизни и ключ проекта в нижнем регистре), обязан совпасть с remote. Так проверяется и
  SSH-хост, который отличается от HTTP-хоста (`git-ssh.corp` против `bitbucket.corp`):
  после совпадения хост remote запоминается у сервера как его псевдоним, и следующие
  репозитории с него находят сервер сами.

  Это не `infra::repository_identity::canonicalize_remote_url`, хотя задача похожа: та
  называет папку индекса и потому порт сохраняет, а `/scm/` не снимает — на шаге пробы №5
  она своё же сравнение провалила бы. Свести две нормализации в одну — отдельная работа,
  не эта фича.

Отвергнуто: эвристика по имени хоста (`bitbucket` в адресе) — на self-hosted её нет вовсе;
проба каждого remote автоматически — запрос на любой хост при открытии папки, без ведома
пользователя.

### 2. Только Data Center, API 1.0 (`/rest/api/latest`)

Cloud — другой API (`api.bitbucket.org/2.0`), другая авторизация, другая модель ревьюеров.
Один адаптер под то, чем пользуются. Trait `CodeHost` в `domain/` нужен ради тестового
двойника сервиса; Cloud, GitLab или Gitea станут второй реализацией, если понадобятся (решение 9).

Запросы этапа 1:

| Что | Запрос |
|---|---|
| PR ветки | `GET …/pull-requests?at=refs/heads/{branch}&direction=OUTGOING&state=OPEN` |
| Можно ли мержить | `GET …/pull-requests/{id}/merge` → `canMerge`, `conflicted`, `vetoes[]` |
| Сборки | только устаревший `GET /rest/build-status/latest/commits/{sha}`. Новый `…/commits/{sha}/builds` на 8.19.26 отвечает 400 «Please specify a non-blank key» — он спрашивает одну сборку по ключу, а не список, — поэтому он не зовётся вовсе (BB-2), а не «пробуется с откатом» |
| Approve | `PUT …/pull-requests/{id}/participants/{userSlug}` `{status: APPROVED \| UNAPPROVED}` |
| Merge | `POST …/pull-requests/{id}/merge?version={v}` — стратегия по умолчанию репозитория |
| Create | `POST …/pull-requests` с `fromRef`/`toRef`; цель по умолчанию — default branch репозитория |

`version` у PR — оптимистическая блокировка: merge по устаревшей версии получает 409, и
полоска перечитывается, а не повторяет запрос.

### 3. Токен — HTTP access token (Bearer), запечатан как ключи провайдеров

Personal HTTP access token Data Center, заголовок `Authorization: Bearer`. Права: `REPO_READ`
на чтение и approve, `REPO_WRITE` на create и merge — форма говорит об этом, а 401/403 на
кнопке объясняются этим же текстом. Хранилище — `code_hosts.enc` по образцу
`mongo_store`: окно видит адрес, псевдонимы хостов и «токен задан», но не сам токен.

Отвергнуто: логин и пароль (basic auth) — пароль от SSO в файле; OAuth — нужна регистрация
приложения админом сервера.

### 4. Свежесть: опрос в бэкенде, пока полоска на экране — с пометкой `ponytail:`

`AGENTS.md` запрещает таймер, который переспрашивает бэкенд, — но здесь переспрашивать надо
внешний сервер, а он ничего не скажет сам: вебхуку нужен адрес, до которого Bitbucket
достучится, а у десктопа его нет. Поэтому:

- Опрашивает **бэкенд**, как `infra/background.rs` и `services/mcp_servers.rs`: команда
  `pull_request_watch(root)` / `pull_request_unwatch`; с BB-8 хук живёт в App и наблюдает,
  пока функция включена и папка открыта — одно чтение кормит и полоску, и кнопки под
  ответом. Раз в 30 с, раз в
  10 с, пока есть сборка `INPROGRESS`. Снимок сравнивается с прошлым, и событие
  `pull-requests:changed { root }` уходит только при разнице — фронтенд перечитывает, как
  везде. `ponytail:` у таймера: потолок — нагрузка на сервер при многих окнах, выход —
  вебхук через relay, если он когда-то появится.
- Сразу, без ожидания тика: при монтировании, после любой кнопки, по ручному Refresh и при
  изменении `.git` (`onGitChanged`) — но только когда сдвинулось то, что мог узнать сервер.
  Это решает бэкенд (`pull_request_git_changed`): remote как записан, ветка и куда указывают
  её копии в `refs/remotes/*` — их двигают push и fetch. Локальный коммит, `git add` и
  `git status` редактора меняют `.git`, но серверу ничего не говорят и запросов не стоят.
  `onFolderChanged` не годится: он приходит на каждое сохранение файла.
- Фронтенд не опрашивает ничего — тест `polling` в `architecture.test.ts` остаётся без
  исключения.

Скорость одного чтения — решено 2026-11-19, после жалобы «долго грузится». Опрос тут ни при
чём: Overview читает сразу. Чтение было пятью запросами подряд (ветка по умолчанию, коммит
ветки, PR, merge check, сборки), каждый — с новым соединением и TLS-рукопожатием, а строка
пустовала до последнего ответа. Теперь:

- строка открывается с последним чтением этой папки (`pull_request_last`, из памяти
  сервиса), пока сервер спрашивается заново; неудачное чтение для этого не хранится;
- клиент держит один `ureq::Agent` на адрес и сертификат, и запросы одного чтения идут по
  соединениям его пула, а не открывают по новому: холодное чтение — два рукопожатия (по одному
  на запрос пары), не пять. Между чтениями соединение не доживает: ureq закрывает простаивающее
  через 15 с, а опрос — раз в 30 с;
- запросы идут тремя раундами, каждый — после предыдущего: ветка по умолчанию с коммитом,
  PR со сборками, merge check с замечаниями и «кто я» (замечания добавлены в BB-8). Чтение
  стоит самого медленного в раунде — обычно merge check,
  который Bitbucket считает у себя, — а не суммы.

**Не проверено:** насколько быстрее на живом сервере — замеров нет.

### 5. Место — строка под веткой в Overview, а не своя страница

Решено 2026-11-19, после BB-4: PR — про ветку, а ветка видна в Overview, в карточке Changes.
Там же PR и стоит — строкой под веткой. Вкладка Changes снова только про файлы и коммит.
Сначала в BB-4 была полоска над списками Changes. Отвергнута: она была крупнее того, что
говорит, и стояла не там, где пользователь смотрит на ветку. Отдельная страница со всеми
PR репозитория — другая задача (вне плана).

Под веткой — две строки. Первая — последняя сборка коммита ветки, своей строкой: что она
делает словами («Build in progress», «Build passed», «Build failed», «Build status unknown»)
и значок справа. Полное имя — в подсказке, клик открывает её страницу.

Последняя — это самая новая по `dateAdded`, когда сервер принял статус (решено 2026-11-19).
Пример: одна сборка собрана, следующая идёт — показывается та, что идёт. Сборка без даты
старше любой датированной. Среди равных — идущая, потом последняя в ответе сервера. Ускоренный
тик наблюдателя (решение 4) тоже смотрит только на последнюю. Статус «in progress», брошенный
умершим прогоном Jenkins, иначе держал бы опрос раз в 10 с навсегда.

Вторая — PR, по образцу Claude; вид утверждён на стенде 2026-11-19. Две
строки с шагом 8px:

- заголовок, справа «⋯» (`ChatMenu`: Approve/Unapprove, Convert to draft; нечего
  предложить — «⋯» нет);
- «1/2 approved · Ready to merge» мельче и бледнее — ревью и то, можно ли его влить, одной
  строкой. Ни номера, ни имени репозитория в строке нет: оба только обрезали её — папка и так
  открыта, — и оба в подсказке строки (`tax-api #153`, решено 2026-11-24). Метка «Draft» у
  черновика, «needs work», если кто-то так сказал. «1/2 approved» — кнопка: по клику рядом
  открывается поповер со списком ревьюеров (решено 2026-11-24).

Можно ли влить — словами в той же строке и цветом иконки в её конце: «Ready to merge»
(зелёная иконка merge), «Cannot merge yet» (жёлтая «!», причины в подсказке), «Not ready for
review» (серый пунктирный круг). Иконка — в том же столбце, что иконка сборки: две строки
вместо трёх (решено 2026-11-24).

Под ними — ряд кнопок: следующего шага («Mark ready» у черновика, «Merge», пока сервер
разрешает) и «Open in Bitbucket» — страница самого PR кнопкой рядом с шагом, а не пунктом
«⋯» (решено 2026-11-24). По клику на заголовок блок раскрывается: автор и цель и причины, по
которым нельзя мержить. Ревьюеров там нет — они в поповере у «1/2 approved». Ревьюер — по
одному в строку: иконка, имя, статус словом справа («approved» зелёным, «needs work» жёлтым,
«not yet» серым), логин в подсказке. Сначала те, кто держит: needs work, потом not yet, потом
approved. После пяти остальные — за «N more»; шесть показываются все, потому что «1 more»
заняло бы ту же строку.

Черновики — с Data Center 8.18 (`draft` в PR). Сервер старше поля не шлёт, и всякий PR там
готовый — и «Convert to draft» ему не предлагается: `draft` в домене — `Option<bool>`, `None` у
такого сервера (ревью BB-5). «Mark ready» и «Convert to draft» — `PUT …/pull-requests/{id}` с изменённым `draft`.
Обновление берёт PR целиком: поле, которого нет в теле, не «без изменений» — пропущенные
ревьюеры снимаются, а описание стирается. Поэтому клиент сначала читает PR с сервера и
отправляет его же, поменяв только `draft`, с `version`, который видел пользователь
(устаревший — 409, как у Merge). Подтверждения нет: шаг обратим из того же меню. Create
открывает и черновик — переключатель в диалоге; `draft` уходит в тело только тогда, чтобы
сервер старше 8.18 не получал незнакомое поле. Цель — список локальных веток папки
(`git_branches`), ветка по умолчанию первой: туда PR и идёт. Ветка, из которой PR, не
предлагается — PR в себя не бывает, — а не прочитанную можно вписать руками: ветку, созданную
на сервере после последнего fetch, локальный git не знает (решено 2026-11-24). Читает её панель Overview (`OverviewPane`), пока она на экране. Сам
`OverviewPanel` только ставит её под веткой и вне репозитория её не показывает.

Состояния:

- Функция выключена, нет remote или нет ветки — ничего.
- Remote не сопоставлен серверу — «Connect Bitbucket…» (форма с подсказками из решения 1).
  Кроме `github.com`, `gitlab.com` и их поддоменов: Bitbucket Data Center там не бывает, и
  предложение было бы шумом в каждой такой папке.
- Ветки нет на сервере — ничего: PR открывать не из чего.
- Ветка есть, PR нет — строка сборки, если она есть, и «Create pull request…». На ветке по
  умолчанию (`defaultBranch` сервера) — только сборка: PR из неё в неё же не бывает (2026-11-19).
- PR есть — он.
- До сервера не достучаться — нет имени, маршрута, ответа вовремя (`CodeHostError::Unreachable`,
  например без VPN) — ничего, только ветка (`PrStrip::Unreachable`, решено 2026-11-19).
  Недостижим только тот, до кого не дошло ни байта: ureq сказал `HostNotFound`, `Timeout`,
  `ConnectionFailed` или ошибку ввода-вывода вида «отказано», «нет маршрута», «время вышло».
  Всё, что сервер прислал в ответ, — TLS-alert, оборванный ответ — `Network`, и показывается
  как отказ ниже (ревью BB-5).
  Причина тут не новость: пользователь знает, что он не в сети, а строка с ошибкой стояла бы
  в каждой папке. Вернётся сервер — наблюдатель увидит перемену и строка появится сама.
- Сервер ответил, но не тем — отказ токена, сертификат, 5xx — последний снимок серым, под
  ним причина и кнопка перечитать: тут пользователю есть что сделать.

Серверы добавляются в шторке самой функции в Catalog, под «Turn off», пока она включена
(`CodeHostServers`) — решено 2026-11-19. Сначала они были разделом Settings → Bitbucket,
который появлялся только с включённой функцией: включить в Catalog, потом искать раздел в
другом окне — длинный путь. Теперь включил — и список с «Add server» тут же. Второй путь —
«Connect Bitbucket…» под веткой — остаётся. Сообщения об ошибках токена, сертификата и
адреса отправляют в Catalog → Pull requests.

Кнопки Push нет — решено 2026-11-14. Push делает пользователь или агент.

### 6. Кнопка — только когда она что-то сделает, и причина, если нет

Решено 2026-11-19: кнопка, которую нельзя нажать, — шум. Поэтому показывается только то,
что сработает:

- Approve — пока пользователь токена может одобрить; Unapprove — пока он одобрил. У автора
  нет ни той, ни другой: сервер всё равно откажет.
- Merge — только пока сервер разрешает (`canMerge`). Иначе вместо кнопки — причины:
  `vetoes[].summaryMessage` и «conflicts» как есть. Это ровно то, что показывает
  веб-интерфейс Bitbucket. Проба подтвердила: строки вето — готовые фразы сервера, а не наш
  текст, и приходят они на английском.
- Refresh — только после неудачного чтения: в остальное время строку держат свежей
  наблюдатель и события.
- Open — всегда у открытого PR: `openExternal` на `links.self`
  (`…/projects/{KEY}/repos/…/pull-requests/{id}`; ключ проекта там в верхнем регистре, а в
  пути API — в нижнем, так что регистр сравнивается только при нормализации).

- Mark ready — только у черновика, Convert to draft — только у готового. Кто вправе — решает
  сервер (автор с чтением или кто угодно с записью); отказ приходит сообщением.

Merge и Create — через `Modal` с подтверждением: действие уходит на сервер и кнопкой не
отменяется.

### 7. Свой CA у каждого сервера

Решено 2026-11-14: сертификаты нужны. Сервер хранит `trusted_cert_pem`, как провайдер
(`domain/settings.rs`), и клиент строит агент через `http_agent::build_agent` с ним — PEM
**заменяет** публичные корни для этого сервера и ни для кого больше. Проба без токена из
решения 1 идёт тем же агентом, поэтому поле сертификата в форме подключения стоит до кнопки
проверки: без него проба на внутренний сервер падает на TLS, и ошибка говорит «добавьте
сертификат», а не «это не Bitbucket».

В форме — тот же виджет, что у провайдера: `Certificate` выносится из `ProviderSettings.tsx`
в свой компонент со своим CSS (используется из двух мест). Сертификат пользователь берёт
сам — из файла или вставкой; встроенный корень AlfaGen остаётся исключением одного
провайдера и сюда не тянется (решено 2026-11-14).

Отвергнуто: системное хранилище сертификатов macOS/Windows — оно у каждого своё, и
приложение уже держит доверие на агенте, а не глобально (`http_agent.rs`).

### 8. Агент читает PR и сборки — отдельным инструментом, только чтение

Решено 2026-11-14: отдельный пункт плана, этап BB-6. Инструмент `pullRequestStatus { branch? }`
отдаёт то же, что видит полоска: PR ветки (по умолчанию текущей), ревьюеров и их решения,
сборки HEAD-коммита с именами, состояниями и ссылками, `canMerge` и вето. Логов сборок в
Bitbucket нет — они в CI; агент получает ссылку и может прочитать её `webFetch`, если CI
отдаёт страницу.

Только чтение: мержить и approve агент не может — это кнопки человека; создать PR он может с
BB-7 отдельным мутирующим инструментом (решение 10). Поэтому этот инструмент
немутирующий и предлагается в Agent и в Analyst; принадлежит функции `pull-requests` и выключен
вместе с ней; не грузится сразу (`loads_up_front` — нет), находится через `toolSearch`.
Читает он через тот же сервис, что и полоска: одна правда, один токен, тот же отказ, если
remote не сопоставлен серверу.

Отвергнуто: отдать агенту `runCommand` с `curl` — токен пришлось бы показать модели.

### 9. Снаружи — нейтральные имена, Bitbucket — только в адаптере

Решено 2026-11-14. Общий механизм под любой хост сейчас не строится: общее у хостов —
только то, что видит пользователь (PR ветки, ревьюеры, CI, можно ли мержить, четыре кнопки),
а внутри у каждого своё — распознавание сервера, две системы CI у GitHub против pipeline у
GitLab и build status у Bitbucket, approve без unapprove у GitHub, свои стратегии merge.
Модель, придуманная по одному хосту, при втором всё равно перекроится; правильная появится
со вторым настоящим адаптером (`AGENTS.md`: слой — под реальную вторую реализацию).

Но то, что потом переименовывается миграцией или ломает старые данные, называется
нейтрально сразу — это ничего не стоит:

| Было | Стало | Почему сейчас |
|---|---|---|
| функция `bitbucket` | `pull-requests` | id — ключ в `settings.json`; переименование — миграция |
| инструмент `bitbucketPr` | `pullRequestStatus` | имя видят модель, лог вызовов и старые чаты. Не `pullRequest`: так уже называется вид `offer`, и модель их спутает |
| канал `bitbucket:changed` | `pull-requests:changed` | имя закреплено тестом и копией во фронтенде |
| `bitbucket_servers.enc`, `SecretPurpose::BitbucketServers` | `code_hosts.enc`, `SecretPurpose::CodeHosts` | файл и назначение ключа — на диске у пользователя |
| `BitbucketApi`, `BitbucketError`, `BitbucketEventSink` | `CodeHost`, `CodeHostError`, `PullRequestEventSink` | trait нужен и так — ради двойника; имя ничего не стоит |

Bitbucket остаётся в одном месте: `infra/bitbucket_client.rs` (пути API, JSON → нейтральный
снимок) и распознавание сервера в форме. Скрипт пробы — тоже его.

Одно исключение, и оно в домене: **форма адреса remote** (`/scm/`, контекстный путь, ssh с
портом, `~user`) разбирается в `domain/code_host.rs`. Она нужна домену дважды — чтобы заполнить
форму подключения и чтобы по хосту найти сервер, — и без I/O; вынести её в адаптер значило бы
потянуть сеть туда, где сейчас чистая функция. Всё, что дальше формы адреса, — пути API и
JSON — остаётся в адаптере.

Чего нет: поля `kind` у записи сервера и перечисления хостов с одним вариантом. Второй хост
добавит `kind` с `#[serde(default)]` = Bitbucket, и старый файл прочтётся как был. Нет и
реестра провайдеров, и общего «распознать любой хост».

### 10. Образец — Claude Code с GitHub: PR — общий у человека и агента

Решено 2026-11-15. В Claude Code PR — не только панель: агент создаёт его сам (`gh pr create`),
читает его состояние одним инструментом, приложение следит за CI и ревью и превращает событие в
работу агента — кнопкой (Fix CI, Address comments, Resolve conflicts) или само, если включён
Auto-fix. Агент при этом CI не опрашивает: следит приложение. Здесь — то же, с Bitbucket вместо
GitHub:

| Claude Code (GitHub) | Здесь (Bitbucket Data Center) | Этап |
|---|---|---|
| Панель PR: номер, состояние, draft, проверки, решение ревью, mergeable | Строка под веткой в Overview (решение 5): PR, ревьюеры, сборки, `canMerge` с вето, `conflicted` | BB-3, BB-4 |
| `get_status` — состояние PR сессии, имена упавших проверок | `pullRequestStatus` — то же: PR текущей ветки, сборки по имени и состоянию, вето, конфликт | BB-6 |
| Агент создаёт PR через `gh`, кнопка `create_pr` после хода | Готовая кнопка `offer { kind: "pullRequest" }` ведёт не в `runCommand`, а в инструмент `pullRequestCreate { title, body?, target?, draft? }` — мутирующий, через карточку одобрения, только в Agent; ветка и сервер — от папки, как у полоски | BB-7 |
| Fix CI | **Нет** (решено 2026-11-15): сборка идёт в Jenkins, Bitbucket о ней только уведомлён — ключ, имя, состояние, ссылка, короткое описание и, с 7.14, счёт тестов. Ни лога, ни имён упавших тестов; Jenkins внутренний и с авторизацией, `webFetch` локальную сеть не открывает. Агенту нечего дать, кроме «упала, вот ссылка» | — |
| Resolve conflicts, Address comments — кнопки | Те же кнопки на полоске и под ответом агента: каждая отправляет в чат папки готовое сообщение (конфликт с целевой веткой; список замечаний), как Fix после ревью (`43-single-loop.md`) | BB-4, BB-8 |
| Замечания ревьюеров | Чтение комментариев PR и незакрытых задач (`…/pull-requests/{id}/activities`, blocker-комментарии) — новый запрос, в пробе его не было: сначала проба | BB-8 |
| CI monitor и Auto-fix: приложение будит агента | Наблюдатель BB-3 различает переходы (появился конфликт, новое замечание; упавшая сборка — нет, см. Fix CI) и при включённом Auto-fix у чата начинает ход сам. Хода, начатого приложением без пользователя, в Kibo ещё нет — это новый механизм | BB-9 |
| Auto-merge | Merge сам, когда `canMerge` стал истинным, — вне плана, пока не попросят | — |
| `gh` для всего остального (diff, чужие PR, поиск) | Установленный Bitbucket MCP: остаётся для глубокой работы агента. Этот план не заменяет его и не дублирует — у него нет полоски, наблюдателя и привязки к ветке, у нас нет диффа и чужих PR | — |

Агент по-прежнему не мержит и не approve'ит — это кнопки человека, как в Claude Code merge —
кнопка, а не шаг агента.

## Нарезка

Каждый этап — отдельный коммит с тестами и мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)).

**BB-0. Проба — без кода приложения.** Решения 1–4 и 7 держатся на том, как отвечает
настоящий сервер, а документация описывает последнюю версию Data Center, не ту, что стоит у
пользователя. Поэтому до первой строки кода — проба на живом сервере, скриптом
`scripts/bitbucket-probe.sh`.

*Что нужно.* Клон репозитория, чей `origin` на этом сервере; ветка с открытым PR (лучше
— с идущей или прошедшей сборкой); HTTP access token
(Profile → Manage account → HTTP access tokens) с правом **Repository read** — для пробы
записи не нужно; если сервер за корпоративным CA — его корень в PEM (Связка ключей →
сертификат → Экспорт в `.pem`, или у администраторов).

*Как запустить.* Из корня клона: `scripts/bitbucket-probe.sh feature/ветка-с-pr`, с
`BITBUCKET_CA=путь/к/root.pem`, если CA нужен, и `BITBUCKET_URL=https://…`, если базовый
адрес не выводится из remote (SSH-remote или веб на другом хосте). Токен скрипт спрашивает
без эха, в историю shell и в файлы он не попадает. Только `GET`: на сервере ничего не
меняется. В конце — блок SUMMARY, его вставить сюда, в «Результаты пробы».

*Что проверяется и что какой ответ решает:*

| # | Проверка | Ответ, который меняет план |

он отменил. Проба на заглушке (`python3` HTTP-сервер с ответами из документации,

**BB-1. Домен — сделано.** Разбор remote (`/scm/`, контекстный путь, SSH с портом, `~user` —
личные репозитории), каноническая форма адреса для сверки с `links.clone`, подсказка базового
адреса, выбор сервера по адресу remote, потом по хосту и псевдониму, правила кнопок, разница
снимков. Тесты: все формы remote из BB-0; remote, не подходящий ни одному серверу, не
выбирает «первый»; автор не может approve; merge закрыт при `conflicted` или вето;
одинаковые снимки — не изменение. `src-tauri/src/domain/code_host.rs`.

**Мутации: 26, все пойманы.** Семнадцать в первом прогоне (снятое требование `/scm/`, ключ
проекта и слизень без нормализации, `.git` в имени, порт в базовом адресе, «первый настроенный
сервер», псевдоним без сверки хоста, автор с Approve, `vetoes` без `conflicted`, `differs`
всегда `true`, последняя строка причины под Merge, регистр хоста и псевдонима) и девять после
правок по ревью (credentials в тексте ошибки, `http` в подсказке адреса, первый из двух
серверов на одном хосте, Approve при неизвестном пользователе, слизень в другом регистре,
`.GIT`, порт внутри хоста, живой Merge, выключенный устаревшим вето).

**Что нашло ревью и что с этим сделано.** Три настоящие находки. Адрес в тексте ошибки нёс
credentials из clone URL — теперь вырезаются, потому что этот текст доходит до окна, а через
инструмент агента и до лога вызовов. Сервер выбирался по одному хосту, и два инстанса на одном
хосте путались — теперь сначала сравнивается адрес, который подсказывает сам remote, а если на
хост отвечают несколько — не выбирается ничего. `can_approve` верил пользователю, которого ещё
не прочитали, — теперь без него кнопки нет, а слизни сравниваются без учёта регистра.
Отклонено: свести эту нормализацию с `infra::repository_identity::canonicalize_remote_url` —
у той другая работа (имя папки индекса: порт сохраняет, `/scm/` не снимает), и это отдельная
правка вне этапа; вместо этого решение 1 назвало нужную функцию.

**Не проверено:** `bun run tsc --noEmit` и `bun test` — фронтенд в этапе не тронут.

**BB-2. Хранилище, клиент и трейт — сделано.** Трейт `CodeHost` в `domain/code_host.rs` (четыре
чтения снимка и три действия) — его берёт двойник в тестах BB-3; его реализация —
`infra/bitbucket_client.rs` (`Bitbucket`) на `http_agent` с PEM сервера. `code_host_store` по
образцу `mongo_store`: `code_hosts.enc` под `SecretPurpose::CodeHosts`, окну — адрес, псевдонимы,
сертификат и «токен задан». Тесты: круг записи и чтения запечатанного списка; пустое поле токена
не стирает сохранённый; «файл не открылся» ≠ «ничего не сохранено»; файл не содержит токена в
открытом виде; разбор ответов пробы (PR, merge, сборки, ветки, default branch, clone links);
401/403/409 → `Unauthorized`/`Forbidden`/`Conflict`; `http` вне этого компьютера отклоняется до
запроса; редирект не сопровождается; TLS-отказ — `CodeHostError::Tls`; клиент с PEM доверяет
серверу за своим CA и не доверяет без него.

**Мутации BB-2: 18, все пойманы** — 9 на код и 9 на правки по ревью.

**BB-8. Замечания ревьюеров и кнопки-задачи — сделано.** Проба прошла 2026-11-23 (ниже, «Проба BB-8»):
чтение замечаний — `activities` (события COMMENTED несут комментарий с `threadResolved`,
`severity`, `state` и якорь `commentAnchor` с файлом и строкой) плюс `blocker-comments`
(задачи); `/comments` отвергнут — он покаментный по файлу (400 без `path`).

Решения этапа:

- Замечание — `Comment` в домене: id, автор (slug и имя), текст, файл и строка (если есть),
  `task` (задача против комментария), `resolved` (тред решён / задача RESOLVED). В снимке —
  все прочитанные замечания с флагом; открытые считает домен (`open_comments`), правило одно.
  Ответы (вложенные `comments[]`, `parent`) — часть треда, не отдельные замечания; PENDING
  (черновики ревью) и удалённые не читаются. Из событий COMMENTED берётся последнее на
  комментарий (правка несёт новый текст), DELETED вычёркивает. Поток идёт от новых к
  старым; при равных `createdDate` новее событие с большим id — сравнение парой
  `(createdDate, id)`, не зависящее от порядка страниц (ревью BB-8).
- Кнопки ведут себя **как Fix после ревью**: кладут готовый текст в поле ввода (`giveBack`),
  отправляет пользователь сам — текст с замечаниями ревьюеров он должен видеть перед
  отправкой. Отвергнуто: немедленная отправка как у офферов — ход начинался бы из Overview
  без просмотра текста.
- Места: полоска PR (своя строка кнопок под карточкой) и под ответом агента в чате. Для
  второго `usePullRequest` поднимается в App — одно чтение и один наблюдатель на папку;
  наблюдатель живёт, пока функция включена и папка открыта (раньше — только пока Overview
  на экране). Отвергнуто: второй экземпляр хука в чате — два наблюдения одной папки.
- Resolve conflicts видна только при `conflicted`, Address comments — только при открытых
  замечаниях; упавшая сборка кнопок не даёт (Fix CI нет, решение 10). Текст Resolve называет
  целевую ветку; Address несёт замечания с местом, автором и текстом, до 20 штук, остальные —
  счёт и `pullRequestStatus` (модель дочитает инструментом).
- `pullRequestStatus` получает текст **всех** открытых замечаний с файлом и строкой:
  кнопка несёт первые 20 и шлёт модель за остальными сюда — потолок здесь сделал бы
  обещание ложным (ревью BB-8). Описание инструмента говорит о них.
- Activities читается страницами по 100 с потолком 10 страниц (`ponytail:` очень длинная
  история PR теряет древнейшие комментарии; выход — чтение комментариев по id).

Тесты: каждая кнопка видна только при своём состоянии (`conflicted`, открытые замечания);
текст сообщения несёт цель конфликта и замечания с местом; решённые замечания не попадают;
упавшая сборка кнопки не даёт; разбор событий (правка, удаление, ответ, PENDING, задача,
два события одной миллисекунды в любом порядке).

Сделано 2026-11-23. Замечание — `Comment` в домене; снимок несёт все прочитанные, открытые
считает `open_comments`. Клиент читает activities страницами по 100 (потолок 10, `ponytail:`)
и blocker-comments; последнее событие на комментарий — по паре `(createdDate, id)`,
DELETED вычёркивает, PENDING, ответы и задачи-в-потоке не считаются; порядок стабилен
(по id) — иначе каждый опрос был бы переменой. Сервис спрашивает замечания в третьем
раунде вместе с merge check и «кто я» (`three`); новое замечание и решение треда —
перемена для наблюдателя. `pullRequestStatus` перечисляет все открытые с местом и автором.
Фронт: `prTasksOf` и тексты запросов в `pullRequestView`, кнопки на полоске и `PrTaskCards`
под ответом (только при `done`), нажатие кладёт текст в поле (`giveBack`); `usePullRequest`
поднят в App — одно чтение и один наблюдатель на папку, пока функция включена.

Тесты: домен — открытые обоих видов, решённый тред и новая задача — перемена снимка;
клиент — фикстура пробы в порядке сервера (якорь, общий, решённый, PENDING, ответ,
задача, правка, удаление, одна миллисекунда в обоих порядках), пагинация, потолок,
стабильный порядок; сервис — снимок, раунды, без PR и без ветки не спрашивается,
наблюдатель говорит о новом замечании и решении; инструмент — место, решённые не в
списке, весь хвост перечислен; фронт — `prTasksOf`, тексты, кнопки полоски по состоянию,
карточки под ответом, упавшая сборка без кнопок.

**Мутации: 26, все пойманы** — 17 на бэкенд и 7 на фронт в первом прогоне (снятые
проверки DELETED/PENDING/ответов/задач-в-потоке, первое событие вместо последнего,
потерянные флаги решённости и якоря, перевёрнутый порядок, снятая пагинация и поднятый
потолок, обнулённый счётчик, выпавшие из снимка замечания, решённые в тексте инструмента,
подменённая цель конфликта, кнопка не по своему состоянию, карточки во время хода),
2 на правки по ревью.

**Что нашло ревью и что с этим сделано.** Две находки, обе исправлены. Кнопка обещала
дочитать хвост замечаний инструментом, а инструмент резал список на 10 — раньше
кнопкиных 20, тот же порядок: хвост был недостижим. Потолок инструмента убран — он
перечисляет все открытые, тест охраняет хвост. При равных `createdDate` в newest-first
потоке старое событие затирало новое — теперь сравнение парой `(createdDate, id события)`,
не зависящее от порядка страниц; тест в обоих порядках, фикстура развёрнута в порядок
сервера.

**Не проверено:** живой сервер после BB-8 — проба шла до кода; решённый тред, задача
и ответ на комментарий на PR пробы отсутствовали — их форма по документации REST;
`agent_bench` — нужен ключ провайдера; в запущенном приложении кнопки не смотрелись.

**BB-9. Auto-fix: приложение будит агента — отложен** (решено 2026-11-23, открытый вопрос 6:
сначала пожить с кнопками BB-8). Переключатель у чата. Наблюдатель отличает переход
от состояния: появился конфликт, пришло новое замечание — один раз на переход, не на каждый тик;
упавшая сборка хода не начинает. При включённом Auto-fix и чате без идущего хода приложение начинает
ход с тем же сообщением, что у кнопки; идущий ход не прерывается — событие ждёт его конца.
Новый механизм: ход, начатый не пользователем, — с потолком (не больше N подряд без
пользователя, как в Claude Code), чтобы ревьюер, отвечающий на каждый пуш, не жёг токены по кругу. Тесты на
двойнике: один переход — один ход; тот же снимок — ни одного; потолок останавливает цикл;
выключенный Auto-fix — только кнопка.
