# Вход через OAuth для MCP-серверов по HTTP

План (не начат). Продолжение [17-mcp-http.md](17-mcp-http.md): там OAuth отложен, и сервер,
который требует входа, отвечает `401` с пометкой, что вход ещё не сделан. Решения этапа 7
«Решения по MCP» (`06-port-plan.md`) остаются в силе.

## Что говорит спецификация

Сверено с MCP 2025-11-25, раздел Authorization. Клиент получает токен так:

1. **Где сервер авторизации.** Сервер отвечает `401` с
   `WWW-Authenticate: Bearer resource_metadata="…", scope="…"`. Без адреса метаданных в
   заголовке клиент пробует `/.well-known/oauth-protected-resource/<путь>`, затем
   `/.well-known/oauth-protected-resource` (RFC 9728). В документе — `authorization_servers`.
2. **Метаданные сервера авторизации.** Поддерживать оба способа — RFC 8414 и OpenID
   Connect. Для издателя с путём порядок такой:
   - `oauth-authorization-server` со вставкой пути;
   - `openid-configuration` со вставкой пути;
   - `openid-configuration` с добавлением в конец пути.
3. **PKCE.** Нет `code_challenge_methods_supported` или в нём нет `S256` — остановиться
   (MUST).
4. **Регистрация клиента.** Рекомендуемый порядок: заранее выданный `client_id` → документ
   метаданных клиента по HTTPS-адресу (CIMD) → динамическая регистрация (DCR, RFC 7591) →
   спросить пользователя.
5. **Браузер** со ссылкой авторизации: PKCE S256, случайный `state`, `resource` (адрес
   MCP-сервера, RFC 8707 — обязателен), `scope`. Ответ — на `http://127.0.0.1:<порт>/callback`.
6. **Обмен кода на токены** — снова с `code_verifier` и `resource`. Приходят токен доступа
   и токен обновления; у публичного клиента токен обновления меняется при каждом обновлении.
7. **Токен** — в `Authorization: Bearer …`, в каждом запросе и только этому серверу.

Права (scope): из `scope` в ответе `401`, иначе всё из `scopes_supported`. На
`403 insufficient_scope` — повторный вход с расширенными правами.

## Предлагаемые решения (не утверждены)

- **Вход — только из вкладки MCP, не посреди хода.** Ход не может ждать браузер:
  пользователь ушёл, а таймаут вызова — 120 с. Сервер, ответивший `401`, получает
  состояние `NeedsSignIn`, в его строке — кнопка «Sign in». Инструментов у него нет, как
  у не запустившегося сейчас.
- **Регистрация клиента:**
  - заранее выданный `client_id` из записи — поле
    `oauth: { clientId, clientSecret?, callbackPort?, scopes? }` в духе Claude Code, точный
    формат сверить при реализации;
  - иначе DCR: её поддерживают почти все публичные серверы (Linear, Notion, Atlassian,
    Sentry);
  - иначе строка вкладки объясняет, что вписать в `oauth.clientId`;
  - CIMD — отложен: нужен JSON-документ по HTTPS-адресу, который мы контролируем, а
    своего сайта у приложения нет (вопрос 1).
- **Порт для ответа браузера** — свободный порт на `127.0.0.1`, выбирается при регистрации и
  запоминается вместе с ней: сервер авторизации сверяет адрес возврата с
  зарегистрированным. Порт позже занят — регистрация заново. Для заранее выданного клиента
  порт — из `callbackPort`.
- **Хранение токенов** — `~/.laika/mcp_oauth.enc`: тот же `secret_store`, тот же мастер-ключ
  из связки ключей, новое назначение `SecretPurpose::McpOAuth`. Ключ записи — адрес
  сервера, не имя: переименование вход не теряет, смена `url` требует войти заново, и токен
  не уйдёт на чужой адрес. В `mcp.json` токены не попадают, модель и лог их не видят.
- **`Authorization` в `headers` важнее OAuth.** Пользователь вписал токен сам — вход не
  предлагается.
- **Обновление посреди хода.** На `401` при наличии токена обновления — обновить один раз и
  повторить этот же запрос. Правило «упавший вызов не повторяется» не нарушено: `401`
  значит, что сервер запрос не выполнял. Не обновилось — сервер в `NeedsSignIn`, вызов
  возвращает модели понятную ошибку.
- **Безопасность:**
  - `state` сверяется;
  - PKCE S256 обязателен;
  - сервер авторизации — только HTTPS (localhost — для тестов);
  - `issuer` в метаданных совпадает с адресом, откуда их взяли (RFC 8414);
  - слушатель — только `127.0.0.1`, одна попытка, путь `/callback`, таймаут 5 минут и
    Cancel;
  - браузер системный, через `tauri-plugin-opener`, не окно приложения.

## Шаги

### F-7.4h — чистая логика (`domain/mcp_oauth.rs`)

Без ввода-вывода:

- разбор `WWW-Authenticate` (параметры в кавычках, несколько схем);
- адреса well-known для ресурса и для издателя во всех вариантах порядка;
- канонический адрес ресурса (схема и хост в нижнем регистре, без `#` и без `/` в конце);
- выбор прав;
- PKCE: verifier и S256-challenge;
- `state`;
- сборка ссылки авторизации;
- типы метаданных, регистрации и токенов;
- `OAuthError` на `thiserror`.

Зависимости: `sha2` (уже в `Cargo.lock` через tauri-codegen), `url`/`form_urlencoded` (тоже
уже в графе); base64url для PKCE — десяток строк или `base64`. Тесты — таблицы входов и
выходов плюс вектор из RFC 7636 для S256.

### F-7.4i — сеть и хранение (`infra/mcp_oauth.rs`, `infra/mcp_oauth_store.rs`)

- Запросы к серверам авторизации на `ureq`: метаданные ресурса и сервера авторизации в
  порядке спецификации, DCR (`token_endpoint_auth_method: none`, наш адрес возврата),
  обмен кода, обновление.
- Слушатель ответа браузера: `TcpListener` на `127.0.0.1`, сверка `state`, короткая
  HTML-страница «можно закрыть вкладку».
- Хранилище: запись на адрес сервера — издатель, регистрация клиента, токены, срок действия.
- Тесты — подменные MCP-сервер и сервер авторизации на `TcpListener`, как в `mcp_http.rs`.
  «Браузер» — тестовый двойник: идёт по ссылке, подменный сервер авторизации перенаправляет
  на наш адрес возврата. Проверяется:
  - порядок обнаружения метаданных;
  - без S256 вход не начинается;
  - чужой `state` отвергается;
  - `resource` передаётся в обоих запросах;
  - `code_verifier` соответствует challenge (сервер проверяет хэш);
  - регистрация через DCR;
  - смена токена обновления.

### F-7.4j — подключение

- `HttpServer` получает источник токена: подставляет `Authorization`; на `401` обновляет
  токен и повторяет запрос один раз; иначе `McpError::NeedsSignIn`.
- `McpServerState::NeedsSignIn`: пул не запускает такой сервер ход за ходом, как `Failed`.
- Команды: `mcp_server_sign_in(name)` (асинхронная, `spawn_blocking`, отменяемая),
  `mcp_server_sign_in_cancel`, `mcp_server_sign_out(name)` (удаляет токены и перезапускает
  сервер). Браузер открывает слой команд; сервис получает порт `open_url: Fn(&str)`, без
  `AppHandle`.
- Политика данных: `mcp_oauth.rs` → `NETWORK_ALLOWED`; в `08-data-policy.md` — новый выход:
  сервер авторизации получает регистрацию клиента, код и `resource`, но не данные рабочей
  папки. Плюс браузер и слушатель на локальном порту.
- Текст ошибки `401` в `McpError::Http`: вместо «OAuth ещё не сделан» — «нажми Sign in».

### F-7.4k — интерфейс

- Строка сервера: «needs sign-in» и «Sign in»; во время входа — «Waiting for the browser…» и
  Cancel; у вошедшего — «Signed in» и «Sign out».
- Поля `oauth` в форме — возможно, достаточно JSON-редактора.
- Экран «Where your data goes»: у сервера с входом назван сервер авторизации.

## Отложено

| Что | Почему потом |
|---|---|
| CIMD | Нужен хостинг документа клиента |
| Повторный вход с расширенными правами на `403 insufficient_scope` | Сначала — ошибка с перечислением прав и кнопкой «Sign in again» с ними |
| Выбор между несколькими `authorization_servers` | Берётся первый |
| `private_key_jwt` и прочая аутентификация клиента | Кроме `none` и `client_secret_post` |

## Открытые вопросы

1. **CIMD**: отложить или завести документ клиента (например, на GitHub Pages репозитория)
   и сделать CIMD основным способом, как советует спецификация?
2. **Где начинается вход**: только кнопка во вкладке или ещё карточка в ленте хода —
   «сервер X ждёт входа, [Sign in]» — без ожидания хода?
3. **Токены**: зашифрованный файл под общим мастер-ключом (как ключи провайдеров) или
   отдельная запись в связке ключей на каждый сервер?
4. **`403 insufficient_scope`**: хватит ошибки с кнопкой «Sign in again» или повторный
   вход с расширенными правами нужен сразу?
