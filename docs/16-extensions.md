# Расширения, собираемые вместе с приложением

Исследование (реализация не начата): как сделать расширения, которые лежат в отдельной
папке, компилируются вместе с проектом и включаются/выключаются пользователем. Расширение
может дать модели новые инструменты, а окну — новые части интерфейса. Песочницы нет:
в сборку попадают только проверенные расширения.

Документ описывает, что в коде уже есть, какой контракт нужен, что придётся один раз
поменять в приложении и чего нельзя потерять. Кода в нём нет — только решения.

## Исходная точка

**Это не противоречит `01-vision.md`, но уточняет его.** §1.4 говорит: «Не делаем свой
язык плагинов. Точки расширения — MCP и skills-файлы». Речь там о расширениях, которые
пользователь ставит сам во время работы. Здесь другое: модули, которые пишет команда и
собирает в бинарник. Языка плагинов, загрузчика и ABI нет — только Rust-трейт и
TS-тип. Строку в vision стоит дополнить, когда решение будет принято.

**Две из трёх нужных механик в приложении уже есть** — их писали для MCP и skills:

| Что нужно расширениям | Где это уже сделано | Что это даёт |
|---|---|---|
| Инструменты, появляющиеся во время работы, под одним вариантом enum'а | `ToolName::Mcp` + `domain::mcp::McpTools` (`domain/tools.rs:58`, `domain/mcp.rs:288`) | Имя `mcp__<server>__<tool>`, вес на каждый вызов (`round_cost`), подтверждение по полному имени (`always_allowed_mcp`), лог только формы аргументов, фильтр по режиму в `tool_definitions_for` |
| Снимок на ход: набор инструментов не меняется между раундами | `commands/chat.rs:504–517` — skills, rules, hooks и MCP читаются один раз за ход | Выключение посреди хода подействует со следующего хода, и этот случай уже продуман |
| Включение/выключение по имени в `settings.json` | `domain::settings::OptOut` (`domain/settings.rs:201`), `skills.disabled`, `rules.disabled` | Хранилище и тесты уже есть; нужно добавить состояние «включено по умолчанию» (ниже) |
| Список с переключателями в UI | `ItemList` + `PanelItem` (`types.ts`), вкладки MCP/Skills | Строка, переключатель, причина поломки |
| Панели окна | `PANES` в `components/panes.tsx`: `{id, label, icon, dock, Component}` | Меню «⋮» в шапке чата строится из этого массива |
| Отрисовка вызова в ленте | `describeTool` в `lib/describeTool.ts`; для незнакомого имени есть запасной вариант | Вызов расширения без своего рендера всё равно показывается |

**Третьей механики нет — вызова своего бэкенда из UI расширения.** Команды Tauri
регистрирует макрос `generate_handler![]`: список статический и лежит в `lib.rs`.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где лежат расширения | `extensions/<id>/` в корне репозитория; внутри Rust-крейт (`Cargo.toml`, `src/`) и, если нужен, UI (`ui/`) | Одна папка на расширение, как просили. Не внутри `src-tauri/`: Vite не следит за `**/src-tauri/**` (`vite.config.ts`), и UI расширения там лишился бы HMR |
| Внешний API | Отдельный крейт `crates/extension-api`: трейт `Extension` и DTO. Зависит только от `serde`, `serde_json`, `thiserror`. Для UI — файл с TS-типами (`src/extensions/api.ts`) | Без отдельного крейта никак: приложение зависит от расширений, поэтому расширение не может зависеть от приложения (цикл). В API нет `tauri::` — расширение оказывается на месте services/infra, а слой команд остаётся единственным, кто знает про окно (правило из AGENTS.md) |
| Сборка | Cargo workspace в корне репозитория: `src-tauri`, `crates/*`, `extensions/*`. Приложение подключает каждое расширение path-зависимостью | Без workspace не работает `cargo test -p <расширение>`: path-зависимость вне корня пакета не считается членом workspace. `tauri dev` отслеживает изменения в зависимых членах workspace (Tauri CLI 2.10+), так что правка расширения пересобирает приложение |
| Регистрация | Явный список: одна строка в Rust-реестре и одна в TS-реестре на каждое расширение. Тест сверяет список папок `extensions/*` с обоими реестрами | Cargo не умеет сам добавлять зависимости по glob. `import.meta.glob` из Vite не работает в `bun test` (проверено на Bun 1.3.9: `import.meta.glob` — `undefined`), а реестр импортируют тесты. Тест-сверка — тот же приём, что `ToolName::ALL` + `all_is_complete` |
| Включение | Во время работы, в `settings.json` → `extensions: { "<id>": true/false }`. Нет ключа — действует `enabledByDefault` из манифеста | Нужны оба направления: расширение, выключенное по умолчанию, пользователь «включает дополнительно»; включённое по умолчанию — выключает. `OptOut` хранит только выключенные и эту разницу не выразит. Cargo features не нужны: в сборку попадает всё, решает переключатель |
| Кто хранит флаг | Бэкенд, как все настройки | Бэкенд фильтрует инструменты для модели, и источник правды должен быть один. Окно перечитывает список после переключения — событие не нужно, переключатель только в одном месте (правило «reuse a signal before adding one») |
| Инструменты | Своя ветка по образцу MCP: `ToolName::Extension`, префикс `ext__<id>__<tool>`, `ToolCall::Extension { name, arguments }` | Контракт «добавить инструмент = пять мест» остаётся для встроенных, а расширение добавляет инструменты без правок ядра. Префикс нужен, чтобы `from_wire_name` оставался чистой функцией без реестра, а окно узнавало владельца вызова по имени |
| Чем расширение отличается от MCP | Расширению доверяют: оно само объявляет `mutating` и `weight` для каждого инструмента | MCP всегда считается мутирующим и доступен только в Agent, потому что подсказкам сервера спецификация не доверяет. Инструмент расширения, который только читает, должен работать в Plan/Ask и не показывать карточку подтверждения |
| Команды для UI расширения | Одна общая команда `extension_invoke(id, method, payload) → JSON` и один TS-wrapper | `lib.rs` не правится под каждое расширение. Проверка «расширение выключено → ошибка» стоит в одном месте. У расширения нет `tauri::` |
| События бэкенд → UI расширения | Пока не делаем. Когда первому расширению понадобится — sink из API, адаптированный в `commands/` в один канал `extension:event { extension, name }` как сигнал перечитать | По правилам AGENTS.md: sink, один канал на источник, событие — сигнал, а не состояние |
| Выключенное расширение и старые чаты | Рендер карточек расширения (`describe`) работает и у выключенного | Отрисовка истории ничего не запускает. Иначе старый чат после выключения выглядел бы по-другому |

## API расширения (контракт, без кода)

### Rust: трейт `Extension`

Блокирующий, `Send + Sync` — как `McpClient` и `LlmProvider`: инструменты и так
выполняются в цикле внутри `spawn_blocking`. У всех методов, кроме `manifest`, есть
реализация по умолчанию: «ничего не даёт».

| Метод | Что возвращает | Заметки |
|---|---|---|
| `manifest()` | `id`, `name`, `description`, `enabledByDefault` | `id` — `[a-z0-9-]`, он же ключ в `settings.json`, префикс имён инструментов и имя папки. Тест проверяет все три совпадения |
| `tools()` | Список `ToolSpec`: `name`, `description`, `parameters` (JSON Schema), `mutating`, `weight` | Читается один раз за ход. `mutating` решает и подтверждение, и режим: немутирующий доступен в Plan/Ask |
| `call_tool(name, args, ctx)` | `ToolOutput { text, data? }` или `ExtensionError` | `text` получает модель; необязательное `data` (JSON) уходит только в окно, для карточки |
| `invoke(method, payload, ctx)` | JSON или `ExtensionError` | Бэкенд для UI расширения |
| `prompt(ctx)` *(отложено)* | Необязательный блок для системного промпта | Место уже есть: `domain::prompt::system_messages` собирает skills/rules/plan. Добавить, когда описаний инструментов окажется мало |

**`ExtensionContext`** — всё, что расширению даёт приложение:

- корень открытой папки;
- `resolve(path)` — та же проверка «путь внутри корня», что в `services::ai_tools::resolve`.
  Песочницы нет, но и без неё расширению незачем писать свою проверку и ошибаться в ней;
- `cancelled()` — кнопка «стоп» хода; для `invoke` не срабатывает никогда;
- собственные настройки расширения: `settings.json` → `extensionSettings.<id>`, JSON,
  который расширение само разбирает через serde;
- своя папка данных `~/.laika/extensions/<id>/`.

**`ExtensionError`** — три варианта, по смыслу как у MCP: `InvalidArguments` (модель
исправит вызов), `Failed` (текст для модели), `Unavailable` (больше не звать в этом ходу).
На границе с моделью они превращаются в `ToolError`, на границе IPC — в строку.

### TS: объект `UiExtension`

| Поле | Что это | Во что встраивается |
|---|---|---|
| `id` | Совпадает с манифестом Rust (проверяется тестом) | — |
| `panes?` | `{ id, label, icon, dock, Component }` | `PANES`, меню «⋮» в шапке чата, `AsidePanel` |
| `settings?` | `{ label, icon, Component }` — раздел настроек | `SECTIONS` в `Settings.tsx` |
| `tools?` | `Record<имя инструмента, (block) => ToolDisplay>` | `describeTool`; без него — запасной вид как у MCP: `id · tool`, аргументы целиком, `text` в теле |

Панель расширения получает **узкие** props (`ExtensionPaneProps`), а не весь
`PaneContext`: `active`, `workspace`, `onNotify`, `onOpenFile`, `onAddToChat` и `invoke`,
уже привязанный к `id` расширения. `PaneContext` — внутренний тип окна, который меняется
с каждой фичей. Если отдать его расширениям, любая правка окна станет ломающим
изменением API.

Правила UI из AGENTS.md распространяются и на расширения: цвета и шрифты — из токенов
`tokens.css`, меню — через `Dropdown`, диалоги — через `Modal`, у каждого компонента
свой CSS-файл. `invoke()` вызывает только общий wrapper.

## Что один раз меняется в приложении

### Бэкенд

| Место | Изменение |
|---|---|
| Корень репозитория | `Cargo.toml` с `[workspace]`. Каталог `target/` переезжает в корень — нужно поправить `scripts/clean-build-cache.sh` и `.gitignore` |
| `domain/tools.rs` | `ToolName::Extension` + `EXT_PREFIX`; `from_wire_name` проверяет префикс; `ToolCall::Extension`, `ToolResult::Extension { text, data }`; `ToolError::ExtensionFailed/Unavailable`. `always_allowed_mcp` обобщается до «всегда разрешено по полному имени» для обоих префиксов, а не дублируется |
| Подтверждение и режим | `is_mutating` по одному имени здесь не работает: ответ даёт объявление инструмента. Вердикт подставляется из снимка хода перед гейтом, так что `ApprovalPolicy` не узнаёт о реестре. То же для `conversation_mode::offers` в `tool_definitions_for` |
| `services/llm_chat.rs` | `round_cost` берёт вес из снимка (как у MCP); `tool_definitions_for` добавляет определения расширений; `ToolDeps.extensions` |
| `services/ai_tools/` | `parse.rs` — ветка по префиксу; `model_text.rs` — `text`; `preview.rs` — `Nothing` (аргументы видны на карточке); `tools/extension.rs` — вызов |
| `domain/tool_call_log.rs` | Логировать только форму аргументов и имя ошибки, как у MCP: заранее неизвестно, что в них чувствительно |
| `services/extensions.rs` | Реестр: все собранные расширения + флаги из настроек → снимок на ход (аналог `McpTools`). Здесь же проверяются уникальность `id` и длина имён: провайдер принимает до 64 символов, `MAX_TOOL_NAME_CHARS` |
| `commands/extensions.rs` | `extensions_list`, `extensions_set_enabled`, `extension_invoke`; регистрация в `generate_handler![]`. Capability для них не нужна: это свои команды приложения, а не API плагина |
| `domain/settings.rs` | `extensions: BTreeMap<String, bool>`, `extension_settings: BTreeMap<String, Value>` |
| `commands/chat.rs` | Снимок расширений строится рядом с `skills`/`mcp` (`:504`) |

### Окно

| Место | Изменение |
|---|---|
| `types.ts` | `ASIDE_TABS` — константный кортеж, и `isAsideTab` проверяет по нему сохранённую раскладку (F-7.12). Id панели расширения — строка, известная только после чтения списка. Панель выключенного расширения, запомненная в раскладке, должна молча закрываться, а не ломать восстановление окна |
| `panes.tsx`, `AsidePanel.tsx`, `ChatPanel.tsx` | Сейчас все три импортируют `PANES` напрямую. Им нужен общий список «встроенные + включённые расширения» — его собирает `App` из хука `useExtensions` и передаёт вниз |
| `Settings.tsx` | Раздел «Extensions» со списком и переключателями (`ItemList`, `PanelItem.kind: "extension"`), плюс разделы включённых расширений |
| `describeTool.ts` | `toolLabel` и выбор рендера по префиксу `ext__` |
| `src/lib/extensions.ts` | Wrapper'ы команд; `useExtensions` читает список при монтировании и после переключения |
| `tsconfig.json` | `include` добавляет `extensions/*/ui` |

## Что нельзя потерять

- **Инструмент расширения проходит через `execute_tool`**, а не мимо: тот же гейт
  подтверждений, бюджет, хуки (`PreToolUse` матчится по полному имени), лог. Это то же
  требование, что для MCP в этапе 7: иначе появится вторая неохраняемая дверь.
- **Выключение действует на всё сразу:** модель не видит инструментов (со следующего
  хода); вызов по памяти — ошибка «unknown tool», как у ушедшего MCP-сервера; панели и
  разделы настроек скрыты; `extension_invoke` отказывает.
- **Имена инструментов — часть API расширения.** Под ними сохраняются «Always allow»,
  матчеры хуков и старые чаты. Имя, обрезанное по длине, получает стабильный хэш
  (FNV, как `tool_wire_name` у MCP), а не `DefaultHasher`.
- **Ход на паузе.** Если расширение выключили, пока висит карточка подтверждения, после
  возобновления вызов получит ошибку «unknown tool». Это приемлемо, но покрыть тестом.
- **Сторожа политики данных расширения не видят.** `data_policy.rs` сканирует только
  `src-tauri/src`, `src-tauri/Cargo.toml`, `src/` и `package.json`. Расширение с `ureq` в
  `extensions/jira/` пройдёт все тесты молча. Сторожей нужно расширить на `extensions/*`
  и `crates/*`. Сетевое расширение должно явно попасть в `08-data-policy.md` и на экран
  «Where your data goes» — сейчас там перечислены только провайдер, MCP и хуки.
  CSP окна остаётся как есть: UI расширения ходит в сеть только через свой бэкенд.
- **Лицензия.** Проект под GPL-3.0-only, а расширение собирается в тот же бинарник —
  значит, лицензия расширения должна быть с ней совместима.
- **Мутационная проверка** (`docs/11-mutation-testing.md`) распространяется и на
  расширения: `cargo test --workspace`, а мутанты — ещё и по реестру, гейту и фильтру режима.

| ⬜ | E-4 | UI: панели и разделы настроек из расширений, `ExtensionPaneProps`, раскладка, которая переживает выключенную панель, рендер карточек |

расширения с фоновым процессом добавляются, когда первое расширение попросит.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Расширение — это Tauri-плагин (`tauri::plugin::Builder`, `invoke("plugin:x\|cmd")`) | Родной механизм Tauri, но расширению придётся зависеть от `tauri::`, а это ломает правило слоёв. Плюс нужны permissions в `capabilities/*.json` и сборка схем на каждое расширение. Выключение во время работы всё равно пришлось бы проверять в каждой команде |
| Расширение как MCP-сервер внутри процесса (реализовать `McpClient`) | Ноль правок ядра, но расширение унаследует недоверие к MCP: только Agent, карточка на каждый вызов, в описании «[MCP server]», а у инструментов нет `resolve` и корня папки. Модели и пользователю это будет стоить дорого без всякой причины |
| Модули внутри крейта приложения (`src-tauri/src/extensions/`) | Проще всего, но тогда нет внешнего API: расширение видит весь `domain::` и завязывается на внутренности. К тому же UI и Rust одного расширения оказались бы в разных деревьях |
| Автообнаружение (`inventory`/`linkme`, `import.meta.glob`, `build.rs`) | Строку в `Cargo.toml` всё равно пишут руками. `import.meta.glob` не работает в `bun test`. Регистрация через секции линкера — магия ради экономии одной строки |
| Cargo features на каждое расширение | Решают вопрос «попадёт ли в сборку», а просили переключать во время работы |
| Имена инструментов без префикса | Модели читать красивее, но `from_wire_name` и окно тогда зависят от реестра, а переименованное расширение молча занимает имя встроенного инструмента |

## Открытые вопросы

- Какое расширение будет первым? От него зависит, нужны ли в E-5 события, секреты и блок
  в промпте, или их можно отложить.
- Настройки расширения — только JSON, который правят руками, или раздел настроек
  (`settings?`) обязателен для каждого расширения с настройками?
- Должны ли инструменты расширений учитываться в «Always allow» глобально или, как MCP,
  по одному инструменту? Предложение — по одному, как у MCP.
