# Ленивый индекс: много открытых папок, модель — только во время хода

План, предложен 2026-11-18; LZ-0, LZ-1, LZ-4 и LZ-6 сделаны 2026-11-18, LZ-2, LZ-3 и LZ-5 сняты (см. «Открытые вопросы», 3). Строится на [10-multi-workspace.md](10-multi-workspace.md) (F-8):
сейчас индекс есть у каждой открытой папки, каждая под наблюдением, и правка в любой из
них грузит модель эмбеддингов. Задача — держать открытыми сколько угодно папок без этой
цены. Смысловой поиск остаётся, но модель эмбеддингов грузится только тогда, когда в папке
работает агент. Сама модель при этом становится в три раза легче: токенизатор без раздутой trie (проба ниже). Работа закончена, когда фоновые папки ничего не стоят, кроме строки в
списке, а ход в любой из них ищет так же хорошо, как сейчас.

Кода в документе нет — только решения.

## Что уже есть

**Замер 2026-11-17** (`search_bench`, 93 вопроса по трём репозиториям, rerank — deepseek-flash):
эмбеддинги нужны. Без них MRR после rerank падает с 0.808 до 0.707, на русских вопросах —
с 0.728 до 0.479 (на английских разница почти исчезает: 0.849 против 0.827). Сигнал «в
папке этого нет» без них тоже перестаёт работать: слабыми помечаются 78 из 93 вопросов, у
которых ответ есть (с эмбеддингами — 27). Поэтому вопрос не в том, убирать ли их, а в том,
когда за них платить.

**Где цена на самом деле** (измерено при исследовании):

| Что | Сколько | Когда платится сейчас |
|---|---|---|
| Модель (`infra/local_embeddings.rs`) | ~320 МБ в памяти, из них ~250 МБ — дерево токенизатора; загрузка 0.35 с | При первом `embed` после выгрузки: синк любой открытой папки нашёл изменённый кусок, или поиск по смыслу. Выгружается через 10 минут без `embed` |
| Вектора папки (`EmbeddingIndex`) | ~0.4 КБ на кусок: у kibo 10 570 кусков, около 4 МБ | При открытии папки (`EmbeddingIndex::load`) |
| Наблюдение (`FileWatcher`) | FSEvents на macOS дёшев. На Linux inotify ставит watch на каждый каталог и упирается в `max_user_watches` | Всё время, пока папка открыта |
| Синк по словам (`repo_index::sync`) | Индекс kibo с нуля строится за 1.3 с, вместе с векторами за 1.9 с (release) | На каждую пачку сохранений в любой открытой папке. При запуске — первый синк всех папок (`open_index_behind`) |

Получается, что тяжёлая здесь модель, а не вектора. Она грузится из-за фоновых папок:
`git checkout` или правка в редакторе в папке, где агент сейчас не работает, всё равно
поднимает 320 МБ на 10 минут.

**Что переиспользуется:**

- `services/workspace_index.rs` — `WorkspaceIndex` с картой `open` (папка → индексатор и
  наблюдатель). Методы `open`/`close`/`searcher`/`indexer` остаются, меняется только то,
  когда они вызываются.
- `services/index_sync.rs` — `RepoIndexer::sync`: «один синк за раз, просьба во время синка —
  ещё один круг», события через `IndexEventSink`. Синк уже разделён на два прохода,
  по словам (`repo_index::sync`) и по смыслу (`embeddings.sync`). Первый можно запустить
  без второго.
- `RepoIndexer::search_meaning` уже возвращает пустой ответ и не трогает модель, когда
  ничего не эмбеддировано. `code_search` переживает chunk id, которого больше нет в
  хранилище (`load_chunk` → `Option`).
- `CodeSearchFn` (`domain/tools/args.rs`) — замыкание, которое ход получает в
  `commands/chat.rs::searcher_of`. Его же клонируют помощники
  (`services/llm_chat/helpers.rs`) и rerank (`llm_chat/calls.rs`). Пока замыкание живо,
  в папке кто-то может искать.
- `IdleCell` в `local_embeddings.rs` — выгрузка модели по простою, уже с возвратом памяти
  аллокатору.
- Фронт: `useIndexStatus(workspace.path)` и `onFolderChanged` нужны только для активной папки.
  Файлы, Changes и счётчики слушают `syncStarted` её индекса. Фоновые папки в окне никто
  не слушает.

**Чего нет:** у `WorkspaceIndex` нет понятия «в папке сейчас ищут». Нет синка только по
словам. Открытие папки сериализует `AgentState::folder_change`, а не сам индекс.

## Модель дешевле в три раза — проба 2026-11-18

Из 320 МБ модели около 280 занимает trie словаря в `tokenizers` (Unigram): у каждого
байта каждого токена свой `AHashMap` детей. Так 2.9 МБ строк словаря превращаются в
сотни мегабайт. Проба (`scratchpad/tokprobe`, вне репозитория) оставила пайплайн HF как
есть (нормализатор Precompiled + 34 `Replace` + `Strip`, Metaspace, добавленные `[PAD]`
и `[UNK]`), а модель Unigram подставила свою — через их трейт `Model` в
`TokenizerImpl`. Своё в ней только плоская trie: на каждый узел диапазон отсортированных
рёбер. И Viterbi из HF `encode_optimized`, построчно, с теми же `K_UNK_PENALTY`,
слиянием `[UNK]` и правилом «при равных строках побеждает последний id».

| | HF `tokenizers` | своя trie в пайплайне HF |
|---|---|---|
| в памяти после загрузки | +281 МБ | +40 МБ (структуры — 14.6 МБ, 646 тыс. узлов; остальное — нормализатор и остаток разбора JSON) |
| загрузка | 227–243 мс | 72–94 мс |
| 6 924 текста, 27 МБ (три репозитория, русский и английский) | 1307 мс | 860 мс |
| id токенов | — | **совпали бит в бит** на всех текстах, включая литералы `[UNK]`/`[PAD]`, é, 世界, эмодзи, CRLF |

Модель целиком — около 100 МБ вместо 320: замер в release после LZ-1 — загрузка 0.11 с
вместо 0.35, +100 МБ в памяти (~30 токенизатор, ~70 int8-таблица), после выгрузки +34 МБ.
Таблицу через mmap не сжать: тексты трёх репозиториев задевают 25.6 тыс. разных
токенов, а это 3 708 из 4 242 страниц по 16 КБ.

Что посмотрено из готового — каждое прогнано на том же корпусе (6 925 текстов, 27 МБ),
id сравнены с HF:

| | id как у HF | структура словаря | 27 МБ текста, все ядра | что ещё |
|---|---|---|---|---|
| своя плоская trie | да | 8.4 МБ | ~1.05 с | ~70 строк, без зависимостей |
| `crawdad` 0.4 (double-array, по символам) | да | 5.5 МБ | ~1.6 с | строится за 54 мс; позиции в символах — нужен перевод в байты |
| `yada` 0.7 (double-array, по байтам) | да | 3.7 МБ | ~4.3 с | строится за 240 мс; паникует на `\0` в запросе — нужен обход |
| `kitoken` 0.11 | **нет**: 757 текстов из 6 925, 0.1% токенов | — | 9.9 с в один поток | свой разбор `tokenizer.json` и свой Unigram (слияния, не Viterbi) |
| `pplx-unigram` | не запускался | ~9 МБ по их статье | — | нет на crates.io; `Replace`/`Strip` пропускает |

- **`kitoken`** наш файл не читает вовсе: тип нормализатора `Strip` ему неизвестен (ждёт
  `StripNormalizer`). С переименованием в копии файла он работает, но по-своему
  нормализует пунктуацию: `...` у HF — три `▁.`, у него — один `▁...`. Косинус векторов
  у разошедшихся текстов — от 0.962, медиана 1.0: искать он бы не мешал, но векторы
  другие — это новый `LOCAL_MODEL_ID` и пересборка всех индексов, а `parity.json` с
  Python перестаёт сходиться. И он тянет полтора десятка крейтов (protox, logos,
  sentencepiece-model…).
- **`crawdad` и `yada`** заменяют только trie, Viterbi остаётся нашим. Они экономят 3–5 МБ
  из ~110 МБ модели. За это — новая зависимость, перевод позиций (crawdad) или обход
  `\0` (yada), и обе медленнее плоской trie на нашем словаре (на 271 тыс. токенов
  двоичный поиск по рёбрам узла дешевле, чем кажется: у большинства узлов одно ребро).
- **`pplx-unigram`** — та же идея, что у нас, но на crates.io его нет, а свой разбор
  конфига пропускает `Replace` и `Strip`: токены бы разошлись. Нужен был бы форк.

## Решения

После LZ-1 ленивые эмбеддинги сняты (вопрос 3): решения 3, 6 и 7 и «тёплое» состояние
решения 1 не делаются — открытая папка синкается полностью. Остаются холодные папки:
решения 1 (холодная / открытая), 2, 4 и 5 — в LZ-4.

### 0. Токенизатор — своя trie внутри пайплайна HF

`Int8Model` держит `TokenizerImpl<CompactUnigram, …>` вместо `Tokenizer`. Нормализация,
пре-токенизация и добавленные токены остаются в `tokenizers`: они точные и уже
собираются, своя копия 34 замен и Precompiled была бы второй реализацией, которая
может разойтись. Своё — только модель (`infra/compact_unigram.rs`). Векторы не меняются,
поэтому индекс пересобирать не нужно и `LOCAL_MODEL_ID` остаётся прежним.

Отвергнуто: `kitoken` (другие токены — пересборка индексов и расхождение с Python),
форк `pplx-unigram` (свой разбор конфига — та самая вторая реализация), `crawdad`/`yada`
под trie (3–5 МБ из ~110 ценой зависимости и скорости).

### 1. Три состояния папки: холодная, тёплая, горячая

- **Холодная** — открыта в окне, но не активна и хода в ней нет. Индекса в памяти нет:
  хранилище закрыто, наблюдателя нет, модель не нужна. Папка — только строка в реестре
  открытых.
- **Тёплая** — активная папка без хода. Она под наблюдением, синк идёт только по словам:
  Файлы, Changes и счётчики окна живут на `syncStarted` её индекса (AGENTS.md, «Reuse a
  signal before adding one»), а синк по словам модели не грузит.
- **Горячая** — в папке идёт ход (или работает помощник, см. решение 2). Наблюдение и
  полный синк, вектора догоняются. Это единственное состояние, в котором грузится модель.

Почему не «тёплая для всех открытых»: тогда наблюдение и синк по словам остаются на N
папок. На Linux это лимит inotify, при запуске — N полных обходов. И окну эта тёплость
ни для чего не нужна, никто её не читает. Почему активная папка не горячая: так просил
пользователь — эмбеддинги работают только во время хода. Правка в редакторе без агента
модель не поднимает.

### 2. Горячая — пока жив хотя бы один поисковик папки

Счётчик держит сам поисковик. `WorkspaceIndex::searcher(root)` открывает папку, если
она холодная, делает её горячей и возвращает `CodeSearchFn`, внутри которого лежит
guard. Когда отпускается последний поисковик (кончился ход, закончил помощник, которому
его клонировали), папка остаётся открытой, если она активна, и закрывается, если нет
(~~остывает до тёплой~~ — тёплого состояния нет, см. начало «Решений»).

Отвергнуто — считать ходы по `AgentState` (начало и конец `chat_start`). Помощник
держит поисковик дольше хода, rerank оборачивает его. Счёт по ходам пропустил бы обоих,
и они искали бы в папке, которую уже никто не синкает. Guard в замыкании покрывает
каждого держателя без отдельного учёта.

### 3. Вектора догоняют в начале хода, а не при сохранении

Когда папка становится горячей, на своём потоке запускается синк с эмбеддингами: по
словам он доделывает то, что изменилось, пока папка была холодной или тёплой, и
эмбеддирует изменённые куски. Ход тем временем подключается к провайдеру и ждёт первый
ответ модели — это секунды. Догонка kibo с нуля — 0.35 с на загрузку модели и около
0.6 с на вектора. Поиск, пришедший раньше, отвечает из того, что уже готово
(`EmbeddingIndex` пишет пачками, это поведение уже есть), а `code_search` в этом
случае помечает результат как слабый.

Синк тёплой папки по словам всё равно убирает из памяти вектора исчезнувших кусков (это
та половина `EmbeddingIndex::sync`, которая модель не трогает). Иначе ушедшие id занимали
бы места в top-k смыслового поиска до следующего хода.

Отвергнуто — эмбеддировать на первом поиске. Тогда первый `semanticSearch` хода ждал
бы загрузку модели и вектора, а в начале хода эта задержка не видна.

### 4. Открытием и остыванием владеет сам индекс

Сейчас папку открывают команды под `folder_change`. Теперь горячей её делает ещё и ход —
`searcher_of` в `chat_start`, вне этого замка. Поэтому `WorkspaceIndex` сам держит
состояние каждой папки (холодная / открывается / тёплая / горячая с числом держателей)
под своим замком, а медленное открытие хранилища идёт вне замка, как и сейчас
(«reading a large store takes seconds»). Две просьбы открыть одну папку получают один
индексатор. Остывание, которое пришлось на открытие, не закрывает только что открытое
из-под нового держателя.

`workspace_close` горячую папку по-прежнему не закроет: ход это запрещает (F-8,
инвариант 5). Помощник, переживший ход, держит свой `Arc<RepoIndexer>`: он доищет по
закрытой папке без синка, а его guard при отпускании папку не найдёт и ничего не сделает.

### 5. Запуск открывает индекс только активной папки

`workspaces_restore` перестаёт открывать индексы фоновых папок (`open_index_behind`
уходит). Запуск с десятью папками стоит как запуск с одной. Смена активной согревает
новую папку и остужает прежнюю, если в ней нет хода.

### 6. Модель выгружается быстрее

С эмбеддингами только во время ходов простой в 10 минут — это 320 МБ между ходами,
пока человек читает ответ. Загрузка стоит 0.35 с, поэтому простой сокращается до
2 минут (`DEFAULT_IDLE_UNLOAD`). Выгрузку по «последний горячий остыл» не делаю: простой
уже покрывает этот случай, а ход, начатый через минуту после прошлого, модель не
перезагрузит.

### 7. Бейдж говорит, что смысловой поиск строится во время хода

У тёплой папки бейдж в композере показывает «Indexed», а в подсказке — «Search by meaning
catches up when the agent works here» вместо счётчика векторов. В начале хода бейдж,
как и сейчас, показывает «Indexing N%», пока вектора догоняют. Фазы и события не меняются:
горячая папка шлёт те же `EmbeddingProgress`.

## Нарезка

Каждый этап — отдельный коммит с тестами и мутационной проверкой
([11-mutation-testing.md](11-mutation-testing.md)).

**LZ-0. Проба — без кода приложения.** На kibo и на самом большом локальном репозитории
(release) замерить: синк без изменений (сколько стоит прогреть папку), открытие
хранилища с загрузкой векторов, догонку после `git checkout` на соседнюю ветку. Если
прогрев дольше секунды, у остывания появляется пауза (папка остаётся горячей ещё
сколько-то после последнего держателя); если нет — остывание сразу.
LZ-1 от этого замера не зависит и может идти первым. **Сделано:** на kibo открытие
хранилища 23–53 мс, синк без изменений 45–72 мс — остывание сразу (вопрос 1).

**LZ-1. Компактный токенизатор.** Решение 0. Тесты: id совпадают с HF `Tokenizer` на
наборе с краями (литералы `[UNK]`/`[PAD]`, символы вне словаря подряд, пустая строка,
одни пробелы, CRLF, эмодзи) — в обычном прогоне, на маленьком словаре; на настоящем
словаре и тексте репозитория — в `local_embeddings -- --ignored` вместе с `parity.json`;
дубли строк в словаре — побеждает последний id; при равных путях Viterbi выбирает то же,
что HF. Цифры памяти и загрузки — в шапку `local_embeddings.rs`.

**LZ-1 — сделано 2026-11-18.** `infra/compact_unigram.rs`; `Int8Model` на
`CompactTokenizer`. id совпадают с HF на маленьком словаре с краями, на моделях напрямую
(слитая цепочка `[UNK]`, которая сама — строка словаря) и на всём тексте репозитория
(`local_embeddings -- --ignored`, 10 тестов, `parity.json` сходится). Модель: +100 МБ
и 0.11 с вместо ~320 МБ и 0.35 с. Мутационная проверка: 25 мутантов, пойманы 24, один
эквивалентен — `[UNK]`, предложенный и там, где символ накрыт однобуквенным токеном: тот
токен от того же начала строго дешевле (`s ≥ min > min − 10`). В первом прогоне выжили и
закрыты тестами: медиана по строкам с дублями; штраф `[UNK]`, «первый счёт вместо
наименьшего» и поиск слитой цепочки `[UNK]` — эти три я счёл эквивалентными, ревью
показало входы: при минимуме не первым в словаре путь `unk + kv` против `zk + v`
переворачивается (добавлены `zk`, `v`, `kv` и текст `zkv`), а `[UNK][UNK]` бывает строкой
словаря (тест на моделях напрямую, с цепочкой в начале и после токена).

**~~LZ-2. Синк по словам.~~ Снят 2026-11-18** (вопрос 3). `RepoIndexer::sync` умеет проход без эмбеддинга: модель не
вызывается, вектора ушедших кусков убираются, `SyncFinished` приходит как обычно.
Тесты: синк по словам не зовёт модель (считающий фейк); убирает вектор удалённого
файла; полный синк после него эмбеддирует то, что накопилось; `status.embedded` верен
после обоих.

**~~LZ-3. Горячая папка — пока жив поисковик.~~ Снят 2026-11-18** как отдельный этап: эмбеддинги
больше не зависят от хода, а guard в поисковике (решение 2) — то, что держит открытой
фоновую папку, — переходит в LZ-4. `WorkspaceIndex` держит состояние папки,
`searcher` возвращает замыкание с guard, первый держатель запускает полный синк,
наблюдатель синкает полностью только горячую папку. Тесты: сохранение в папке без
держателя модель не зовёт; первый `searcher` эмбеддирует накопленное; сохранение при
живом поисковике эмбеддируется; после отпускания последнего — снова только слова;
клон поисковика (как у помощника) держит папку горячей после отпускания оригинала; две
папки горячи и остывают порознь.

**LZ-4. Холодные папки — сделано 2026-11-18.** Индекс открыт только у активной папки и тех, чей поисковик
жив (решение 2: guard в `CodeSearchFn`).
`workspaces_restore` открывает только активную, `activate` согревает новую и остужает
прежнюю, `searcher` открывает холодную и закрывает её после последнего держателя.
Открытием владеет `WorkspaceIndex` (решение 4). Тесты: запуск с тремя папками открывает
индекс одной; смена активной снимает наблюдение с прежней; ход в фоновой папке открывает
её и закрывает после; гонка двух `searcher` одной холодной папки даёт один индексатор и
один первый синк; остывание во время открытия не закрывает папку нового держателя;
отпускание поисковика закрытой папки ничего не делает.
Как сделано: счёт поисковиков на папку с эпохой — `close` начинает новую, и поисковик,
переживший закрытие (помощник), не закрывает папку, открытую заново; открытия
сериализованы одной блокировкой (`ponytail:` — по слоту на папку, если ожидание станет
заметным); папку, которую оставили, пока читался её стор, открытие бросает. Ход берёт
поисковик в `spawn_blocking`: холодную папку он открывает за десятки миллисекунд.
Мутационная проверка: 18 мутантов, 17 пойманы, 1 эквивалентный (запись со счётом 0 не
убирается из карты — `in_use` смотрит на счёт); в первом прогоне выжили ещё 3 — открытие
без блокировки, брошенное открытие сохранено, `close` оставляет счёт; тесты добавлены
(восемь поисковиков разом видят один индексатор; переключение, пока читается стор;
старый поисковик не держит папку, открытую заново).

**~~LZ-5. Простой модели и бейдж.~~ Снят 2026-11-18** (вопросы 2 и 3). `DEFAULT_IDLE_UNLOAD` — 2 минуты, текст `describeIndex`
для тёплой папки. Тесты: `describeIndex` для готовой папки без хода; живой тест
`local_embeddings -- --ignored` после правки.

**LZ-6. Документы — сделано 2026-11-18.** `docs/README.md`, `CHANGELOG.md`, в `10-multi-workspace.md` пометка, что
индекс теперь не у каждой открытой папки, шапка `local_embeddings.rs` (когда грузится
модель), строка про индекс в `AGENTS.md`, если её формулировка разойдётся с кодом.

Живые проверки после LZ-4: `search_bench` (синк трогается, ранжирование нет — числа должны
совпасть с замером выше) и запущенное приложение: пять открытых папок, RSS до первого хода
и после него, модель выгружается через 2 минуты после хода.

## Вне плана

- **Убрать эмбеддинги и переводить русский запрос на английский перед поиском.** Каждый
  поиск стоил бы лишний вызов модели, а сигнал «этого нет» в замере не держится и с
  английскими запросами. Вернёмся, если ленивый индекс не снимет цену.
- **Не выгружать модель вовсе.** После LZ-1 она весит ~110 МБ. Но в
  остальное время она всё равно не нужна, а загрузка стоит 0.35 с — простой
  остаётся.
- **Модель в отдельном процессе.** Выгрузка стала бы надёжной (процесс умер — память
  ушла), но это IPC на каждый поиск, а `release_freed_memory` уже возвращает память.
  Не нужно.
