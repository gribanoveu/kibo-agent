# 14. План: качество семантического поиска

Статус: **шаги 0–5 сделаны** (см. «Результаты»). Что делаем с `semanticSearch` дальше, в каком порядке и как
каждое изменение проверяется. Реранкер и модели, требующие нейросетевого рантайма, —
отдельно, в [13-reranker-research.md](13-reranker-research.md).

## Отправная точка

Бенч `search_bench` (93 вопроса, три репозитория, модель ru-en), 2026-09-21, MRR:

| | MRR |
|---|---|
| все вопросы | 0.564 |
| на английском | 0.619 |
| **на русском** | **0.457** |
| ответ — документация | 0.589 |
| ответ — место вызова | 0.444 |

Главная слабость — **русский вопрос к коду на английском**. Большая часть пунктов ниже
бьёт именно в неё.

Что уже есть и не повторяется: гибрид BM25 + смысл через `fuse_rrf` (веса подобраны
бенчем), структурная нарезка (tree-sitter, заголовки), `includeDocs`, вес истории git,
подсказки в `meta.hint`.

## Общие правила для каждого пункта

- Отдельный коммит на пункт, в нём — тест, который падает на старом поведении, и мутации
  по [11-mutation-testing.md](11-mutation-testing.md).
- Пункт, меняющий ранжирование, **прогоняется бенчем до и после**
  (`cargo test --release search_bench -- --ignored --nocapture`); цифры — в раздел
  «Результаты» этого документа.
- **Критерий принятия ранжирования:** общий MRR не падает, целевая группа растёт, ни одна
  группа (язык, тип ответа, репозиторий) не проседает больше чем на 0.02. Не прошло —
  изменение не вливается, цифры всё равно записываются.

## 0. Подготовка бенча

Нужна, чтобы пункты 1 и 4 было чем мерить.

- **Пары ru/en.** В бенче 19 ответов, на которые есть вопрос и по-русски, и
  по-английски. Бенч печатает для них отдельную строку: MRR русских формулировок, MRR
  английских. Разница — **потолок пункта 1**: сколько русские вопросы выиграли бы, если
  бы модель переписала их на английский.
- **Режим «пара в одном вызове»** (для пункта 4): для тех же 19 ответов — поиск по обеим
  формулировкам разом, как это сделал бы `queries`.
- Изменения только в `services/search_bench.rs`, приложение не трогается.

## 1. Запрос на языке кода (п. 5 — rewriting, step-back, HyDE)

**Идея.** Преобразование запроса уже делает сама модель-агент — это бесплатно и не требует
второй LLM. Ей надо сказать, как писать запрос под наш индекс.

**Изменение** — только описание `semanticSearch` (`tools/semantic_search.rs`):

- писать `query` на языке, на котором написан код (обычно английский), даже если
  пользователь спросил по-русски; для документации на русском — по-русски;
- класть в `fts` предполагаемые идентификаторы (`sendNotification`, `RetryPolicy`),
  а не слова вопроса;
- сложный вопрос — несколькими поисками по частям, а не одним длинным (decomposition);
- если конкретного места не видно — сначала общий запрос о подсистеме, потом уточнение
  по найденному имени (step-back);
- можно писать запрос так, как выглядел бы искомый код (HyDE силами самой модели).

**Проверка.** Бенч сырые формулировки пользователя не переписывает, поэтому эффект
напрямую не измерить. Меряем потолок (п. 0, пары ru/en) и смотрим на транскрипты:
пишет ли модель английские запросы на русские вопросы. Тест — на наличие правил в
описании инструмента (как `the_model_is_told_how_its_memory_works`).

**Цена:** одна правка описания. **Риск:** модель переводит запрос и к русской
документации — описание явно разводит эти случаи.

## 2. Контекст фрагмента в эмбеддинге (A)

**Идея.** Contextual Retrieval без LLM и без сети. Сейчас эмбеддинг считается по голому
тексту фрагмента; имя объявления есть только в BM25, путь — только в `PATH_BOOST`.
Фрагмент `retry()` внутри `SendNotificationService` не знает, что он про отправку
уведомлений.

**Изменение.**

- `services/embedding_index.rs`, `sync`: эмбеддить не `text`, а
  `"{path}\n{qualified_name}\n{text}"` (без `qualified_name`, когда его нет). BM25 не
  меняется — там имя уже есть с весом.
- Смена `model_id` (например, суффикс `+ctx`), чтобы индекс пересчитался целиком, а не
  смешал старые вектора с новыми. Запрос эмбеддится как раньше.
- Путь — разбитый на слова (`send_notification_service` → `send notification service`),
  иначе статическая модель видит его одним неизвестным токеном. Проверить на бенче оба
  варианта.

**Варианты для бенча:** только путь; только имя; путь и имя. Статическая модель
усредняет токены, поэтому заголовок весит пропорционально длине — длинный путь может
перетянуть короткий фрагмент. Если так — брать имя файла вместо полного пути.

**Тест:** текст, который уходит в модель, содержит путь и имя (фейковая модель в тестах
`code_search` записывает, что ей дали); смена `model_id` запускает пересчёт.

**Цена:** полная переиндексация у пользователей при обновлении (секунды на средний
репозиторий — `docs/06-port-plan.md`, замеры индексации).

## 3. Разнообразие по файлам (D, п. 9 — MMR)

**Идея.** В топ-10 могут прийти пять фрагментов одного файла, и тогда второе место по
файлам уезжает за пределы выдачи. MMR в простейшем виде, без векторов.

**Изменение.** `services/code_search.rs`, сборка `matches`: не больше `MAX_PER_FILE`
(начать с 2) фрагментов одного файла, пока не набрано `top_k`; отложенные — в конец,
если без них выдача неполная. Совпадения по имени (`Symbol`) под ограничение не
попадают: объявление, названное в запросе, важнее разнообразия.

**Бенч:** file@5, file@10 и MRR; проверить 2 и 3 на файл.

**Тест:** пять сильных фрагментов одного файла и один слабее из другого, `top_k = 3` —
второй файл в выдаче; при `top_k` больше числа файлов отложенные возвращаются.

## 4. Несколько формулировок за вызов (C, п. 5 — multi-query)

**Делать, если пункт 1 не закрыл разрыв** (пары ru/en в бенче после п. 1 по транскриптам
и по потолку).

**Изменение.**

- `SemanticSearchArgs.queries: Option<Vec<String>>` — дополнительные формулировки к
  `query` (до 3).
- `code_search::search`: по каждой формулировке — список по смыслу и список по словам;
  все списки — в один `fuse_rrf` с теми же весами. Совпадения по имени — объединение.
  История git — по `query`.
- Порт `CodeSearchFn` принимает формулировки списком.
- Описание: «русская и английская формулировки одним вызовом дешевле двух вызовов».

**Бенч:** режим «пара в одном вызове» из п. 0 против каждой формулировки отдельно.

**Тест:** фрагмент, который находит только вторая формулировка, попадает в выдачу;
формулировки сверх лимита отбрасываются.

**Цена:** запрос в 2–3 раза дороже по эмбеддингам и BM25 — миллисекунды.

## 5. Фильтр по пути (E, п. 8 — пре-фильтрация)

**Идея.** `includeDocs` показал, что отсечь лишнее до ранжирования выгоднее любой
подстройки весов. Следующий шаг — дать модели сузить поиск самой: «только `src/main`»,
«без `generated`».

**Изменение.**

- `SemanticSearchArgs`: `glob` и `exclude` с той же семантикой, что у `grep`: `glob` без
  `/` сравнивается с именем файла, со `/` — с путём; `exclude` — всегда с путём.
- Логику сопоставления вынести из `tools/grep.rs` в одно место (`domain/search_query.rs`
  или отдельный `path_filter`) и использовать в обоих инструментах — второй копии не
  заводить.
- Фильтр применяется там же, где `includeDocs`; при заданном фильтре пул кандидатов
  расширяется, как при выключенной документации.
- Подсказка при пустой выдаче из-за фильтра: «ничего не прошло фильтр `glob`/`exclude`».

**Бенч** здесь ничего не покажет — это возможность для модели, а не ранжирование.

**Тест:** `glob` по пути и по имени, `exclude`, пустая выдача с подсказкой; общий
сопоставитель — одни и те же случаи для `grep` и `semanticSearch`.

## Порядок

| Шаг | Что | Ранжирование? | Зачем в этом месте |
|---|---|---|---|
| 0 | пары ru/en в бенче | — | мерило для 1 и 4 |
| 1 | запрос на языке кода | нет (описание) | одна строка, бьёт в главную слабость |
| 2 | контекст в эмбеддинге | да | самый вероятный прирост в самом ранжировании |
| 3 | разнообразие по файлам | да | дёшево, независимо от остального |
| 4 | несколько формулировок | да | только если после 1 разрыв ru/en остался |
| 5 | фильтр по пути | нет | независимо, в любой момент |

Шаги 2 и 3 меняют одно ранжирование — мерить их по отдельности, не вместе, иначе не
понять, что сработало.

## Не входит

- Contextual Retrieval и doc2query **через LLM** — индекс считается встроенной моделью
  без сети ([08-data-policy.md](08-data-policy.md)); вернуться, когда появится локальная
  LLM, и отдельным решением по данным.
- Learned sparse, BGE-M3, late interaction, реранкер — нужен трансформер-рантайм,
  см. [13-reranker-research.md](13-reranker-research.md).
- HNSW и параметры индекса — поиск точный перебором, при наших размерах (тысячи
  фрагментов) не нужен.
- Дообучение статической модели на своих данных — отдельное исследование.

## Результаты

2026-09-21, модель ru-en, MRR.

| | исходно | шаг 2 (путь) | + шаг 3 (≤2 на файл) |
|---|---|---|---|
| все 93 | 0.564 | 0.577 | **0.583** |
| laika-agent | 0.629 | 0.654 | 0.663 |
| docflow | 0.432 | 0.465 | 0.468 |
| wowtax | 0.566 | 0.556 | 0.558 |
| на английском | 0.619 | 0.632 | 0.635 |
| на русском | 0.457 | 0.473 | 0.482 |
| пары: en | 0.720 | 0.765 | 0.765 |
| пары: ru | 0.384 | 0.420 | 0.429 |
| документация | 0.589 | 0.589 | 0.596 |
| file@5 / file@10 | 71 / 77 | 71 / 76 | 74 / 78 |
| decl@5 | 53 | 53 | 52 |

**Шаг 0.** Пары ru/en в бенче: 19 русских и 22 английских вопроса на одни и те же
ответы. Исходный разрыв 0.384 против 0.720 — столько русский вопрос теряет только на
языке.

**Шаг 1.** Правила в описании `semanticSearch`: запрос на языке кода, идентификаторы в
`fts`, разбиение, step-back, запрос в виде ожидаемого кода. Бенч эффект не меряет —
проверять по транскриптам.

**Шаг 2.** Эмбеддинг — `путь словами + текст`, `EMBEDDED_TEXT_VERSION = "+path1"`.
Варианты на бенче: путь целиком 0.577, имя файла 0.574, имя файла и объявление 0.585, но
русские из пар −0.028 (не проходит), только объявление 0.558. Взят путь целиком:
проходит критерий, лучший из прошедших. Опасение, что длинный путь размоет короткий
фрагмент, не подтвердилось.

**Шаг 3.** Не больше двух фрагментов с файла, объявления из запроса без лимита. При двух
фрагментах 0.583 и file@5 +3, при трёх — 0.579 и file@5 без изменений. Взято два;
`decl@5` −1 — второй фрагмент нужного файла иногда уступает место другому файлу.

**Шаг 4.** `queries` в `semanticSearch` — до трёх дополнительных формулировок;
`code_search::search_many`: по каждой — список по смыслу и по словам, все в один
`fuse_rrf`; имена — из всех формулировок; `fts` заменяет слова только первой; история git —
по первой. Бенч, режим «пара в одном вызове» (19 русских вопросов с английской парой):

| | MRR | file@5 |
|---|---|---|
| только русская формулировка | 0.429 | 11 |
| только английская | 0.765 | 20 из 22 |
| **русская + английская одним вызовом** | **0.798** | **19 из 19** |

Пара одним вызовом лучше и английской в одиночку: русская формулировка добавляет
документацию и комментарии на русском. Одиночный запрос ранжируется как раньше (docflow и
wowtax совпали построчно; сдвиг в laika-agent — от правки самого индексируемого кода).

Попутно: пометка «слов запроса нет в индексе» ставится, только если это верно для **каждой**
формулировки — русская к английскому коду почти целиком состоит из «неизвестных» слов.

Мутации: десять, все пойманы; три выжили в первом прогоне и получили тесты (пустые
формулировки занимали место в лимите; `fts` не должен подменять слова последующих
формулировок; последующие ранжируются и по словам).

**Шаг 5.** `glob` и `exclude` в `semanticSearch`, сопоставитель вынесен в
`domain::search_query::PathFilter` и общий с `grep`; с фильтром пул кандидатов
расширяется; при пустой выдаче из-за фильтра — подсказка.

**Мутации: четырнадцать, все пойманы.** Четыре выжили в первом прогоне и получили тесты:
заголовок проверялся через ничью равных векторов; версия текста в `model_id` не была
проверена; нет случая с тремя объявлениями из запроса в одном файле; нет случая, где
фильтр пути отсекает весь пул.
